# 术语白名单的人工维护（新增 / 编辑 / 删除）（spec）

Status: ready-for-agent
Branch: 待定（建议 `feat/term-whitelist-crud`）

---

## Problem Statement

**① 管理端只能启停，不能增删改。**

知识库管理页的「术语白名单」tab 现在只有「确认启用 / 停用」一个操作。种子灌进来的 72 条（部位 29 / 症状 43）之外，管理员**没有任何办法**把系统漏掉的词加进去，也没有办法纠正一个归错类的词、或删掉一个明显加错的词。页面上「来源」列已经能区分「模型抽取 / 人工维护」，但「人工维护」这条路径其实不存在。

后果不是"少一个按钮"，而是白名单作为**受控词汇表**无法被真正策展：一个真实主诉里反复出现的症状词如果不在表里，信息充足性门槛（`SufficiencyRule` 的子串匹配）会一直把它当"过于笼统"，而管理员只能去改数据库。

**② 术语种子代码是这条路的替代品，但它只会在空表时触发，且判存在口径有隐患。**

`SeedDataRunner.seedMedicalTerms()` 用 `medicalTermMapper.selectCount(null) > 0` 判断"表是不是空的"——`selectCount` 会带上 `deleted=0`。一旦 72 条种子全被逻辑删除，它会看到 0 行、判定空库、重新灌种子，INSERT 撞物理唯一键 `uk_mt_term_type`，`ApplicationRunner` 抛异常导致 **Spring Boot 启动失败**。这正是《数据库设计.md》§0.1 记录的那场 `sensitive_word` 事故的同款形状，只是术语表此前没有删除入口，所以一直没被触发。

**③ 管理端 LLM 配置页有一个永不生效的输入框。**

「追问升级阈值（轮次）」对应键 `guide.upgrade.rounds`：它只出现在常量定义、管理端白名单、单测三处，**全仓库没有任何业务代码读它**。真正驱动"追问到上限就强制出结论"的是 `chat.ask.max.rounds`（页面标签「追问轮数上限」）。管理员改前者，页面提示"保存后立即生效"，实际什么都不发生——与管理端自己的规定「不让页面产生假配置」直接冲突。

---

## Solution

**① 两端补齐术语白名单的增删改。**

后端新增三个接口（新增 / 编辑 / 删除），与既有启停并列；管理端知识库页术语 tab 补上对应入口。领域规则落在 `kb` 模块的 `MedicalTermService`，管理端只做编排与 DTO 映射——与既有 `toggle` 的路径完全一致。

**② 删除术语种子代码。**

人工维护入口上线后，种子不再是唯一来源。删掉术语种子（保留科室语料、敏感词、健康标签种子），白名单从此只由 `medical_term` 表决定。

**③ 移除假配置。**

从管理端白名单与初始化脚本中移除 `guide.upgrade.rounds`，页面只留真正生效的「追问轮数上限」。库中已存在的那行数据保留（没有代码会读它，删数据不可逆）。

## User Stories

1. 作为管理员，我想在术语白名单页新增一个词，以便把真实主诉里反复出现、但种子没覆盖的症状词补进白名单。
2. 作为管理员，我想在新增时选择「部位」或「症状」类别，以便这个词进入正确的分组。
3. 作为管理员，我想让新增的词立刻生效，以便不用重启服务、也不用等缓存过期。
4. 作为管理员，我想在新增一个已存在的词时看到明确提示，以便知道它已经在表里、不必重复添加。
5. 作为管理员，我想在新增一个曾被删除的词时让它直接恢复，以便不必先去找它的 id 再恢复。
6. 作为管理员，我想在新增单字词时被拒绝并得到原因说明，以便知道单字会放宽信息充足性门槛、不是系统坏了。
7. 作为管理员，我想在新增时被拦下首尾空格、内部空白与超长输入，以便白名单里不出现难以排查的脏词。
8. 作为管理员，我想编辑一个词的词面，以便修正录入时的错字。
9. 作为管理员，我想编辑一个词的类别，以便把误归到「部位」的症状词改到「症状」下。
10. 作为管理员，我想在编辑撞上另一个已存在的词时被拒绝，以便不会静默覆盖另一行。
11. 作为管理员，我想在编辑撞上一个曾被删除的词时得到「请直接在新增里恢复」的提示，以便知道下一步该做什么。
12. 作为管理员，我想编辑时不能改启用状态，以便"启停"始终只有一个入口、不会出现两处各说各话。
13. 作为管理员，我想删除一个加错的词，以便它不再参与入口判定。
14. 作为管理员，我想删除前看到确认弹窗并写明后果，以便知道这不是不可逆的物理删除。
15. 作为管理员，我想删除后可以用同一个词重新新增来恢复它，以便误删之后有退路。
16. 作为管理员，我想删除词后它立刻从入口判定里消失，以便不用等缓存过期。
17. 作为管理员，我想对模型抽取的词同样能编辑和删除，以便白名单的最终形态完全由人决定。
18. 作为管理员，我想看到模型抽取的词在被人工编辑后「来源」仍显示「模型抽取」，以便还能追溯它最初是怎么来的。
19. 作为管理员，我想新增成功后列表自动去掉筛选并回到第 1 页，以便立刻看到自己刚加的词。
20. 作为管理员，我想删除当前页最后一条后自动回到上一页，以便不会停在一页空白上。
21. 作为管理员，我想确认同一个词可以同时作为「部位」和「症状」各占一行，以便不必先猜它"该算哪类"才能加。
22. 作为管理员，我想让术语表在空库时保持为空、由我逐个添加，以便白名单的初始内容是我认可的那份，而不是自动灌进去的。
23. 作为维护者，我想让术语表被删空后重启服务不会崩，以便「删到空」不构成一条启动失败路径。
24. 作为维护者，我想让管理端参数页上每个输入框都真的控制行为，以便管理员不会对着一个假开关反复调试。
25. 作为维护者，我想在文档里看到「术语白名单可维护」与「种子里没有术语」的事实，以便下一个人不必重新考古。
26. 作为患者，我想让管理员补进白名单的口语症状词真的影响分诊，以便「肚子疼」这类短主诉不再被反复模板追问。

## Implementation Decisions

### 模块与分层

- **`kb`（领域规则）**：`MedicalTermService` 增加 `add` / `update` / `remove` 三个方法；判重、复活、校验、刷新内存白名单都在这一层。`MedicalTermMapper` 增加两条绕开逻辑删除的自定义 SQL（物理判存在 + 复活），与 `SensitiveWordMapper` / `HealthTagMapper` 的既有写法同形。
- **`admin`（编排）**：`KbAdminService` 增加对应的编排方法（DTO ↔ 实体），`KbAdminController` 增加三个端点；不把领域规则写进 controller 或 service 的编排层。
- **`common`**：新增错误码 `TERM_EXISTS`（kb 段 5xxx，message「术语已存在」）。
- **前端**：`views/admin/KbManage.vue` 的术语 tab + `api/admin.js` 三个调用。沿用科室 tab 的弹窗范式，不新造组件。

### 接口契约

| 方法 | 路径 | 请求体 | 返回 |
|---|---|---|---|
| `POST` | `/api/admin/kb/terms` | `{ term, type }` | 该行 `TermVO` |
| `PUT` | `/api/admin/kb/terms/{termId}` | `{ term, type }` | 该行 `TermVO` |
| `DELETE` | `/api/admin/kb/terms/{termId}` | — | `Result<Void>` |
| `POST` | `/api/admin/kb/terms/{termId}/toggle` | —（既有） | 该行 `TermVO` |

`type` 取 `part` / `symptom`（英文小写编码值）；解析按 code 遍历匹配，**禁止 `valueOf`**（既有约定）。

### 领域规则（新增）

- 词面 `trim` 后长度 **2–20 字**；**拒绝单字**；拒绝内部空白与换行。
- **单字被拒的理由必须如实告知**：`SufficiencyRule` 用子串匹配，单字会让几乎所有主诉都被判「含医学术语」，信息充足性门槛当场失真。现有种子里确实有单字，但那是历史集合，不构成新增时放行的先例。
- 新增：`source = manual`、`enabled = 1`，**不受 `term.manual.review` 约束**——该开关的语义是「模型抽取的词要不要人工确认」，人工亲手添加的词已经过一次确认。
- 判存在按**物理行**（含 `deleted=1`）：
  - 活跃行存在 → `TERM_EXISTS`；
  - 仅有已删除行 → **复活**（`deleted=0`、`enabled=1`，`source` 保持原值）。
- 并发撞键：捕获 `DataIntegrityViolationException` 并转成 `TERM_EXISTS`，不冒 500。

### 领域规则（编辑）

- 可改**词面 + 类型**；**不接收启用状态**（启停只有 toggle 一个入口）。
- 目标行不存在（含已逻辑删除）→ `TERM_NOT_FOUND`。
- 新 `(term, type)` 与**另一行**物理冲突 → `TERM_EXISTS`，文案区分：活跃行「该术语已存在」；已删除行「该术语曾被删除，请直接在新增里填写以恢复」。
- 只改词面/类型，**`source` 与 `enabled` 原值不动**；`refresh()` 立即重载。

### 领域规则（删除）

- 逻辑删除（`@TableLogic`），不物理删；`refresh()` 立即重载。
- 不校验是否被历史记录引用——术语表是**当前生效源**，不是历史快照；历史导诊记录读的是证据快照，不受影响。
- 目标行不存在 → `TERM_NOT_FOUND`。

### 去重口径

唯一键 `(term, type)`：**同一个词允许同时是「部位」和「症状」各一行**，与 `health_tag` 的既有口径一致。`enabledTerms()` 最终是一份扁平 Set，两行同词对判定零影响。

### 种子

- 删除 `SeedDataRunner.seedMedicalTerms()` 与 `SeedCorpus.PART_TERMS` / `SYMPTOM_TERMS`；随之移除 `SeedDataRunner` 不再需要的 `MedicalTermMapper` / `MedicalTermService` 依赖及对应的测试 mock。
- 科室语料、敏感词、健康标签种子**不动**。
- **接受的代价（已确认）**：新库从 `mysql_init.sql` 建起来后 `medical_term` 为空表，需管理员逐个新增。空表期间：`SensitiveGuard` 的术语防误杀不生效；`SufficiencyRule.tooVague()` 对短于 6 字的主诉一律判信息不足。现有真实库的 72 条不受影响。

### 假配置清理

- 从 `SysConfigAdminService` 的 `ParamSpec` 白名单删除 `guide.upgrade.rounds`；从 `mysql_init.sql` 的 `sys_config` 种子删除 `('c02', 'guide.upgrade.rounds', ...)`；删除 `SysConfigService.KEY_UPGRADE_ROUNDS` 常量（删除后无消费者）。
- 「追问轮数上限」（`chat.ask.max.rounds`）**保持不动**——它本来就是真正生效的那个。
- 库中已存在的那行 `sys_config` 数据**保留**。
- `cluster.upgrade.count` 本轮不碰（仍在代码侧，不进白名单）。

### 前端交互

- 术语 tab 工具条加「新 增 术 语」；弹窗字段 = 术语输入框 + 类型下拉（部位 / 症状）。
- 操作列加「编辑」「删除」；编辑与新增共用同一弹窗状态，标题按是否带 id 切换。
- 删除走 `ElMessageBox.confirm`，文案写明：不再参与入口判定、历史导诊记录不受影响、用同一个词重新新增即可恢复。
- 新增成功后**清空关键词与状态筛选并回到第 1 页**；编辑与启停原地刷新；删除后若当前页已空且不是第 1 页，自动回退一页。
- 分页与切条数复用 `utils/pager.js` 的既有工具，不另写。

### 不做

- 不做术语批量导入/导出（敏感词有，术语暂不需要）。
- 不做术语的软删除回收站 UI（用「新增同词即恢复」承担）。
- 不改 `term.manual.review` 对模型抽取词的控制逻辑。
- 不改 `SufficiencyRule` / `SensitiveGuard` 的匹配方式（精确 vs 子串的分工保持现状）。
- 不实现「追问升级」新功能。

## Testing Decisions

**什么是好测试**：只测外部行为——给一个请求/状态，断言落库结果、返回值、或内存白名单的可见内容；不断言私有方法、不 mock 被调用的同类方法内部实现。

**测试缝（沿用既有，不新增缝）**

| 编号 | 缝 | 覆盖 | 先例 |
|---|---|---|---|
| 缝一 | `MedicalTermService`（mock `MedicalTermMapper`） | 领域规则全部：新增成功、撞活跃行、复活已删除行、单字拒绝、编辑撞键（两种文案）、编辑不存在、删除后立即从 `enabledTerms()` 消失、编辑不改 `source` / `enabled` | 既有的三条 `toggle` 测试（`MedicalTermServiceTest`），同一构造方式 |
| 缝二 | `KbAdminService`（mock `MedicalTermService`） | 编排与 DTO 映射：`type`/`source` 按 code 进出、三个方法各自的返回形状 | 既有 `termsUseEnumCodes` / `toggleTermReturnsCodeShape` |
| 缝三 | `SysConfigAdminService` | 白名单里**不再包含** `guide.upgrade.rounds`，且保存该键被拒（2008） | 既有 `SysConfigAdminServiceTest` 的白名单断言组 |
| 缝四（人工） | 真实环境 | ① API 全流程（新增→列表→编辑→启停→删除→同词复活→撞键报错），每步查库确认；② 判定层：新增一个临时症状词，确认一条原本被判「过于笼统」的短主诉通过门槛，验完删除；③ 管理端页面真机点一遍，确认 toast、筛选重置、分页回退 | 本项目一贯的"真实环境验证"，无 E2E 脚本 |

**前端**：不新增测试基建（仓库只有两个纯函数自检脚本，没有组件测试框架）。前端改动靠缝四③覆盖。

**构建闸**：`backend` 全量 `mvn test` 通过；`frontend` 的 `npm run check` 与 `npm run build` 通过。

## Out of Scope

- 术语抽取（LLM 批量实体抽取 → ES terms 聚合 → 白名单候选池）仍然不做；本次的人工新增是它的替代通道，不是它的一部分。
- `track_event` 的管理端查看入口、慢病标签管理端页面、统计看板离线聚合——都是此前登记的其他待办，与本次无关。
- 敏感词的变形词/大小写/全角绕过问题。
- 术语批量导入导出。
- 「追问升级」的新功能设计。
- `mysql_init.sql` 里补 `medical_term` 的初始数据（已明确接受空表）。

## Further Notes

- **两份词表的边界**：`medical_term` 服务入口防误杀与信息充足性判定；患者端「人体图」的字与词是前端自持（已解耦），本次改动对患者端界面零影响——唯一的影响是新增词会改变判定行为。
- **单字限制的理由要写进代码注释**：现有种子里有「头 / 腹 / 心 / 肺」等单字，那是历史集合；新增时拒绝是为了不让子串匹配进一步失真。这条注释是防止后来者"顺手放开"的唯一护栏。
- **`数据库设计.md` §0.1 的状态要更新**：`medical_term` 从「⚠️ 暂无插入路径」变为已实现，这是那张表第一次有插入路径。
- 真实库当前状态（截至 2026-10-17 核实）：`medical_term` 72 行（part 29 / symptom 43），`deleted=1` 为 0 行。删除种子不影响存量数据。
