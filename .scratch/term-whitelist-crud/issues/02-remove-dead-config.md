# 02: 移除永不生效的「追问升级阈值」配置

**What to build:**

管理端 LLM 配置页不再出现「追问升级阈值（轮次）」这个输入框；直接调保存接口传该键返回「不支持的配置项」；而真正生效的「追问轮数上限」仍可改、改完导诊立即用新值。

**事实依据（先说清楚，免得下一个人再考古）：**

- 该键 `guide.upgrade.rounds` 只出现在三处：常量定义、管理端参数白名单、单测。**全仓库没有任何业务代码读它。**
- 真正驱动"追问到上限就强制出结论"的是 `chat.ask.max.rounds`（页面标签「追问轮数上限」），链路 A 里有两处消费。
- 它与后者语义重叠而非互补：接上去等于让两个键控制同一件事，改一个不改另一个，症状比现在更糟。
- 它从建表提交起就只是"被列出来"，从未有实现；原始架构文档里也没有这个设计。

**已定的规则：**

1. 从管理端参数白名单移除该项；从初始化脚本的参数种子里移除该行。
2. 删除对应的配置键常量——删前 `grep` 确认零消费者。
3. **库中已存在的那行配置数据不删**：没有代码会读它，而删数据不可逆，为清理一行脏数据不值得。
4. **「追问轮数上限」保持不动**，它本来就是真生效的那个。
5. **聚合归桶的真实升级阈值本轮不碰**：它仍在代码侧、不进白名单（既有刻意取舍）。
6. **补一条回归单测**：保存该键被拒，把这个决定钉住，防止以后有人"顺手加回来"。

**验收**

- [ ] `grep` 全仓零命中该键与对应常量
- [ ] LLM 配置页刷新后不再出现该输入框，其余参数一个不少
- [ ] 直接调保存接口传该键 → 2008「不支持的配置项」
- [ ] 「追问轮数上限」仍可改、改完导诊立即用新值（回归）
- [ ] `mvn test` 通过

**Blocked by:** None (can start immediately)

**Status:** resolved
