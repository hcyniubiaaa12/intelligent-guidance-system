# 04: 删除术语——端到端

**What to build:**

管理员在术语列表某行点「删除」，确认框说清后果后，该行从列表消失、**立即**不再参与 chat 入口判定；之后用同一个词重新新增即可恢复它。删掉当前页最后一条时自动回到上一页，而不是停在一页空白上。

**已定的规则：**

1. **删除是逻辑删除，不是物理删除。** 确认框文案必须写清三件事：删除后不再参与入口判定、**历史导诊记录不受影响**、用同一个词重新新增即可恢复。**不能含糊成"永久删除"**——它不是。
2. **不校验是否被历史记录引用。** 术语表是**当前生效源**，不是历史快照；历史导诊记录读的是证据快照，天然不受影响。
3. **目标行不存在（含已删除）→ 报「术语不存在」。**
4. **写库后立即刷新内存白名单**，与启停一致。
5. **可删除模型抽取的词。** 白名单的最终形态完全由人决定；`source` 只是审计标签，不构成操作权限。
6. **前端删除后若当前页已空且不是第 1 页，回退一页**再刷新。
7. **恢复路径已由新增那一片承担**：同词新增会命中已删除行并复活。本片**不做回收站 UI**。

**验收**

- [ ] 删除后该行从列表消失，且在判定用的启用词集合里**立即**消失
- [ ] 数据库里该行是逻辑删除（`deleted=1`），不是物理删除、不是 `enabled=0`
- [ ] 确认框文案含恢复路径与"历史记录不受影响"
- [ ] 删除本页最后一条后自动回到上一页
- [ ] 删除后用同一词新增 → 复活为正常行（**与 01 的复活语义串起来验证一次**）
- [ ] 删除不存在的 id → 「术语不存在」
- [ ] 后端单测覆盖逻辑删除与立即失效；`mvn test` 通过
- [ ] `npm run build` 通过、`npm run check` 全绿
