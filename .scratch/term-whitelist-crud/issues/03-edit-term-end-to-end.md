# 03: 编辑术语——端到端

**What to build:**

管理员在术语列表某行点「编辑」，弹出的表单预填当前词面与类型；改成新词面或新类型并保存后，该行就地更新，且**该词的目的地随之改变**（例如把误归到「部位」的症状词改到「症状」下，列表筛选与判定行为都跟着变）。

**已定的规则：**

1. **可改词面 + 类型；不接收启用状态。** 启停已有独立按钮，同一件事给两个入口会让"我刚改的到底生效没有"含糊。
2. **目标行不存在（含已逻辑删除）→ 报「术语不存在」。**
3. **新 `(term, type)` 与另一行冲突 → 报「术语已存在」，且文案要分两种：**
   - 撞的是活跃行：「该术语已存在」；
   - 撞的是**已删除行**：「该术语曾被删除，请直接在新增里填写以恢复」——否则管理员在列表里根本看不到那一行，却被告知"已存在"。
4. **`source` 与启用状态原值不动。** 来源是审计标签：模型抽取的词被人工改过之后仍显示「模型抽取」，否则改一次词面就把来源洗成「人工维护」，以后无法回答"这条是模型提的还是人加的"。
5. **写库后立即刷新内存白名单。**
6. **前端复用新增那一片的弹窗**（同一份表单状态、标题按是否带 id 切换），**不新造第二个弹窗、不新造样式类**。
7. 编辑成功后**原地刷新当前页**，不重置筛选（与新增的"清筛选回第 1 页"相反——编辑不需要找回刚加的东西）。

**验收**

- [ ] 编辑词面与类型都真实落库；启用状态与 `source` 未被改动
- [ ] 改词后该词在判定用的启用词集合里以新词面出现、旧词面消失
- [ ] 撞另一活跃行 → 「已存在」；撞已删除行 → 文案指向"用新增恢复"
- [ ] 编辑一个已删除的词 → 「术语不存在」
- [ ] 页面：行内「编辑」预填正确、保存后行更新、当前页与筛选保持不变
- [ ] 后端单测覆盖两种冲突文案与 `source` 不变；`mvn test` 通过
- [ ] `npm run build` 通过、`npm run check` 全绿
