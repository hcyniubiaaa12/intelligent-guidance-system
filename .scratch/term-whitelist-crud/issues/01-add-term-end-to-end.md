# 01: 新增术语——端到端

**What to build:**

管理员在知识库管理页的「术语白名单」tab 点「新 增 术 语」，填词面 + 选类型（部位 / 症状）并保存，列表立刻多出一行、来源列显示「人工维护」；这个词**立即**参与 chat 入口判定（敏感词防误杀与信息充足性门槛），不需要重启或等缓存过期。

这一片贯穿全链路：数据访问（物理判存在 + 复活）→ 错误码 → 领域规则（校验、判重、复活、刷新）→ 管理端编排与端点 → 前端 api 与弹窗 → 单测。

**已定的规则：**

1. **新增默认 `source=manual`、`enabled=1`**，**不受 `term.manual.review` 约束**——该开关只管模型抽取的词要不要人工确认；人工亲手加的词已经过一次确认。
2. **校验：`trim` 后 2–20 字；拒绝单字；拒绝内部空白与换行。**
   - **单字的理由必须写进代码注释**：信息充足性门槛用**子串**匹配，塞一个「痛」进去会让几乎所有主诉都被判「含医学术语」，门槛当场失真。现有种子里有「头 / 腹 / 心 / 肺」等单字，那是历史集合，**不构成新增时放行的先例**。
3. **判存在按物理行判（含已逻辑删除）**——唯一键 `(term, type)` 是物理的，逻辑删除的行仍占着它：
   - 活跃行 → 报「术语已存在」；
   - **仅有已删除行 → 复活**（`deleted=0`、`enabled=1`），**`source` 保持原值**（来源是审计标签，不该被一次恢复洗掉）；
   - 并发撞键兜底成可展示错误，不冒 500。
4. **写库后立即刷新内存白名单**，与既有启停一致。
5. **去重口径是 `(term, type)`**：同一个词**允许**同时是「部位」和「症状」各一行，与健康标签词表一致；判定用的是一份扁平 Set，两行同词无影响。
6. **前端沿用科室 tab 的弹窗范式**，字段只有术语 + 类型（不放启用状态开关）；新增成功后**清空关键词与状态筛选、回到第 1 页**再刷新——否则新词可能落在筛选条件外，管理员看不到自己刚加的东西、以为没成功。
7. **错误提示直接用后端文案**，前端不另拼一套判断。
8. **自定义 SQL 要写明为什么不能用 Wrapper**：逻辑删除注解只作用于框架生成的语句。这是仓库仅有的几处自定义 SQL 之一，注释不能省。

**验收**

- [ ] 新词落库为 `source=manual` / `enabled=1`，并立即出现在判定用的启用词集合里
- [ ] 撞活跃行报「已存在」且不写库；仅有已删除行时复活（同一 id 回到正常态）且 `source` 不变
- [ ] 单字 / 纯空白 / 超长输入 → 参数错误，不写库
- [ ] 页面：新增后列表出现该行、来源显示「人工维护」，筛选被清空并回到第 1 页
- [ ] 判定层真实生效：新增一个临时症状词后，一条原本被判「首条主诉过于笼统」的短主诉通过门槛（验完删除）
- [ ] 撞键时页面显示后端文案，不是「操作失败」
- [ ] 后端单测覆盖上述领域规则与编排映射；`mvn test` 通过
- [ ] `npm run build` 通过、`npm run check` 全绿
