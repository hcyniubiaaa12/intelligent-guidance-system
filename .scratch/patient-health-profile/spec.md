# 患者健康档案（spec）

## Problem Statement

患者每次描述症状时，系统只看到「这一次说了什么」，看不到「这个人是谁」——他有高血压吗？在吃氨氯地平吗？青霉素过敏吗？

由此产生三个具体的问题：

1. **反复追问已经说过的事实。** 分诊追问里最常问的就是"有没有高血压、糖尿病？平时吃什么药？"——患者刚填过还要被再问一遍。
2. **既往史无法参与判断。** 项目知识库里本来就写着"中老年，或有高血压、糖尿病、高血脂、吸烟史者风险更高"这类风险因素，但系统不知道患者有没有这些情况，这条知识等于白写。
3. **推荐结论没有"结合个人情况"的依据。** 患者拿到的置信度与说明，与自己是谁无关。

患者要么被问得不耐烦，要么拿到一个没有考虑自身背景的推荐。

---

## Solution

让患者可以**选填**一份健康档案：性别、年龄段、过敏史、既往病史、长期用药。

档案在三个地方起作用：

1. **多开一条检索召回通道** —— 把主诉召不到、但与既往史相关的知识片段捞回来；
2. **作为背景进入模型上下文** —— 影响置信度与结论说明（"结合您的糖尿病史…"）；
3. **免除重复追问** —— 不再问"有没有高血压"这类患者已经填过的问题。

同时，档案**永远没有决定推荐哪个科室的权力**：它不参与精排排序，也不能出现在推荐卡的「判断依据」里。推荐卡另起一行，明确标注「已参考您的健康档案：糖尿病史、青霉素过敏」——让患者看得见、也分得清「哪条是医学证据、哪条是我自己填的」。

## User Stories

### 填写与修改（患者端）

1. 作为患者，我希望用下拉框选择性别，以便系统考虑与性别相关的科室差异。
2. 作为患者，我希望用下拉框选择年龄段，以便系统考虑与年龄相关的科室差异（儿童 / 老年）。
3. 作为患者，我希望多选自己的既往病史（高血压、糖尿病、冠心病…），以便系统知道我的基础疾病。
4. 作为患者，我希望在既往病史里还能补一段自由文本，以便词表里没有的病史不至于无处可写。
5. 作为患者，我希望多选自己的长期用药，以便系统知道我可能在服用的药物。
6. 作为患者，我希望过敏史既能选类别（青霉素类 / 头孢类 / 海鲜…）又能填具体药名，以便准确表达。
7. 作为患者，我希望能看到每个自由文本输入框还剩多少字，以便知道还能写多少。
8. 作为患者，我希望超出额度时当场就写不进去，而不是保存之后被系统默默裁掉——我不想不知道少了什么。
9. 作为患者，我希望档案完全选填——一个字都不填也能正常分诊，不要拦住我。
10. 作为患者，我希望能随时修改我的档案，因为我的健康状况会变。
11. 作为患者，我希望修改档案**不会改变**我过去那些就诊记录里已经写下的内容。

### 分诊过程中（患者端）

12. 作为患者，我希望在推荐卡上看到「已参考您的健康档案：糖尿病史、青霉素过敏」，以便知道系统确实用了我填的信息。
13. 作为患者，我希望推荐理由里能说明「结合您的糖尿病史…」，以便我理解它为什么这么建议。
14. 作为患者，我希望推荐卡的「判断依据」只列医学知识来源，不要把我自己填的东西混进去冒充证据。
15. 作为患者，我希望我填过的既往史 / 过敏史 / 用药信息不再被重复追问。
16. 作为患者，我希望系统**仍然**会追问这次不舒服的具体情况（哪个部位、什么性质、多久了、有没有加重），不要因为我填了档案就跳过这一步。
17. 作为患者，我希望"其他"里写的口语（比如"血糖有点高"）也能被系统看到，即使它不是我勾选的标准病名。
18. 作为患者，我希望不填档案时的体验和以前完全一样，不要有任何退化。
19. 作为患者，我希望导诊记录回放时看到的是"我当时填的那份档案"，而不是我后来改过的那份。

### 可观测与可审计（管理员）

20. 作为管理员，我希望能在投诉/复查时看到某条导诊记录"当时用的档案快照"，以便还原系统当时看到了什么。
21. 作为管理员，我希望档案超长时系统告警，而不是静默截断。
22. 作为管理员，我希望能调整标签条数上限与自由文本字数上限，而不需要改代码、不需要重启。
23. 作为管理员，我希望能维护慢病标签词表（启用 / 停用），以便档案选项随业务调整。
24. 作为管理员，我希望既有的准确率 / 盲区榜口径**不受档案影响**（档案不参与准确率统计）。

### 系统与工程（开发者）

25. 作为系统，我希望没有档案时检索退化为与今天**完全一致**的两路召回，以保证回归安全。
26. 作为系统，我希望档案召回串为空时不产生额外的 embedding 调用。
27. 作为系统，我希望 `rag` 层不感知业务状态（会话、用户），档案由上层组装好再传进去。
28. 作为系统，我希望提示词配置里漏了档案占位符时**启动直接失败**，而不是静默降质。
29. 作为系统，我希望「首条主诉过于笼统」（如"我不舒服"）这类输入仍然被规则硬门槛拦在调模型之前——**档案不能让它直接出结论**。
30. 作为系统，我希望一条结论如果完全建立在档案之上，这件事是**可被发现的**（而不是悄悄发生）。
31. 作为开发者，我希望「档案 → 待注入文本」这段决策密集的逻辑是**纯函数**，可以零依赖地测。

## Implementation Decisions

### 数据模型

- 新增**用户级**表 `user_health_profile`，`user_id` 唯一（一人一份）。
- 字段：性别（枚举）、年龄段（枚举）、既往病史（标签数组 + 自由文本）、长期用药（标签数组 + 自由文本）、过敏史（标签数组 + 自由文本）、更新时间。
- **不往既有 `user` 表加列。** 理由：档案是一人一份、可空、字段还会长；挂上去会把用户表变成档案表。
- 年龄段是**枚举区间**（0-3 / 4-6 / 7-14 / 15-44 / 45-59 / ≥60），不是具体岁数——具体岁数做检索锚点没有意义，"儿童 / 老年"才有。

### 模块归属与依赖

- 档案归 **`auth`**（用户域属主）：`auth` 已是用户级数据（用户、违规留痕）与全局参数（`sys_config`）的属主。
- **零新增依赖边**：`chat → auth` 是**既有边**（chat 读 `sys_config` 就是走它），档案复用这条边。
- **不得让 `rag` 去查档案**：`rag` 不感知业务状态（会话、用户）。档案由 `chat` 读出来、组装成两段文本，经 `RagRequest` 传进去。
- **不新开模块**：为一张表开一个模块，成本大于收益。

### 接口契约

- 患者端读写档案走 REST（读 + 覆盖写），**仅登录用户可访问，且只能读写自己那一份**；未登录按既有约定返回 401。
- `RagRequest` **新增两个字符串字段**：
  - `profileText` —— 进 prompt 的档案背景；
  - `profileQuery` —— 进检索的档案召回串。
  - 两者都可为空。为空即"无档案"，链路行为与今天一致。
- `RagService.retrieve()`：`profileQuery` 非空 ⇒ 多一次 embedding + 两路召回 ⇒ RRF 输入 **4 个排名列表**；为空 ⇒ **2 个**（与今天一致）。
  - 已确认 `RrfFuser.fuse` 的签名本来就是「一个排名列表的列表」，多两路就是多两个元素，**不是新机制**。
- `PromptBuilder`：新增 `profileBlock()`，渲染出 `【患者健康档案】` 段。
- `prompts.yml` 的 diagnosis 主模板**新增第五个占位符 `{profile}`**（既有四个：知识片段、候选科室、结论分隔符、附加约束）。`PromptProperties.validate()` 的必填集合同步加入 `{profile}` —— 这个校验存在的全部意义就是"配错后启动失败"，漏改等于静默降质。

### 档案 → 两段文本的组装规则（决策密集，纯函数）

- **标签优先**：标签词直接进两段文本。
- **自由文本**：命中慢病 / 过敏词表 ⇒ 进两段文本；**未命中 ⇒ 只进 `profileText`，不进 `profileQuery`**。理由：口语（"血糖有点高"）在知识库里命不中任何东西，塞进召回串只会稀释向量；但生成模型读得懂人话，丢掉可惜。
- `profileQuery` = 性别 + 年龄段 + 命中词表的标签与词；全空则为空串。
- `profileText` 按「性别 / 年龄段 / 既往病史 / 长期用药 / 过敏史」顺序拼接；**段内不写任何指令性文字**（指令统一留在主模板，避免两处口径漂移）。

### 预算（把 350 从"患者预算"降级为"文本天花板"）

- **标签类 → 限条数**（既往病史 / 长期用药 / 过敏史各设上限）；**自由文本 → 限字数**（每框上限 + 三框合计上限）。两类上限均走 `sys_config`，管理端可调、改完立即生效。
- **`profileText` 拼完 ≤350 字**：这是硬天花板，不是患者额度——正常情况一百多字就见顶。**超出不是患者的问题，是配置或词表出了问题 ⇒ 记 WARN 告警，不静默裁剪。**
- **超限行为**：前端硬限（到额度写不进 + 显示剩余字数）+ **后端二次校验拒绝**（项目惯例：前端控件只是提示，不构成约束）。
- 与链路 B 对"丢字"零容忍的态度一致：**超限要在源头被发现，不是事后悄悄裁掉。**

### "不决定性"的三层落地（本方案的核心）

| 层 | 机制 | 性质 |
|---|---|---|
| 检索 | **精排的 query 仍是主诉串**（不变）⇒ 档案没有排序话语权 | 结构保证 |
| 输出 | 注号只能指向证据快照里的切片 ⇒ **档案结构上无处可进** | 结构保证 |
| 生成 | 主模板写明硬约束：档案是背景不是证据 / 结论须由片段支撑 / 当前症状信息一律仍须追问；**第 4 条（2026-10-03 端到端实测补）：相关时必须把档案说出来**（前三条只强调"不是证据"，模型于是只字不提，患者看不到反馈）；**不得因档案改变推荐科室** | 软约束 |

- 为什么必须让档案走"扩容"而不是"偏置"：**偏置一旦发生，没有任何机制能发现它**——精排分数是模型给的，你无法区分"这篇片排第一是因为主诉相关还是因为档案相关"，两者写在同一个分数里。而扩容不会：档案捞回的片**必须靠主诉相关性**才能挤进前 N，一篇"与主诉无关、只是沾了档案"的片进不来。
- 前两层**不需要任何新增校验**——"不决定性"没有变成一堆 if，而是变成了两个"没做"（没给排序权、没给注号位）。

### 追问豁免的边界

- 档案**可以**免除对"既往史 / 过敏史 / 长期用药"的追问（这三类它自己答过了）。
- 档案**不得**替代对**当前症状**（部位 / 性质 / 时长 / 诱因 / 伴随）的追问；档案里没有的当前症状信息一律仍须追问。
- 形态：写进主模板的硬约束（现有链路里"该不该追问"本来就是模型判的，不是规则判的，保持一致）。
- **白送的安全阀**：规则硬门槛（无效输入 / 首条主诉过于笼统）跑在**调模型之前** ⇒ 档案到不了模型眼前 ⇒ 档案不可能让"我不舒服"直接出结论。

### 输出与快照

- **推荐卡**新增一行「已参考您的健康档案：…」。数据来自**后端读到的档案**，不是模型输出 ⇒ **解析层不需要改动**。文案上明确标为「健康档案」，与「判断依据（知识片段）」分开呈现。
- **证据快照新增 `profile` 节点**，与既有 `retrieved` / `retrieved_query` / `prompt_snippet` **同构**（同一个 JSON，不新增存储）。存"当时用的档案文本 + 结构化档案内容"。
- 为什么必须快照（两条既有铁律推出来的，不是可选项）：
  - "回流只前向修正，**永不回改历史导诊记录**"——档案可变，若记录只存用户 id、回放时实时读档案，患者今天删掉"糖尿病"，历史记录的推荐理由就当场失真，等于变相回改历史；
  - 证据快照的用途是"还原系统当时看到了什么"——档案参与了召回与生成，就是"当时看到的输入"的一部分，不进快照 = 不可复现。

### 降级

- 无档案 ⇒ 不拼 `profileText`、不产生 `profileQuery` ⇒ **与今天完全一致**（不额外调 embedding、不走档案召回）。
- 部分字段为空 ⇒ 只写实填的。
- 这条是**回归保证**：档案是可选增强，不是链路上的必经环节。

## Testing Decisions

**什么算好测试**：只断言**外部行为**（输入 → 输出 / 发出的调用），不断言实现细节（私有方法、内部调用顺序）。纯逻辑给纯断言、零 mock；需要外部依赖的地方用 mock，断言"发了什么请求"。

### 缝一（新增，主缝）：档案 → 两段文本的组装，纯函数

- **位置**：highest point —— 一个不依赖 Spring、不依赖数据库、不依赖任何客户端的纯函数：`结构化档案 → (profileText, profileQuery)`。
- **为什么它是主缝**：本方案决策密度最高的部分（标签优先 / 自由文本词表匹配 / 命中与丢弃 / 两段文本的分流 / 两段长度上限）全部落在这里，而且**零依赖**，是能跑得最快、最稳的测试。
- **断言点**：
  - 全空档案 ⇒ 两段均为空串（**降级保证**：上层据此退回 2 路、不拼 prompt 段）
  - 标签全进两段文本
  - 自由文本命中词表 ⇒ 进两段；未命中 ⇒ **只进 profileText、不进 profileQuery**
  - 条数 / 字数超限 ⇒ 行为明确（拒绝 or 明确裁剪），不静默
  - `profileText` 超 350 字天花板 ⇒ 产出告警信号
- **先例**：`SufficiencyRuleTest`、`AnswerParserTest`、`RrfFuserTest` —— 同属"纯逻辑单元测试"一类，风格照抄（JUnit 5 + AssertJ，构造输入 → 断言输出）。

### 缝二（扩展既有最高点）：检索装配

- **位置**：`RagService.retrieve()` —— `rag` 模块对外的最高入口，输入 `RagRequest`、输出检索上下文。Mock 掉 embedding / 向量库 / ES / 精排客户端。
- **断言点**：
  - `profileQuery` 为空 ⇒ RRF 收到 **2 个列表**（回归保证：与今天一致）
  - `profileQuery` 非空 ⇒ RRF 收到 **4 个列表**
  - `profileQuery` 为空 ⇒ **不产生额外的 embedding 调用**（成本保证）
  - `RagRequest` 的既有字段行为不变（检索参数、多轮改写路径不受影响）
- **先例**：`ChatServiceTest` 的 Mockito 风格（mock 依赖 → 断言行为）+ `RrfFuserTest` 的断言风格。
- **注意**：`rag` 侧目前**没有** `RagService` 的测试（只有 support 类的单测）。**这是本方案唯一一个新缝**，需要新建测试类——这是刻意的：需要新缝时，提在能提的最高点，且只提这一个。

### 不测的（并说明为什么）

- **`PromptProperties` 的 `{profile}` 必填校验**：由**启动即失败**覆盖——应用起不来是最强的测试，再写一个单测是重复。
- **`RrfFuser` 的多列表融合**：**既有测试已覆盖**（它本来就接受 N 个列表）。本次只是多传两个列表，不产生新行为。
- **解析层**：不改动（"已参考健康档案"信息来自后端，不是模型输出）。
- **端到端效果**：档案对检索质量的影响需要真实语料 + 真实 embedding，属离线评估，见 Further Notes。

## Out of Scope

- **档案语料的建设**（"以既往史为锚点的鉴别片"）。业务侧后续补；本次**不改知识库内容**。
- **"结论必须至少 1 条引用来自主诉路召回片段"的后置校验。** 选了"档案完全不许改变科室"之后不再需要——档案本来就没有排序话语权。⚠️ 但这个豁免是**有条件的**：一旦将来把精排 query 改成带档案，这条校验**必须补上**，否则"不决定性"在检索层失守。
- **双跑对照的离线评估**（度量"因档案而改变科室"的比例）。属后续的可靠性论证，本次不做。
- **管理端的档案配置界面**。本次只做 `sys_config` 键（条数 / 字数上限）与标签词表的后端维护与读取；管理端页面视需要另排。
- **档案与旁路机制的交互**（资料回答 / 敏感词 / 禁言 / 埋点口径）。档案不参与这些路径。
- **导出 / 打印档案、代填（给别人建档）、一人多份档案**。
- **档案的移动端适配打磨**。沿用患者端既有方案，不新开视觉方案。

## Further Notes

### 1. 检索线当前测不出效果（最重要的一条，别误报成果）

当前种子语料是 **7 科室 / 14 片切片**，主诉双路各召回首 K（`sys_config` 初始 10）合并去重后**基本覆盖全库** ⇒ 档案路召回的片段**全是主诉路已有的** ⇒ **当前扩容收益 ≈ 0**。

所以：**不要声称"档案提升了检索准确率"**，现在没有数据支撑。准确的说法是"**通道已就位，收益随知识库规模释放**"。这条线的价值是一条与库规模成正比的优化，**不是一条能立刻演示差异的功能**。

### 2. "以既往史为锚点的语料"是另一门手艺

它与"以症状为锚点的鉴别片"是两种语料：后者主诉路天然召得到（档案路是冗余），前者主诉路天然召不到——**那才是档案路的用武之地**。补语料之前先想清楚要哪一类。

### 3. 需同步的文档（项目硬规则）

CLAUDE.md 要求：新领域概念**先补进领域词汇表再写代码**。本次至少需要新增三个词条：**健康档案**、**档案召回串**、**档案快照**。另外涉及链路对齐点的改动要同步进《总体架构与链路设计.md》。

### 4. 慢病标签词表

建议 **20–30 个常见慢病**起步（高血压、2 型糖尿病、冠心病、脑卒中、慢阻肺、哮喘、慢性胃炎、类风湿关节炎…），照既有医学术语白名单表的模式（可扩展、可停用）。**词表是召回串的原料**：词表空 ⇒ 召回串恒为空 ⇒ 档案路不生效。

### 5. 依赖边（再强调一次）

档案归 `auth`，`chat → auth` 是既有边，**零新增依赖**。不要为一张表新开模块，也不要让 `rag` 去查档案——那会破坏"RAG 层不感知业务状态"这条基线原则。

### 2026-10-03 · 端到端实测补：生成层硬约束 4（档案必须说出来）

**背景**：实现完成后做端到端实测（真后端 + 真 MySQL/pgvector/ES，A/B 空档案对照；脚本 `测试文档/健康档案端到端测试.py`）。**结构保证全部通过**（档案行只对有档案的会话出现、空档案回归、有档案 `RRF 4 个排名列表` / 空档案 2 个、精排 query 不含档案、`cites` 不含档案词、两组**落点科室相同**）；**未发现解析 bug**（`evidence.model_output_raw` 与解析出的 verdict/dept/confidence/top3/note/cites 逐字一致）。

**发现缺口**：本 spec 的 Solution 与 User Story 12/13 本就要求"结论说明体现档案"，但实现落地时主模板只写了三条硬约束——**三条全部在说"档案不是证据、不进注号、不替代追问"，从未要求模型把档案用起来**。实测后果：档案确实进了 prompt、也影响了置信度与 Top3 构成，但模型的回复与 `note` **只字不提**档案，患者看不到任何反馈 ⇒ 对患者是**隐形功能**。

**处置**：主模板新增**硬约束 4**——正向指令（相关时必须讲清档案如何影响判断）+ 边界（不得把**本次症状没指向的**科室提上来或换掉；不得给档案编注号、不得写进 `cites`）。修后实测 A 组 `note` 出现"结合骨关节炎病史，退行性腰痛可能性上升"，与空档案组形成可见差异。**这不是新增范围，是补齐本 spec 已要求的行为**（Implementation Decisions 表「生成」一行已就地补注第 4 条）。

**两条实测更正**（防重复踩）：
1. 早前把"推荐老年医学科"归因为"零切片科室 ⇒ 模型靠先验推荐"——**不成立**。模型引用的是骨科文档里那片《老年医学科——老年患者可首诊》（人工写进腰痛文档的），而那片讲的是**腰痛**、患者问的是**头晕** ⇒ 真实问题是**误引**。
