# 05: 游客态的对话页——闸在发送，不在按钮

**What to build:**

游客能完整走一遍"导诊前的准备"：选部位、看锁定回执、在输入框里写字。**只有按发送那一刻**才告诉他需要登录。

三处改动：

1. **发送按钮的 `disabled` 条件保持不变**（流式中 / 等待态 / 无内容），**不加入游客判断**。
2. **`send()` 入口拦一道**：游客点击时展示"需要登录"提示，把焦点交给「去登录」，**不跳转**。
3. **输入区左下角那格换成**「登录后我才能给您导诊 · 去登录」。

**已定的规则**

1. **按钮必须可点**。灰按钮会让人的第一反应变成"我是不是哪里没填对"，而真正的原因必须在他**试图发送时**告诉他。
2. **一个刻意保留的不对称**：`partStage` 门禁（等待态）**仍然禁用按钮**，因为那一条的提示已经写在 placeholder 里（"先在上面选好位置，就能开始说了…"），用户能自己读懂；而"没登录"这条没有任何就地线索，必须靠点击触发。
3. **提示是常驻的，不是按需的**。它取代免责语的位置——同位置、同角色，**不新增一行**。医疗产品那条线（免责信息要一直在场）在游客态下以"登录后我才能给您导诊"的形式承担。
4. **点了发送不跳转**。跳转会打断一个刚选完部位、写完一句话的游客——页面突然消失是惩罚性交互。去哪里由他点「去登录」决定。
5. **草稿在游客态要存进 store**（`guestDraft`，见工单 02），挂载时用 `consumeGuestDraft()` 取回。**清除点只有两处**：取走那次、登出那次。**不许写进 `reset()`**。
6. **游客态输入框可写**。"闸在发送"的核心就是让游客走完准备流程；输入框 readonly 等于把闸挪到了输入区，与决定相违。
7. **登录回来后的路径已经核实是通的，不要额外处理**：`partStage` 仍是 `locked`、`parts` 还在、`sessionId` 为空 ⇒ 后端 `isFirstTurn`（`askRound==0 && hasResult!=1`）会把它当新会话首条、采纳声明。**这条不需要代码，但它是"草稿必须保留"的技术前提**。

## Comments

**最容易被改坏的两处，已写进 spec 的 Further Notes**：

1. 别把游客判断写进发送按钮的 `disabled`——那会让"按钮灰着、用户不知道为什么"重现。
2. 别把 `guestDraft` 塞进 `reset()`——后果是"游客点了去登录、回来一看输入框空了"，正是本次要修的缺陷。

### 实现说明（2026-10-23）

**改了三个文件**：`frontend/src/views/patient/Chat.vue`、`frontend/src/styles/patient.css`；store 侧（`stores/chat.js`）**一行未动**——工单 02 的三个动作已经够用。

- **发送闸落在 `send()` 里、紧跟既有那行守卫之后**。`disabled` 那一行（`:disabled="chat.streaming || partStage === 'awaiting' || !draft.trim()"`）**git diff 中完全没出现**（`git diff -U0 | grep disabled=` 无输出，可复核）。顺序上「等待态 / 流式中 / 空内容」三条照旧先拦（`partStage === 'awaiting'` 那条还兜着 Enter 旁路），游客判断在其后：`if (user.isGuest) { nudgeLogin(); return }`——不跳转、不表草稿、不发请求。

- **「提示高亮」的具体做法**：那句提示是**常驻**的（游客态下顶替免责语那一格），点击时**不新造浮层、也不新开一行**，只做两件事——① 给它挂一个临时 class `is-nudged`（`--leaf-soft` 底色 + `--r-xs` 圆角，1.5s 后由 `setTimeout` 复位；底色而非位移/描边，是因为它本来就是一行说明文字，做得像"弹出"反而读成错误弹窗）；② `nextTick` 后 `focus()` 它本身。**为什么高亮的是整句而不是「去登录」三个字**：焦点与高亮必须落在同一个元素上——整句是一个 `<button>`（`ref="loginHintEl"`），「去登录」只是它内部的 `<span>` 着主色 + 下划线；若只高亮内层 span，键盘焦点会落在外层按钮上，两者指的不是同一处。可点范围就是整句（`min-height:44px`），点到「去登录」这三个字当然也算。

- **为什么把免责语换成按钮而不是在同一行再加一句**：§3.5 那格只有一份位置（左小字、右发送），塞第二句会把 `bar` 在 375px 下挤成三行。同理，`.p-composer__hint--guest` 是**扩展** `.p-composer__hint` 的修饰类（同一元素两个类），不是第二个类名实现——符合 §5「同名类不许两处实现」（这里外观差异是状态差异，不是重复实现）。

- **草稿存取**：`goLogin()` 里 `if (user.isGuest) chat.saveGuestDraft({ draft, parts: parts.value.locations, partStage })` —— 只有游客才存；已登录用户根本看不到这句提示，但 `goLogin` 也被手机顶栏/左栏的「去登录」调用，那道 `isGuest` 判据保证不会替已登录用户写草稿。取回在 `onMounted` 里、紧跟 `consumeReplay()` 之后：`consumeGuestDraft()` 拿到就还原 `draft` / `parts` / `partStage` 并 `nextTick(autoGrow)`。两者并列且互不覆盖（`pendingReplay` 由挂号成功写入、`guestDraft` 由游客去登录写入，不会同时有值）；先取回放是因为回放态下输入区整块不渲染，草稿即使同时存在也不会被顶掉。**`reset()` 里没有、也不许有 `guestDraft`**（`grep` 可验，工单 02 的 15 条断言里就钉着这一条）。

- **`parts.sentence` 不存也不还原**：它只在"选完部位的那一次"用来把句子拼进输入框，拼完就已经是 `draft` 的一部分了；门禁只看 `partStage`、请求体只看 `locations`，还原时补 `sentence: ''` 不影响任何行为。

- **`readonly` 没动**：游客在等待态仍然只读（部位门禁对游客一视同仁），锁定后即可自由编辑——「闸在发送」的落点正是这里。

**归人工（本环境无浏览器）**：探针 4（点发送 ⇒ 高亮 + 焦点 + URL 不变）、探针 5（登录往返草稿与回执都在）、探针 6（后端日志新会话首条 + 声明被采纳）、视觉走查（`--leaf-soft` 高亮与 44px 触达）。
