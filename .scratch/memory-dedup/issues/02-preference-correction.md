# 02: 偏好改口生效（第一根 tracer bullet）

**What to build:**

患者改口之后，偏好以新说法为准，而不是两条并存互相打架。

完成后：患者先说「我希望你讲慢一点」，系统记住；过一会儿再说「你讲话不要太慢了」，系统把旧那条**原地改掉**（不是删旧插新），值变成新说法、原话变成新那句。开一个新会话提问题，助手的语速按新说法走，而不是还慢吞吞的。

这一刀切穿提示词 → 解析 → 校验 → 落库分派 → 注入五层，是第一个能给患者演示完整效果的切片。

**Blocked by:** 01

**Status:** resolved

- [x] 偏好校验放宽：取消「值必须逐字出现在原话里」，改为「原话必须整体出现在本轮对话原文里」——偏好允许改写表述，但依据不能是编的
- [x] 稳定背景与档案候选的严格判定（否定句 / 禁止推断 / 当前主诉 / 档案事实兜底）**原样不动**，只有偏好这一条放宽
- [x] 落库层按 action 分派：`new` 走既有插入；`update` 原地更新旧行（id 不变，改值 / 原话 / 置信度 / 观察时间）；`skip` 零写入
- [x] `skip` 不写审计——值没变却刷新观察时间，会让这条无理由地跳到「我记住的」列表最前面
- [x] `update` 的审计记为 `update`（old→new），能看出这是一次改口，而不是两笔互不相干的删除与新增
- [x] 取旧记忆的时机在「患者更正收回」之后，避免把刚被置失效的记忆当成判重候选
- [x] 判重整体异常时降级为 `new` 落库，不丢本批
- [x] 满额合并保留为兜底，并在 `update` 时让原话直接取新原话（修掉「改写后挂上旧原话」的缺陷）
- [x] 患者端界面不变，不新增「已更新」标记
- [x] 测试：校验层（改写放行 / 原话不在对话原文则丢 / 背景改写仍被挡）；编排层（三条路径、`update` 原地改且审计正确、`skip` 零写入零审计、判重异常按 `new`）
- [ ] 真机验证：新账号复现改口链路，换会话提问，助手语速确实改变；「我记住的」只剩一条 —— **未做**，见 Comments

## Comments

- 2026-11-15 立项。这是本需求的第一根 tracer bullet：偏好不向量化，所以这一刀不涉及向量一致性，可以先把分派逻辑跑通。

- 2026-11-15 实现完成。改动落在四个文件 + 一个新类：

  **校验层（`MemoryExtractValidator`）**
  - `validPreferences(drafts, minConfidence, dialogue)` 增加第三个入参「本轮对话原文」。原来那条
    `supportedByQuote`（值逐字出现 或 有稳定标记）换成 `quoteInDialogue`（去空白后原话整体在对话里）。
  - 比的是**去空白后**的串：模型照抄原话时常把行内空格/换行改掉，那不改变「患者确实这么说过」。
    对话原文为空时偏好一律丢弃（没有原文就没有依据）。
  - 否定句判定保留（`negated`）——「不要太慢」不会被记成一条肯定偏好。
  - `validBackgrounds` **一行未改**。

  **解析层（`MemoryExtractor`）**：`extract` 把 `dialogue` 透传给校验器。金标集走 `extract(dialogue)`
  重载，同样传原文，口径与生产一致。

  **分派层（新增 `MemoryDedupPlanner`，纯函数、零依赖）**
  - 入参是「草稿列表」+「**送进提示词的那份清单**」，产出 `updates`（改哪一行 + 用哪条草稿）与 `news`。
  - 四道降级：序号越界/null、目标行非 ACTIVE、目标行与本条草稿**不同类**、同一行本批已被改过 ——
    任一成立即按新增落下（不抛异常、不丢草稿）。
  - `skip` 两边都不进（零写入、零审计）。

  **编排层（`MemoryExtractionService`）**
  - 旧记忆只查**一次**：`rememberedRows(userId)` 在 `retractCorrectedBackgrounds` 之后取，
    同一份 `List<Memory>` 既转成 `ExistingMemory` 送进提示词，又传给 `savePreferences` 解析 target。
    **这是本单唯一容易错的地方**：原来 `savePreferences` 内部另查一次 `activeMemories(userId, PREFERENCE)`，
    那份查询只有偏好、顺序也不同，拿它去解析混排编号的 target 会改错行。
  - `new` → 既有 `insert` + `audit(ADD)`；`update` → `LambdaUpdateWrapper` 显式 `set` 值/键/原话/置信度/
    观察时间/updated_at，`audit(UPDATE, old, new)`；`skip` → 直接 continue。
  - 失败降级分两层：分派本身抛异常 ⇒ 本批全按 NEW；**单条 update 失败 ⇒ 只把这一条改成 NEW**（其余照改）。
  - 满额合并仍是兜底；合并输入里的旧行快照在 update 成功后同步刷新，否则「改口 + 满额」会把新说法合并回旧说法。
  - `bestQuote` 改为**新原话优先**（原先把 existing 排在前面，改口后的值会挂上改口前的原话）。

  **未做（背景侧）**：`saveBackgrounds` 保持原样全插 —— 背景 update 要连带刷 `retrieval_text` 与重算向量，
  属工单 03；提前切过去会写出「新值 + 旧向量」的行。

  **target 序号对齐选自哪条路**：走「① 把送进提示词的清单缓存下来传给 savePreferences」。
  理由：清单只查一次、顺序天然与提示词一致，`target` 直接按 index 取；② 的分组编号要在提示词与
  两处代码里各维护一份分组规则，改一处漏一处就会错行。类型不一致的校验仍然保留（清单是混排的，
  模型完全可能把 [背景] 的序号填到偏好上）。

  **测试**：memory 模块 180 用例全绿（基线 162，新增 18：校验层 4、分派纯逻辑 8、编排层 6）。
  全后端 `mvn -o -B test` BUILD SUCCESS。
  顺带修了 `MemoryExtractorTest` 的三处 fixture —— 它们的 quote 与对话原文并不逐字一致
  （以前只要求「值」出现，所以没暴露）。按新口径那是「模型没照抄原话」，修 fixture 而不是放松判定。

  **真机验证未做**：本机没有起 MySQL / pgvector / Redis / 真实 LLM Key 的全栈环境，
  编造一份「助手语速确实变了」的结果没有意义。判重正确性由上面三条缝（纯函数 / 分派 / 编排）保证，
  模型质量由金标集回归保证（工单 04 跑）。

- 2026-11-16 **真机验证（补做）**。环境：MySQL `127.0.0.1:3306`（本地库 `guide`）、pgvector/Redis/MinIO/ES 在 `192.168.193.131`、真实 DeepSeek。步骤：注册新账号 → 走两轮真实 `POST /api/chat/message` → 等异步抽取落库 → 查 `user_memory` / `user_memory_log`。

  **第一次跑就暴露了单测与金标集都没抓住的失败形态**：患者先说「我希望你讲慢一点」、再说「你讲话不要太慢了，正常语速就行」，
  模型判了 `new`，库里两条偏好并存——正是 spec 要修的症状。根因不在分派逻辑，在提示词：模型是拿**抽出来的 value**
  与旧值比字面（「正常语速」vs「讲慢一点」→ 不同 → new），而不是看**患者这句话在说什么**。原规则 3 只给了
  「「讲慢一点」→「不要太慢」」一个例子，模型没把 value 被改写的情形推广进来。

  **修法**：`prompts.yml` 规则 3 改为明确「判断看患者这句话在说什么，不是 value 字面」，并给出
  「不要太慢了 / 正常语速就行 / 快一点」三个改写例。协议与四条口径的语义未动。

  **修后复验**：
  - 真机同场景：`user_memory` **只有一条偏好，id 不变**，`mvalue` 由「讲慢一点」改为「正常语速」；
    `user_memory_log` 为 `add`（讲慢一点）→ **`update`（讲慢一点 → 正常语速）**。
  - 改口专项（多轮改口 / 单句改口 / 称呼改口）连跑 **2 次都是 3/3**。
  - 全量 82 条抽取：F1 **0.848 / 0.868**、四类空期望 **16/16**（门禁仍过）。
  - 新增判重样本 `D09`（多轮改口，即真机失败形态）与 `D10`（称呼改口）。

  **未验证项（如实记录）**：「换会话提问，助手语速确实改变」是主观语感，没有做断言；它由「偏好全量注入」的既有单测覆盖，
  真机只验到「库里存的是新值、旧值已不在生效偏好里」。
