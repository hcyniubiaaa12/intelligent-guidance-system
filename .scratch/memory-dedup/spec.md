# 记忆判重前置（spec）

Status: ready-for-agent

> 类型：**修 bug + 补功能**。修的是「改口后旧偏好不覆盖」与「同义记忆并存」，补的是「落库前判重」这条缺失的环节。
> 前置：`feat/health-profile-memory` 分支，`171f812` 之后。历史上下文见 `.scratch/health-profile-memory/`。

---

## Problem Statement

**患者说过的话，系统会当成两条互不相干的记忆并存，而且改口之后旧的那条还在生效。**

三处具体的患者可见症状：

1. **改口不生效**。患者先说「我希望你讲慢一点」，再说「你讲话不要太慢了」。当前结果：旧偏好「讲慢一点」仍在库里、仍在注入 prompt，新偏好**根本没落库**——下一个会话助手还是慢吞吞地讲。患者会以为自己说了没用。
2. **同义重复堆积**。患者说过「我有2型糖尿病」，过几天又说「2型糖尿病，控制良好」。当前结果：两条并存。这不只是「看着乱」——稳定背景上限只有 10 条，重复吃掉配额；更糟的是这两条各自带向量，按需召回 top-3 时**可能三条全被一组近义背景占满**，把另一条真实背景挤出注入，患者某个真实情况当场哑掉。
3. **患者无法察觉**。上面两件事都是静默发生的。患者要主动翻「我记住的」、逐条对照，才可能发现系统记住了自相矛盾的东西。

根因不是某一处判断写错了，而是**判重这件事在流程里放错了位置**：

- 落库前只做 `(key, value)` **全等**比对——只挡得住「同一句话被说了两遍」，挡不住任何改写；
- 语义判重（`memory-merge` 提示词）**只在偏好满 5 条时才被叫起来**，抽到第 1 条新偏好、库里已有 3 条时，语义判重**根本没有发生**；
- 患者更正收回那条路径只处理「否认一条事实」（「我没有2型糖尿病」），而偏好改口是「提出相反要求」，不在它的语义范围内。

金标集实测的误差结构也印证了这一点：FP/FN 里绝大多数是**同一事实的表述粒度差异**（期望「哮喘」、模型给「哮喘，换季时容易发作」）。这类差异全等判重一律漏掉。

---

## Solution

**把判重从「事后整理」改成「写入前决策」：每条新抽取的记忆在落库之前，先与已有记忆比对一次，按三种结果之一落地。**

| action | 语义 | 落库动作 | 审计 |
|---|---|---|---|
| `new` | 没说过的 | 插入新行 | `op=add` |
| `update` | 同一条，但新说法更具体或相反 | **原地改旧行**（id 不变） | `op=update`（old→new） |
| `skip` | 旧值已经更好或等价 | 什么都不写 | 不写审计 |

**判据交给模型，且与抽取同一次调用完成**——输入多一段旧记忆清单（按序号编号），输出每条多两个字段 `action` 与 `target`。这样零额外模型调用，且跨 key 的同义偏好（「回答方式：讲慢一点」vs「语速：慢点」）也能被识别，这是字串规则和向量筛选都做不到的。

**字串规则降为兜底，不做裁决**：只有模型没给出 `action`（漏字段、格式串味）时，才用「完整子串或足够长的公共子串」判同，判同走 `skip`、否则走 `new`。它的职责是「解析失败时不把一条真记忆丢掉」，不是代替模型判断。

**失败一律按不重复落库**：判重出任何问题（模型漏字段、target 越界、action 非法值），降级为 `new`。多一条重复，患者看得见、能手动删；少一条，他永远不知道自己被漏记了。

**患者端不新增任何提示**：改口/补充后直接显示当前生效的值，界面不变。合并/更新是系统内部整理，不是患者需要处理的事。

## User Stories

### 改口与更正

1. 作为患者，我说「你讲话不要太慢了」之后，希望系统把「讲慢一点」换掉，而不是两条并存互相打架。
2. 作为患者，我说「不要叫我老王了，叫老陈」之后，希望下次会话助手用新称呼，而不是还喊老王。
3. 作为患者，我改口说「先讲结论再说细节」之后，希望这条偏好立刻对下一次回答生效。
4. 作为患者，我希望改口之后不用手动去「我记住的」里删旧的那条。
5. 作为患者，我改口时如果系统没听准，我仍然能在「我记住的」里改或删，不需要特殊操作。
6. 作为患者，我改口之后，旧说法不应该还出现在「我记住的」列表里让我困惑。

### 重复与补充

7. 作为患者，我先说「我有2型糖尿病」、后说「2型糖尿病，控制良好」，希望系统只留一条更完整的，而不是两条。
8. 作为患者，我重复说一遍已经记过的事，希望系统不要因此产生第二条。
9. 作为患者，我补充细节时（「我青霉素过敏」→「青霉素和头孢都过敏」），希望旧的那条被补充而不是新的另起一条。
10. 作为患者，我想知道系统只保留一条，是因为重复的记忆会占用配额、把我的其它背景挤掉。
11. 作为患者，我说了一句跟已有记忆语义相同但换了词的话（「语速慢点」vs「讲慢一点」），希望系统能认出是同一件事。
12. 作为患者，我说的两件事只是措辞相近、其实不是一回事，希望系统不要误合并成一条。

### 安全与可纠

13. 作为患者，系统判断「这条和之前那条是同一件事」时如果判错了，我能在「我记住的」里看到并改回来。
14. 作为患者，我希望系统在拿不准的时候宁可多记一条，也不要悄悄把我说的某句话丢掉。
15. 作为患者，我希望判重失败时系统照常把我说的话记下来，而不是整批丢弃。
16. 作为患者，我不希望系统为了整理我记忆里的事而让我多等——判重不能拖慢当前这轮回答。
17. 作为患者，我希望系统记住「我为什么会这样记」——每条记忆仍能看到是从我哪句话记来的。

### 边界与范围

18. 作为患者，我希望我的偏好和健康背景之间不会被互相合并——偏好说的是「怎么回答我」，背景说的是「我是谁」，是两回事。
19. 作为患者，我希望已经失效（过期/被删）的旧记忆不要参与判重，否则系统会拿我已经放弃的说法来比。
20. 作为患者，我希望档案（过敏/用药/手术）仍然走「待确认 → 我自己接受才写档案」这条路，不要被这次改动顺带改掉。
21. 作为患者，我希望档案例外——它本来就靠我逐条确认，重复项我当场就能拒绝。

### 运维与回归

22. 作为开发者，我希望判重的判定规则是纯可测的，不依赖模型输出就能钉住每一条边界。
23. 作为开发者，我希望模型不守协议（漏 `action`、`target` 越界、给了不认识的值）时，系统有明确的降级路径，而不是崩或写坏数据。
24. 作为开发者，我希望改完提示词之后能用已有的 82 条金标集回归，确认抽取质量没被弄坏。
25. 作为开发者，我希望这次改动不改表结构——`user_memory` 现有列与 `user_memory_log` 已有的 `update` 操作码够用。
26. 作为开发者，我希望偏好的向量化口径保持不变——偏好永远全量注入，不向量化。
27. 作为开发者，我希望稳定背景更新时 `retrieval_text` 与向量同步刷新，不要让召回继续用旧文本的向量。

## Implementation Decisions

### 提示词协议（`prompts.yml` 的 `memory-extract`）

- **输入多一段已记住的记忆**，按序号编号（模型不认 id）。两类分别列出，标注 `[偏好]` / `[背景]`；没有时写「（无）」。
- **输出每条多两个字段**：`action`（`new` / `update` / `skip`）与 `target`（旧清单序号，仅 `update` 需要）。
- **提示词要写死的四条口径**：
  1. 只有明确是同一件事才 `update`；只是措辞相近、说的不是一回事，按 `new`。
  2. `update` 时 `value` 取信息量更大的那个；旧值已经更具体就 `skip`。
  3. 新说法与旧值相反 → `update`，以新说法为准。
  4. **拿不准就 `new`** —— 多记一条患者能看见能删，漏记一条他永远不知道自己被记错了。

### 解析层

- 抽取入口增加「已有记忆」入参；保留一个只收对话文本的重载，供金标集评估与既有单元测试沿用，语义上等价于「旧清单为空」。
- 两个草稿 record 各增 `action` / `target` 字段。
- **降级规则**（重要，测试要钉）：`action` 缺失、不在三值之内，或 `target` 越界/缺失时，一律按 `new` 处理。模型没说话时按「宁可重复」。
- 顺带修一个既有缺陷：合并提示词目前只把旧偏好的 **值** 送进去，却要求模型输出 key，模型只能自己编。改成送「键：值」。

### 纯函数校验层

- **偏好放宽**：取消「值必须逐字出现在原话里」这一条，改为**原话必须整体出现在本轮对话原文里**。依据性反而更强——偏好允许改写表述，但依据不能是编的。
- 校验函数需要拿到本轮对话原文，入参增加一项。
- **背景、档案候选的严格判定原样不动**（否定句、禁止推断、当前主诉、档案事实兜底全部保留）。

### 落库编排层

- **取旧记忆的时机**：在「患者更正收回」之后取，避免把刚被置失效的记忆当成判重候选。旧记忆只取生效中的，按类型分别取。
- **分派**：`new` 走既有插入路径；`update` 走原地更新（id 不变，改值、原话、置信度、观察时间）；`skip` 零写入、零审计。
- **背景的 `update` 必须多一步**：同步刷新用于 embedding 的扩展文本并重算向量。这与患者手动编辑记忆走同一套口径，不能写第二份实现。偏好不向量化，无此步。
- **失败兜底**：判重整体异常时按 `new` 落库，不丢本批。
- **满额合并保留**作为兜底，主路径改为判重；其「改写后挂上旧原话」的缺陷一并修——`update` 时原话直接取新原话。

### 不动的部分

- 档案候选的判重保持现状（候选要患者逐条确认，重复项当场可见可拒绝，这是天然的人肉去重）。
- 存量重复记忆不清洗。自动清洗需要批量调模型并改写既有数据，误删一条真记忆无法恢复，风险高于收益。
- 表结构不变。`user_memory_log.op` 已有 `update`，`user_memory` 现有列够用。
- 患者端界面不变，不新增「已更新」之类的标记。

## Testing Decisions

**好的测试长什么样**：只测外部行为，不测实现细节。具体到这件事——测「给定模型输出与旧清单，最终库里发生了什么」，而不是「有没有调用某个私有方法」。`MemoryExtractionServiceTest` 现在就是用 `ArgumentCaptor` 抓 `insert` / `updateById` / `deleteById` 的调用与参数，这正是外部行为，沿用这套写法。

**四条缝全部复用，不新开**：

| 缝 | 现有文件 | 这次钉什么 |
|---|---|---|
| 纯函数校验 | `MemoryExtractValidatorTest`（零 mock） | 偏好改写可落库；原话不在对话原文中则丢；背景改写仍被挡。 |
| 解析层 | `MemoryExtractorTest`（mock 模型） | 三种 action 解析；`target` 越界/缺失/`action` 非法 → 降级 `new`；旧清单确实进了 user 消息。 |
| 编排层 | `MemoryExtractionServiceTest`（mock mapper） | `new`/`update`/`skip` 三条路径；`update` 原地改且审计为 `update`；`skip` 零写入零审计；判重异常按 `new` 落库；背景 `update` 触发向量重算、偏好不触发。 |
| 真实模型回归 | `MemoryGoldSetEvalTest`（`MEMORY_EVAL=true`） | 样本可带 `existing` 字段；有值时同时校验 `action`/`target`。**门禁：总体 F1 不低于 0.805、四类空期望仍为 100%。** |

**先写失败用例再实现**（TDD）。这次改动的主体是判定规则与分派，纯函数与 mock 编排都能先行钉住。

**已知的测试局限**：真实模型下「改口」的行为无法稳定复现，所以不写真机 E2E——那种用例只能验证「没崩」，验不出判重对不对，还会因模型输出波动变成 flaky。判重正确性由前三条缝保证，模型质量由金标集回归保证。

## Out of Scope

- **档案候选的语义判重**：候选本身就要求患者逐条确认，重复项当场可见可拒绝；且「青霉素」与「青霉素钠」这类同族药名在专业上未必是同一条，自动合并有医学风险。
- **存量重复记忆的清洗**：只在入库时判重，历史重复不动。
- **偏好向量化**：偏好永远全量注入，不参与按需召回，这是既有口径。
- **判重结果的患者可见提示**：不新增「已按您最新的说法更新」之类的 UI。
- **管理端记忆内容页**：隐私面不扩大，本轮不做。
- **合并失败时的降级展示**：沿用现有「丢弃本批新偏好、保留旧偏好」，不改。

## Further Notes

### 方案的历史取舍（为什么不是别的做法）

- **为什么不用「只要有旧有新就合并」**：那等于每轮抽到偏好就多一次模型调用，且旧偏好的措辞会被反复改写。改成抽取时顺带判重，零额外调用且只动真正相关的那几条。
- **为什么不做向量预筛**：旧记忆总量 ≤15 条（偏好 5 + 背景 10），全量塞进提示词才 300 字符左右；预筛反而要额外算 embedding，还会漏掉跨 key 同义（向量近但字串不沾）——那正是本次要解决的问题。
- **为什么字串规则不裁决**：患者改口说的是「提出相反的新要求」，字面上往往只与旧值共享一两个孤立单字（「讲话不要太慢了」vs「讲慢一点」），规则天然判不到。把它降为兜底，是为了不让规则误判影响模型已经判对的结果。

### 安全性支点

放宽偏好校验 + 判重前置，会让「模型静默丢记忆」的风险从一处变成两处。唯一的防线是患者可见可编辑——这在背景上够用（记错了立刻能发现），在偏好上未必。所以提示词里「拿不准就 `new`」不是客套话，是整个方案的安全性支点，必须有对应的测试用例钉住。
