# 术语抽取：入库时 LLM 批量抽取 → 白名单候选 → 关键词通道加分（spec）

Status: ready-for-agent
Branch: 待定（建议 `feat/term-extraction`）

---

## Problem Statement

**① 白名单没有任何自动来源，新建库从零开始。**

2026-10-17 删掉术语种子后，`medical_term` 只由管理端人工维护。新库启动时是一张空表，而它有**三个消费方**：信息充足性门槛（`SufficiencyRule.tooVague`，短于 6 字且不含术语即追问）、敏感词防误杀（`SensitiveGuard.isTerm`，白名单里的词不被当违规词拦下）、以及管理端策展。空表期间，患者端一条本就能说明问题的主诉（「胸闷」「反酸」）仍会被当成"说不出所以然"，而管理员只能凭经验逐个补词——他不知道知识库里到底有哪些词。

**② 文档里写好的抽取链路一行代码都没有。**

《链路A-导诊对话.md》§6.5 描述的是「LLM 批量实体抽取 → 写 ES → ES terms 聚合 → 白名单」，而实际状态是：

- `llm` 适配层没有抽取客户端；
- 真实上传路径（`DocSplitter`）给每片 chunk 的 terms 是写死的空列表，只有开发种子语料（`SeedCorpus`）手写了词；
- `EsChunkUtil` 没有任何聚合方法；
- `MedicalTermService` 没有"模型抽取词入库"的路径。

于是 ES 的 `medical_terms` 字段对真实文档恒为空，`term.manual.review` 这个管理端可见的开关**没有任何代码读它**——它在页面上写着"开启后术语白名单变更需人工确认"，改它对系统毫无影响。这是一处与管理端「不让页面产生假配置」直接冲突的现状。

**③ 关键词通道完全用不上术语。**

`EsChunkUtil.searchChunks` 只对 `title^2` 与 `content` 做 `multiMatch`。切片里已经带着（种子语料的）术语，但检索完全不看它——用"胸闷"检索时，写着「胸闷伴出汗」的正文能命中，而术语字段里的同义词不会带来任何加权。

---

## Solution

**① 入库时抽取，抽取结果当场落两处。**

切分完成后、写库之前，由 `kb` 侧的抽取器把 chunk 按 **20 片一批** 送进 LLM，要求输出**部位 / 症状术语 + 类型**；结果直接写进这两处：

- **ES 的 `medical_terms`**（随同一次 `indexChunks` 写入，不二次更新）
- **MySQL 的 `medical_term`**（`source=llm_extract`，`enabled` 由人工审核开关决定）

**不做** ES terms 聚合那一步：抽取结果已经当场落库，聚合是从 chunk 反推同一份清单的重复劳动。

**② 抽取是旁路，绝不阻塞入库。**

抽取失败只记 WARN，切片照常入库、文档照常标 `done`。整条流水线本来就在 async 线程池里跑，管理端可以离开页面，回来看到的是「解析中 N% → 正在切分与提取术语 → 写入 x / y → 已完成」。

**③ 管理端能看见、能一键确认。**

术语 tab 增加「来源」筛选与待确认计数，顶部一个「待确认 N · 全部启用」入口（上限 500 条）。

**④ 关键词通道给术语加分。**

`medical_terms` 的 mapping 从 `keyword` 改成 `text`（ik 分词）+ `.keyword` 子字段；检索查询改为「`must: multiMatch(title^2, content)` + `should: match(medical_terms).boost(1.0)`」。其余（向量通道、RRF 融合、精排、Prompt、链路 A 判定）一律不动。

## User Stories

1. 作为患者，我想让「胸闷」这种两三个字但含医学术语的主诉直接进入判断，以便不必先被模板追问一轮"请详细描述"。
2. 作为患者，我想让「不舒服」这类含糊短句照旧被追问，以便系统不会拿一句空话去猜科室。
3. 作为患者，我想让知识库里出现过的症状词自动进入判定，以便我不必用书面语重新组织表达。
4. 作为患者，我想让含医学术语的短消息不被敏感词误拦（如「回滚」里的「滚」），以便正常的医学表达不被阻断。
5. 作为管理员，我想在文档入库后看到系统自动抽出的术语，以便知道知识库里实际有哪些词、而不用自己读完每一份文档。
6. 作为管理员，我想看到每个自动抽出的词来自哪份文档的入库过程，以便判断它是否可信。
7. 作为管理员，我想让自动抽出的词默认**待确认**，以便白名单的最终形态由人决定。
8. 作为管理员，我想能把审核开关关掉、让抽出的词直接生效，以便在信任抽取质量时省掉点击。
9. 作为管理员，我想一键启用当前所有待确认的词，以便不必逐个点几十次。
10. 作为管理员，我想在批量启用前看到"N 条"的准确数量，以便知道这一下会改变多少。
11. 作为管理员，我想按来源筛选术语（人工 / 模型抽取），以便分开审视两类词。
12. 作为管理员，我想让"待确认"的口径不包括我手动停用的词，以便我的决定不会被一次批量操作推翻。
13. 作为管理员，我想在抽取失败时文档仍正常完成，以便一次模型抖动不会让整份文档白解析（DocumentMind 按次计费）。
14. 作为管理员，我想在文档入库页看到「正在切分与提取术语」，以便知道这段等待在做什么。
15. 作为管理员，我想在入库期间离开这个页面，以便不必守着进度条。
16. 作为管理员，我想让抽出的词也遵守"至少 2 个字"的规则，以便单字不会放宽信息充足性门槛。
17. 作为管理员，我想让抽取撞上我手动停用的词时不把它翻回来，以便自动流程不覆盖人的决定。
18. 作为管理员，我想让抽取撞上我删掉的词时不复活它，以便"删除"是真的删除。
19. 作为管理员，我想在知识库页直接决定"抽出的词要不要我确认"，以便不用去另一页找一个不相关的开关。
20. 作为开发者，我想在检索日志里看到术语加分是否生效，以便调整 `boost` 时有依据。
21. 作为开发者，我想让 ES 查询的形状（must/should/mustNot + boost 值）被单测钉住，以便日后调参不会悄悄改变召回范围。
22. 作为开发者，我想让抽取失败的信息留在日志里（文档 id + 批次 + 原因），以便排查"为什么这份文档没有术语"。
23. 作为开发者，我想让抽取的提示词放在 `prompts.yml`，以便调整抽取口径不必改代码、不必重新编译。
24. 作为开发者，我想让单字过滤只有一处实现，以便种子语料与上传文档走同一条口径。
25. 作为答辩演示者，我想上传一份文档就能看到一个可复现的闭环（抽取 → 待确认 → 启用 → 患者端生效），以便说明这条链路真的通了。

## Implementation Decisions

### 模块与依赖

- **提示词**进 `prompts.yml`（`prompts.term-extract.*`），由 `common` 的 `PromptProperties` 承载。这与既有的 `prompts.split.*` **完全同构**：`kb` 模块已经在读 `PromptProperties`（`LlmModelSplitter`），不新增依赖边。
- **抽取器**放在 `kb`（`kb/service/TermExtractor`），不放 `llm`：`llm` 只留"唯一外部出口"的模型客户端，领域提示词与输出协议属于 `kb`。
- 抽取走 `ChatModel.chat()`（一次性返回，非流式），不新增客户端接口。

### 抽取的执行位置

- 在 `DocIngestService.splitAndIndex` 内、**切分完成之后、第一批 `indexChunks` 之前**执行。
- **仍用现有的 async 线程池**（`IngestPipeline` 已有的那个），不新建线程池——只做旁路的第二套并发模型没有收益，且与「async 线程池与在线导诊线程隔离」的既有约束无关。
- **不新增 `ingest_task.stage` 枚举值**。抽取耗时会计入 `split` 阶段；管理端该阶段的文案改为「**正在切分与提取术语**」。把旁路抬进状态机会立刻产生"抽取失败要不要改阶段"这种无解问题。
- `ingest_task` **不新增字段**。

### 抽取的批量与失败语义

- **20 片一批**，与 `INDEX_BATCH_SIZE` 对齐。
- **单批失败不中断整份文档**，记 WARN 后继续下一批。
- **连续失败 3 批即熔断**，中止本文档剩余批次，记一条 WARN（写明已失败批次数与原因）。3 是经验阈值，必须写进代码注释说明来由（"连续三次同一路径失败几乎可断定不是网络抖动，继续只会白烧调用"）。
- **抽取异常绝不上抛**：`DocIngestService` 的返回值、`ingest_task` 状态、`kb_doc.status` 都不受影响。
- 抽取结果按 `(term, type)` 在内存中**跨批去重**后，整份文档只写一次 MySQL。

### 抽取输出协议

- LLM 输出 JSON 数组，每项 `{ "term": "...", "type": "part" | "symptom" }`。
- **类型非法时降级为 `symptom`，不丢弃该词**——类型错了人可以在管理端改，丢了真实的词更亏。
- **所有抽取词复用 `MedicalTermService` 的词面校验**（`trim` 后 2–20 字、拒绝内部空白与换行、**拒绝单字**）。单字必须挡在入口：`SufficiencyRule` 用子串匹配，一个「头」进来会让几乎全部主诉都被判"含医学术语"。
- 抽取到的词**仅在文档里出现过至少一次**才写入；不做同义词扩展。

### 白名单写入语义（与人工新增刻意不同）

新增 `MedicalTermService.mergeExtracted(Collection<ExtractedTerm>)`，语义是"合并候选"，**不复用 `add`**——`add` 的复活语义是人工路径的契约，抽取不能借用：

| 表内状态 | 抽取撞上时的处理 |
|---|---|
| 活跃行（`deleted=0`） | **跳过，不动 `enabled`**（人手动停用过的词不能因为又被抽到就复活） |
| 已删除行（`deleted=1`） | **跳过，不复活**（"删除"是人的决定） |
| 不存在 | 插入，`source=llm_extract`，`enabled` 由 `term.manual.review` 决定 |

判存在必须按**物理行**判（`countIncludingDeleted` 同款自定义 SQL），理由同《数据库设计.md》§0.1。`mergeExtracted` 写库后**立即 `refresh()`**。

### ES 写入侧

- `ChunkIndexService` 组装 `ChunkDoc` 时**统一过滤单字术语**（种子语料与上传文档同一条路，只此一处实现）。
  理由：`medical_terms` 一旦参与打分，单字会命中半库切片；与 `validateTerm` 的 2 字下限同源。
- **不改 `SeedCorpus`**：语料里的词是给 ES 用的，过滤是写入侧的职责。

### ES 检索侧

- `medical_terms` 的 mapping：`keyword` → `text`（`ik_max_word` / `ik_smart`）+ `.keyword` 子字段（供精确匹配与将来聚合）。**ES 不允许原地改字段类型**，需删除并重建索引后重灌文档。
- 查询形状（`EsChunkUtil.searchChunks` 内抽出**包内可见的纯函数**构造 bool query，便于单测）：

```
bool:
  must:    multi_match(query, fields: ["title^2", "content"])
  should:  match(medical_terms, query), boost = 1.0
  mustNot: chunk_type = "title"      // 既有 ChunkRetrievalFilter，不动
```

- **为什么是 `should` 而不是把 `medical_terms` 加进 `multiMatch`**：`best_fields` 是"取最高分字段"，术语多的切片会把标题信号顶掉；`should` 才是加法，且不改变原有召回集。
- **`boost` 初值 1.0**：`medical_terms` 是短字段，BM25 的长度归一化会让它的命中分天然偏高；取 1.0 起、靠真实数据验，不预设 2.0。该值以常量形式写死并注明来历，本轮**不进 `sys_config`**（为一个尚未验证的数新增受管参数，要连带白名单、页面、文档四处）。

### 管理端

- `GET /api/admin/kb/terms` 增加 `source` 查询参数（`llm_extract` / `manual`），与既有 `keyword`、`enabled` 组合筛选。
- 新增批量启用端点：`POST /api/admin/kb/terms/batch-enable`，body `{ "ids": [] }`，**上限 500**；**只对 `llm_extract && enabled=0` 生效**，返回实际启用条数。不做"全部启用"语义（不可撤销的大动作），不做 `action` 参数（多余弹性）。
- 术语 tab 顶部加「**待确认 N · 全部启用**」：N = `source=llm_extract & enabled=0` 的 total；点击先 confirm（写明条数与后果），成功后清空筛选、刷新列表。
- 「待确认」口径**不含人工停用的词**——这正是把 `source` 作为独立筛选参数、而不是只用 `enabled=false` 的原因。
- 人工审核开关 `term.manual.review` **从 LLM 配置页移到知识库页术语 tab**（与敏感词页「处置规则与词库同页」同一判据）。`ParamGroup` 相应调整，`docs/architecture/管理端控制台.md` §7.1 的"17 项"计数与归类同步。

### 文案

- 管理端入库进度，`split` 阶段文案：`正在切分` → `正在切分与提取术语`。
- 阶段仍无百分比（切出多少片是切分的结果，抽取也不是可线性推进的量）。

## Testing Decisions

**好的测试**：只测外部行为——"给定这些输入，系统产出了什么"，不断言内部调用顺序、不 mock 到看不见的地方。既有测试全部是这种风格（service + mock 的 mapper/客户端，纯函数直接断言）。

### 复用既有测试缝（不新增）

| 缝 | 既有测试类 | 钉住什么 |
|---|---|---|
| `DocIngestService.splitAndIndex` | `DocIngestServiceTest` | 抽取在切分后执行；`indexChunks` 收到的切片带上了 terms；**抽取抛异常时仍正常返回、切片照常入库** |
| `IngestPipeline` | `IngestPipelineTest` | 抽取失败时任务仍是 `success`、文档仍是 `done` |
| `MedicalTermService.mergeExtracted` | `MedicalTermServiceTest` | 新词插入且 `enabled` 受开关；活跃词跳过且 `enabled` 不变；**已删除词跳过、不复活** |
| `KbAdminService` | `KbAdminServiceTest` | `source` 与 `enabled` 组合筛选；批量只动 `llm_extract && enabled=0`；返回实际条数 |
| `TermExtractor`（新增类） | 新增测试类 | 提示词渲染；JSON 解析；**非法 type 降级为 `symptom`**；单字/超长被丢弃；**单批失败返回空、不抛** |
| ES 查询构造纯函数 | 新增测试类 | `must` 里没有 `medical_terms`、`should` 里有、`boost == 1.0`、`mustNot` 仍排除标题片 |

**ES 的真实效果不做单测**：单测只能证明"查询长这样"，证明不了"排序变好"。加分效果用真实环境验证（见验收），结果写进施工日志。不引入 Testcontainers/内嵌 ES（新依赖、新中间件，违反约束）。

## 验收（真实环境）

1. 上传一份**新**文档，进度文案出现「正在切分与提取术语」，期间可切到其他页面再回来。
2. 日志出现抽取结果（批次数、抽取词数、落库条数）。
3. 管理端术语 tab：出现 `来源=模型抽取`、`未生效` 的词；「待确认 N」计数与列表一致。
4. 点「全部启用」→ 列表状态变为已生效 → **患者端发一条 2–5 字、含该术语的主诉，不再触发模板追问**；发「不舒服」**仍然追问**。
5. 抽取失败可复现：临时把模型 Key 改错，上传一份文档 → 文档仍 `done`、切片照常可检索、日志只有 WARN。
6. 检索加分：同一条查询在加 / 不加 `should` 两种配置下对比 Top-3，差异记入施工日志（**不承诺准确率提升**，只记录可观察的排序变化）。
7. 旧索引重建后，`medical_terms` 参与检索不报错、标题片仍被排除。

## Out of Scope

- **不回填存量文档**：已入库的 18 份文档不重新解析（DocumentMind 按次计费）、不重跑抽取。候选池只从新入库的文档开始长。
- **不做 ES terms 聚合**：文档 §6.5 的第 ③ 步整个砍掉。
- **不给种子语料补写白名单**：`SeedCorpus` 里手写的 terms 保留（写 ES，供关键词通道加分），但**不灌进 `medical_term`**——白名单仍然没有「自动的种子」，空表依旧是合法状态，管理员自行补词。
- **不新增 `ingest_task` 阶段或字段**，抽取失败不在页面上可见（只留日志）。若日后要做"本次未抽取术语"的提示，属于增量。
- **不调整向量通道、RRF 融合、精排、Prompt、链路 A 的判定逻辑**。
- **不把 `boost` 参数化**进 `sys_config`。
- **不做抽取质量的自动评估**（无准确率指标），也不做"按文档删除术语"。
- **不解决**已被登记的既有缺口：`CHUNK` 分组 3 个切分参数目前没有管理端端点（文档称"知识库管理页"，实际无入口）。本轮只把审核开关挪进来时顺带核对，不凭空补一整套切分参数页。

## Further Notes

- **中途澄清的两处口径**（写在这里避免后来者按字面复现错）：
  - 信息充足性门槛是「长度 < 6 **且** 不含术语」两条同时成立才追问。术语白名单的作用是"让含术语的短主诉不被追问"，**不是**"让短主诉都不被追问"。「不舒服」照旧追问。
  - 「抽取失败不影响文档状态」不等于「抽取必须在 `done` 之后跑」——它说的是失败不上抛，抽取仍在流水线内、`done` 之前。
- **种子语料与白名单的关系**：种子 terms 让 ES 在首次部署时就有可加分的词；白名单为空则入口判定仍只认人工词。两者不同源，这是刻意的取舍（见 Out of Scope）。
- **`term.manual.review` 的默认值仍是 `true`**（待确认）。批量启用入口是这个默认值可用的前提——没有它，"要人审"等于"词永远不生效"。
