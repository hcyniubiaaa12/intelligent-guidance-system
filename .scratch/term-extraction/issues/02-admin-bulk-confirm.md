# 02: 管理端一键确认——候选词变成生效白名单

**What to build:**

管理员在知识库管理页的「术语白名单」tab 里能看到「**待确认 N · 全部启用**」，一眼分清哪些是模型抽的、哪些是人加的、哪些是人手动停用的；点一下就把待确认的全部启用，**患者端的入口判定立刻用上这些词**。审核开关（`term.manual.review`）也从 LLM 配置页搬到同一页——"哪些词被抽出来"和"要不要我确认"是一件事的两半。

**已定的规则：**

1. **「待确认」的严格口径是 `source=llm_extract AND enabled=0`**，不能只用 `enabled=false`——后者会把管理员**故意停用**的词算进去，那个数字会骗人，而且一次"全部启用"会推翻人的决定。
2. **列表接口增加 `source` 查询参数**（`llm_extract` / `manual`），与既有 `keyword`、`enabled` 组合。不做单独的计数端点（复用同一套分页与筛选口径）。
3. **批量启用端点**：`POST /api/admin/kb/terms/batch-enable`，body `{ ids: [] }`
   - **上限 500 条**，超出拒绝（防一次误点全库）
   - **只对 `llm_extract && enabled=0` 生效**，其余 id 静默跳过
   - **返回实际启用条数**（不是请求条数）——前端拿它做 toast
   - 不做"全部启用"语义（不可撤销的大动作），不做 `action` 参数（多余弹性）
   - 写库后 `refresh()` 一次，不是逐条
4. **状态列区分两种"未生效"**：模型抽取未确认 → 「待确认」；人工维护且 `enabled=0` → 「已停用」。同一列混着写，管理员会以为人工停用的词也能被一键启用。
5. **confirm 文案写明条数与后果**（"将启用 N 条模型抽取的术语，它们会立即参与入口判定"）——启用不是破坏性操作，但候选池大时会显著改变患者端行为。
6. **启用成功后清空筛选、回到第 1 页再刷新**——否则启用后的词可能落在筛选外，管理员看不到、以为没生效。
7. **审核开关归位**：`term.manual.review` 从 LLM 配置页移到知识库页术语 tab（与敏感词页「处置规则与词库同页」同一判据）。后端参数分组相应调整，LLM 配置页由 9 项减为 8 项。

**Blocked by:** 01（没有抽取产物，「待确认 N」永远是 0，本票无法验收）

**Status:** resolved

## Comments

**实现**（后端 11 文件 + 前端 2 文件，一个提交 `2d99f7b`）：

- `KbAdminController`：`GET /terms` 加 `source`；新增 `POST /terms/batch-enable`；新增 `GET/PUT /params`（`ParamGroup.KB`）供知识库页读改写参数。
- `MedicalTermService.page` 加 `source` 过滤；新增 `batchEnable(ids)`：单条 UPDATE 带 `source=llm_extract AND enabled=0` 两个条件、`refresh()` 只调一次、返回实际启用条数。**查询侧同时带两个条件**而不是查出 ids 再逐条 toggle——后者在"判存在与写库之间被停用"的竞态下会把人的决定覆盖掉。
- `ParamGroup.CHUNK` → **`KB`**：这一组现在同时装切分三档与术语开关，叫 CHUNK 名不副实（下一个维护者一定会建第二个分组）。`checkChunkLengths` 的"本次是否触及"判据已按 `KB` 更新。
- 前端术语 tab：审核开关面板（与敏感词页「处置规则与词库同页」同一判据）、来源筛选、`待确认 N · 全部启用` 横条、状态列三态（已生效 / 待确认 / 已停用）。

**三处与原计划不同**：

1. **待确认计数不用当前列表的 total**，而是固定按 `source=llm_extract + enabled=false` 另查一次（size=1，只要 total）。否则管理员切个筛选、数字就跟着变——它答的是"这个库积压了多少待确认"，与当前筛选无关。
2. **批量启用先取 id 再发请求**（按 100/页翻完待确认清单）：接口收 id 清单而不是无参的"全部"，一个不可撤销的大动作不该有免确认参数的形态；同时 confirm 里能写出准确条数（工单验收第 10 条）。
3. **`term.manual.review` 的 key 在前端写成了字符串字面量**（`termRule` 的 `find`）。没有从后端导常量——前端没有常量表这种既有机制，写死一个 key 的代价小于为它建一整套；页面拿不到该项时整块降级成"加载失败"提示，不会静默显示成一个假开关。

**中断与续写**：本票实现代理在编辑前端脚本时因模型不可用中断，后端已完、前端只写了模板（`termRule` / `termPendingCount` / `onBatchEnable` / `saveTermRule` 四个引用无定义）。续写时补了脚本 + `.kb-pending` 样式，并用一次 SFC 编译 + 一次"模板引用 vs script 定义"交叉核对验证——`<script setup>` 缺定义不报错、模板只是静默渲染不出东西，正是当时那种症状。

**只能真机跑的验收**：

1. 上传新文档（工单 01）→ 术语 tab 出现 `来源=模型抽取`、状态 `待确认`；顶部「待确认 N」与按 `来源=模型抽取 + 未生效` 筛出的条数一致。
2. 点「全部启用」→ confirm 条数正确 → 列表状态变「已生效」→ 患者端发 2–5 字含该术语的主诉不再触发模板追问；发「不舒服」**仍然追问**（反向验证）。
3. 手动停用一个**人工**词 → 待确认计数不增加；再点「全部启用」→ 该词仍停用（不被翻回来）。
4. LLM 配置页不再出现「术语人工审核开关」，知识库页可见可改、保存后立即生效。
