# 02: 管理端一键确认——候选词变成生效白名单

**What to build:**

管理员在知识库管理页的「术语白名单」tab 里能看到「**待确认 N · 全部启用**」，一眼分清哪些是模型抽的、哪些是人加的、哪些是人手动停用的；点一下就把待确认的全部启用，**患者端的入口判定立刻用上这些词**。审核开关（`term.manual.review`）也从 LLM 配置页搬到同一页——"哪些词被抽出来"和"要不要我确认"是一件事的两半。

**已定的规则：**

1. **「待确认」的严格口径是 `source=llm_extract AND enabled=0`**，不能只用 `enabled=false`——后者会把管理员**故意停用**的词算进去，那个数字会骗人，而且一次"全部启用"会推翻人的决定。
2. **列表接口增加 `source` 查询参数**（`llm_extract` / `manual`），与既有 `keyword`、`enabled` 组合。不做单独的计数端点（复用同一套分页与筛选口径）。
3. **批量启用端点**：`POST /api/admin/kb/terms/batch-enable`，body `{ ids: [] }`
   - **上限 500 条**，超出拒绝（防一次误点全库）
   - **只对 `llm_extract && enabled=0` 生效**，其余 id 静默跳过
   - **返回实际启用条数**（不是请求条数）——前端拿它做 toast
   - 不做"全部启用"语义（不可撤销的大动作），不做 `action` 参数（多余弹性）
   - 写库后 `refresh()` 一次，不是逐条
4. **状态列区分两种"未生效"**：模型抽取未确认 → 「待确认」；人工维护且 `enabled=0` → 「已停用」。同一列混着写，管理员会以为人工停用的词也能被一键启用。
5. **confirm 文案写明条数与后果**（"将启用 N 条模型抽取的术语，它们会立即参与入口判定"）——启用不是破坏性操作，但候选池大时会显著改变患者端行为。
6. **启用成功后清空筛选、回到第 1 页再刷新**——否则启用后的词可能落在筛选外，管理员看不到、以为没生效。
7. **审核开关归位**：`term.manual.review` 从 LLM 配置页移到知识库页术语 tab（与敏感词页「处置规则与词库同页」同一判据）。后端参数分组相应调整，LLM 配置页由 9 项减为 8 项。

**Blocked by:** 01（没有抽取产物，「待确认 N」永远是 0，本票无法验收）

**Status:** ready-for-agent

**验收**

- [ ] 页面出现「待确认 N」，与按 `来源=模型抽取 + 全部状态=未生效` 筛选出的列表条数一致
- [ ] 点「全部启用」→ confirm 显示正确条数 → 列表状态变为已生效 → **患者端发 2–5 字含该术语的主诉不再被模板追问**
- [ ] 发「不舒服」**仍然追问**（这条是反向验证：白名单只让"含术语的短主诉"过关，不是让所有短句都过关）
- [ ] 手动停用一个**人工**词后，「待确认」计数**不增加**；批量启用也不会把它翻回来
- [ ] 超过 500 个 id → 参数错误，不写库
- [ ] 审核开关在知识库页可见可改，LLM 配置页不再出现
- [ ] 单测：`source` 与 `enabled` 组合筛选条件正确、批量只动 `llm_extract && enabled=0`、返回实际条数、`refresh()` 只调一次
