# 会话首轮事实（服务端） + 查看切片分页（spec）

Status: 01 / 02 / 03 已落地（2026-10-14，真机探针 11 条全过）；**04 / 05 已定案、未实现**——见 `issues/04-register-closes-conversation.md`、`issues/05-register-is-the-only-end.md`
Branch: `feat/session-fact-and-paging`

---

## Problem Statement

**① 部位声明的携带判定在两个事实源上各算一次。**

- 前端：`utils/sse.js` 用 `!sessionId` 预测"这条是新会话"；
- 后端：`ChatService.isFirstTurn(session)` 用会话状态机（`askRound==0 && hasResult!=1`）判"这条是新主诉"。

两者不等价的路径有两条（都是主流路径）：**出结论后**（`hasResult=1`）与**挂号成功后**（`status=CLOSED`）在同一聊天页接着输入 —— 后端会**新建会话**、`isFirstTurn=true`（愿意收声明），前端却因为手里还留着旧 `sessionId` 而**把刚声明的部位丢掉**。而这一轮恰好是**唯一需要声明的那一轮**（声明只在新会话首条生效）。

后果：丢的是结构化的【已标位置】（句子已拼进输入框、`content` 里仍有位置词，检索与术语判定不受影响），也就是"模型不再问部位"这条收益在这条路径上失效。全程**没有日志、没有测试**：后端只在"非首轮被丢弃"时打日志，这条是后端愿意收、前端没带，谁都不出声。

**② 管理端「查看切片」抽屉全量渲染**：`GET /kb/docs/{docId}/chunks` 返回裸列表、不分页，单文档切片多时一屏很长。

**③（2026-10-14 追加）会话边界口径与 UI 对不上**：后端把"**出结论**"当成这次会话的结束（`continuable()` = `status==ONGOING && has_result!=1`），于是患者出结论后问一句"那我该注意什么"会被当成**新的一次就诊**（要求重新声明部位、另开会话、刚才那段原地只读）。用户定案：**挂号才结束，出结论之后仍可继续询问**；并且挂号成功后这段对话要在 UI 上**收尾转只读**，而不是让患者"在旧对话页里开下一次"。这两件事见工单 04 / 05。

---

## Solution

**工单 01**：把判定权收到后端。前端不再预测会话状态，只报**自己知道的事实**（"我手里有一份还没提交的声明"）；`session` 事件新增 `firstTurn`，把后端的判定暴露给前端，UI 的"新就诊"对齐也消费它。

**工单 02**：切片真分页——内容在 SQL 分页，派生（本标题下第几块/共几块）保持**单处 Java 实现**，吃一份瘦投影。

**工单 04 / 05（2026-10-14 追加）**：把"会话边界"这件事在**后端口径**与**UI 行为**上同时对齐——后端改成"挂号才结束"（05），前端在挂号成功那一刻把这段对话**收尾转只读**、想继续就开新会话（04）。两者合起来，"一次会话 = 一次就诊"才在两端说得通。

## User Stories

### 出结论后接着看第二次病（患者）
同一页面继续描述、按提示重选部位、发送 —— 后端开新会话并**收下**这次声明，不再出现"我明明点了位置、它又问我在哪"。

### 挂号成功后回来再问（患者）
`status=CLOSED` 同样会让后端开新会话：前端靠 `firstTurn` 回到等待态，**不再依赖"组件重新挂载"这个巧合**。

### 维护者
声明被丢弃时后端一直有日志；本轮补上"首轮判定"进 INFO，这条路径从此可查。

### 管理端维护者
一份两百片的文档，抽屉一次只渲染一页。

## Implementation Decisions

### 判定只算一次
`stream()` 里算一次 `firstTurn = isFirstTurn(session)`，同时喂两个消费者：`resolveParts(...)`（决定声明是否采纳）与 `session` 事件（决定前端看到的 `firstTurn`）。`resolveParts` 改吃 boolean —— **不许两处各算一次**（这正是本 bug 的成因）。

### `session` 事件字段的边界（必须先说清）
`session` 事件是**服务端 → 客户端**，所以它**无法**决定同一轮请求体里要不要带 `parts`（顺序上不可能）。因此：

- 真正修 bug 的动作是**拆掉前端预测**（有未提交的声明就带，接不接纳交给后端裁决——后端一直就在裁决，且有日志）；
- `firstTurn` 的价值是**把后端判定暴露出来**，让 UI 的"新就诊"对齐不再靠推测，并给排查一个抓手。

兼容性：加字段是加法，老前端忽略即可；**前端对字段缺失也要能工作**（不硬依赖）。

### 前端只报自己的事实
带不带 `parts` = `partStage==='locked' && locations 非空 && 本轮尚未提交过`。前两个都是前端自己的状态（"我完成了声明流程"），第三个是"这份声明还没花掉"。

### 分页（工单 02）
- 内容分页在 SQL（`selectPage`，按 `seq`）；总数由 `IPage` 给出。
- 派生规则**保持单处 Java 实现**（节可能跨页，把它复制进 SQL 会变成第二份实现——本仓库明令禁止"同一份事实两处拼装"）；改为吃一份瘦投影（`id` + `chunk_type`，按 `seq` 序）。
- 复用既有的 `KbAdminDTO.PageVO`、`pageVO(...)`、`clamp(...)`；前端复用 `utils/pager.js` 的 `PAGE_SIZES` / `applySizeChange`。

### 不改的东西
- 追问 / 结论 / 敏感词 / 检索 / 落库行为一律不改；`parts` 进模型上下文的规则不改。
- 不加新表、不加新中间件；只在既有接口上加参数与字段。
- 入库切分不动（那三条上游损耗与本链条无关）。

## Testing Decisions

### 缝一（后端单测 · 先红后绿）
- `ChatServiceTest`：既有的"首轮采纳 / 非首轮丢弃 / 已出结论后开新会话仍采纳"三条保留 —— 它们钉的是**可观察的那一半**（声明有没有进模型上下文）。
- **一致性不写测试，由结构保证**：`firstTurn` 与 `resolveParts` 收成同一个局部值，`isFirstTurn` 全类只调用一次（含 `ruleGate`），编译期就不可能分叉。**事件载荷本身在单测里不可观察**（`stream()` 内部自建 `SseEmitter`，无注入点；真去反射 Spring 的 `SseEventBuilder` 属于测实现细节），所以不为它写假断言 —— 线级载荷交给缝二。
- `KbAdminService` 的分页：**第 2 页起的** `noInSection` / `sectionTotal` 必须与全量推导一致（跨页不串号）、超范围页码与每页条数夹紧、`total` 取自分页结果。

### 缝一之二（前端纯规则自检 · 先红后绿）
- `scripts/check-chat-body.mjs`：请求体规则（**有声明就带，不看 `sessionId`**）。红绿各验一次：把旧写法放回去 → 2 条红；改回 → 全绿。

### 缝二（人工 · 真机探针 · 需要真环境，由用户跑）
出结论后同页继续 → 选部位 → 发送：后端日志应出现「会话新建」+ 声明被采纳，**不应**出现「部位声明丢弃」。

### 不做的事
不给 SSE 加"发请求前的握手"（那是协议重构，与本 bug 无关）。

## Further Notes

这条 bug 与仓库里踩过的「一个值扛两种粒度」同源：**同一个判定（是不是新就诊）在两处各自算，而两处用的事实不同**（前端看 `sessionId`、后端看状态机）。判据仍是那一句：**同一个值服务两个消费者时，只许有一处算它。**
