## Problem Statement

患者开口说"肚子疼"，系统的第一反应往往是先问一句"具体是哪个部位不舒服"——**这一问是白问的**：部位是患者最知道、也最容易表达的一件事，却要占掉一次追问机会（追问上限只有 3 轮），而真正需要问清楚的（疼的性质、时长、诱因、伴随症状）被挤到了后面。

反过来说，患者想主动说清楚位置也很难：输入框是一张白纸。"右下方肚子疼"和"肚子疼"在他眼里差不多，在分诊里却是**不同的提示方向**（右下腹痛要留意阑尾，上腹痛多在胃）。他既不知道该说到多具体，也没有一个便宜的表达方式。

结果是：**追问轮次花在最不该花的地方，而分诊最需要的范围信息反而最模糊。**

---

## Solution

在患者开口之前，先让他在**人体图上点一下**——把"哪里不舒服"这一步从对话里拿出来，变成一次十秒钟的点选。

具体形态：

1. **新会话的第一条输入之前，先声明部位**（必填）：点人体图 → 选位置 → 顺手点一下"哪一侧"和"什么感觉" → 拼成一句话落进输入框 → 患者接着补自己的话，然后发送。
2. **部位词全部来自后端已有的术语白名单**（`medical_term` 的 `type=part`）：图上只会出现判定认得的词，所以选出来的句子一定不会被规则门槛判成"过于笼统"。
3. **必填的是"这一步动作"，不是"必须点中某个区域"**：覆盖层里保留「说不清在哪儿 · 直接描述」出口。发烧、乏力、浑身没劲、头晕这类主诉根本指不出位置，没有这个出口这批人会被挡死。
4. **追问不变**：部位落定之后，系统照旧问性质、时长、诱因、伴随——**部位声明只省掉"问部位"这一轮，绝不省掉追问本身**。

患者拿到的是：少被问一句废话，以及一个比打字更省事的表达方式。系统拿到的是：**首轮就带着明确的范围**。

## User Stories

### 首次进入 · 声明部位

1. 作为患者，我希望打开页面时就被清楚地告知"先告诉我哪里不舒服"，而不是面对一个不知道从何说起的空白输入框。
2. 作为患者，我希望用一个按钮打开人体图，而不是自己去猜这个功能藏在哪。
3. 作为患者，我希望在图上点一下就能选中一块位置，不要让我输入任何坐标或文字。
4. 作为患者，我希望选中的那块在图上**看得出被选中了**，以便确认我点对了地方。
5. 作为患者，我希望图有**正面和背面**两个视角，因为背痛、腰痛在正面图上根本指不出来。
6. 作为患者，我希望点中一块较粗的区域后，能看到它包含的更具体的说法（比如"腹部"下面还有"上腹 / 腹部 / 下腹"），以便我选得更准。
7. 作为患者，我希望**可以选多个位置**（比如"上腹和下腹都不舒服"），而不是被迫二选一。
8. 作为患者，我希望顺手点一下「哪一侧」（左 / 右 / 两侧），因为左边疼和右边疼对医生是两件事。
9. 作为患者，我希望这一侧可以不选——我不知道该算哪边的时候不想被迫选。
10. 作为患者，我希望再点一下已选的那一侧就能取消，不用找别的按钮。
11. 作为患者，我希望顺手点一下「什么感觉」（疼 / 胀 / 酸 / 麻 / 灼热 / 绞痛 / 刺痛），以便少打几个字。
12. 作为患者，我希望「说不上来」也是一个可选项——感觉本来就说不清的时候，我不想被逼着选一个。
13. 作为患者，我希望在选择过程中**随时看到"这句话最后会长什么样"**，以便知道自己在凑出什么。
14. 作为患者，我希望在"已选"那一栏里能一条条删掉选错的东西，而不是只能全部重来。

### 必填与出口

15. 作为患者，我希望在没声明部位之前，输入框是**明确的等待态**（灰掉 + 一句"先选好位置就能开始说了"），而不是能打字但发不出去。
16. 作为患者，我希望**说不清位置时也能开始问诊** —— 有一个「说不清在哪儿 · 直接描述」的出口，点了就让我直接说话。
17. 作为患者，我希望点了那个出口之后，系统对我就和以前完全一样（照旧追问、照旧能出结论），**不要因为我没选位置就降级对待我**。
18. 作为患者，我希望**只有新的一次就诊才要求我声明位置**，后面系统追问时我回答"三天了""左边，按压更疼"这些短句，不要再被拦一次。
19. 作为患者，我在旧会话里接着说话时，不希望被要求重新选位置。
20. 作为患者，我希望位置选错了能一键重新选，不用退出重进。
21. 作为患者，我希望"位置已经锁定了"这件事在界面上有一处明确的回执，以便我知道系统收到了。

### 表达的自由度

22. 作为患者，我希望选完之后输入框里是**可编辑的一句话**，而不是一个不可改的成品 —— 我还要补"两天了，一阵一阵的，饭后更明显"。
23. 作为患者，我希望图上表达不了的信息（"左手更明显""弯腰时加重"）照样能写在输入框里，图上没覆盖到的部位（比如胃、心口）也能直接打字说。
24. 作为患者，我希望系统**不要因为我选了位置就不再追问** —— 我选的是"腹部"，它该问我疼的性质、多久了、有没有别的不舒服。
25. 作为患者，我希望常见主诉的快捷词（肚子疼 / 头疼头晕 / 心慌胸闷 / 腰背酸痛 / 皮肤起疹）点一下就**直接带我去图上对应的位置**，而不是绕过这一步。

### 可理解与可信

26. 作为患者，我希望覆盖层里有一句话解释"为什么器官不在图上"（心 / 肺 / 胃 / 肠是器官，不是体表位置），以免我找不到自己的症状时以为系统做不了。
27. 作为患者，我希望图上**不出现让我做医学判断的选项** —— 我指得出"肚子这块疼"，但指不出"胃在哪"。
28. 作为患者，我希望知道这一步是必填的、以及大概要花多久，而不是点进去才发现有流程。

### 术语与可维护（管理员）

29. 作为管理员，我希望部位词的**唯一来源仍是术语白名单**，而不是前端另存一份 —— 否则我在管理端停用一个词之后，患者端还在让他选。
30. 作为管理员，我希望停用某条部位术语后，患者端的位置选项里**立刻不再出现它**。
31. 作为管理员，我希望新增一条部位术语时**不需要改前端代码**它就能出现在选项里（前端只为已画出的区域提供图形）。

### 可观测（开发者 / 排查）

32. 作为开发者，我希望**没有声明部位的请求与今天的链路行为完全一致**（回归零退化），以免这个功能成为一次无法回滚的行为变更。
33. 作为开发者，我希望模型能明确知道"位置已经确认过了"，以免它习惯性地再问一遍部位、白吃一轮追问。
34. 作为开发者，我希望前端**提交的句子**（进检索）与**声明的部位**（进模型上下文）是同一份事实派生的两样东西，不出现"检索里没有部位词"这种自相矛盾。
35. 作为开发者，我希望前端图上词与后端术语表**对不上时能被测试抓到**，而不是等到患者点了图却发现毫无作用。

## Implementation Decisions

### 模块与接口

- **kb 模块 · `MedicalTermService`**：新增一个按类型取词的方法（`type = part` 且 `enabled = 1`）。现有实现把全部启用术语加载成一个内存集合，**不带类型过滤**，类型字段目前只有管理端页面在显示标签，没有任何代码消费过它——所以"按类型取"必须是新增能力，不是复用。
- **admin 模块 · `ChatController`**：新增只读接口 `GET /api/chat/parts`，与既有的 `GET /api/chat/depts`（患者端取科室清单）并排，风格一致。**响应为字符串数组**（只含部位词）——"图上哪块区域对应哪个词"是前端资产，后端不提供，也不需要知道。
- **chat 模块 · 首轮入参**：`MessageReq` 新增一个可选字段承载**部位声明**（字符串数组）。缺省为空数组 ⇒ 行为与今天完全一致。
- **admin 模块 · 主提示词**：新增一句，把已声明的部位作为**已知信息**注入，措辞要说明"**这是患者在人体图上标明的，不必再追问部位**"。措辞刻意用"患者标明的位置是 X"，**不说"患者的部位是 X"**——因为患者随后可能自己改掉输入框里的那句话，而"他标过 X"这个事实始终为真。
- **患者端 · 位置声明纯函数**（新建，零依赖）：输入覆盖层的选择状态，输出两样东西：

  ```
  { locations: string[], sentence: string }
  ```

  - `locations` = 方位前缀 + 部位词（例：`["左腹部"]`）；**全身性词（皮肤、关节）不加方位前缀**
  - `sentence` = `locations` 顿号连接 + 感觉 + 「，」（没选感觉时回落成"不舒服"）
  - 「说不上来」是感觉里的占位项，**不进句子**
  - 这个函数的输出就是前端的提交物：`sentence` 进患者那句话（`content`），`locations` 进部位声明字段

- **患者端 · 人体图覆盖层**（新建）：SVG 前后两面 + 区域映射表 + 细分词 + 方位 + 感觉 + 已选 + 预览 + 两个出口。复用既有的"健康档案覆盖层"那套浮层语言，**不新造一种浮层**。

### 关键决策

- **部位声明的判据与「新主诉判定」同口径。** 门禁只作用在**会被判定为新会话的那一条输入**上；进行中的会话内（含追问应答轮、回放后继续、归档会话里续聊）**一律不拦**。判据必须与后端同一口径（会话是否已出结论、是否已关闭），且以**后端状态**为准（新会话 id 由 SSE 的 `session` 事件回传）。这是本功能最容易做错的一处：判据若与后端不一致，患者要么被反复拦、要么整条门禁形同虚设。
- **"说不清在哪儿"出口不产生部位声明。** 此时 `content` 就是患者原话、声明字段为空 ⇒ 链路回落到今天的行为（模型可能追问部位）。**这是接受的降级**，不是待修的缺陷。
- **必填是引导，不是后端强制。** 后端不校验"必须带部位声明"，它只是一个可选入参。强制点在前端的门禁上——把必填做进后端会让"说不清"那条路彻底断掉。
- **声明字段只在首轮携带**，追问轮不带（上下文里已经有了）。
- **不把方位与感觉并进声明字段**：声明字段只装部位（`["左腹部"]`），感觉留在患者那句话里。语义清晰、也让后端不必重新拼一次。
- **图上只出现术语表里已有的词。** 这是硬约束：拼出来的句子若不含部位词，就绕不过信息充足性规则门槛，这个功能等于白做。
- **心肺胃肠刻意不进图**：它们是器官不是体表位置，让患者自己在图上指"心的位置"等于诱导自我诊断。它们仍在术语白名单里，患者打字说"胃疼"照样命中。
- **「腹」不进图**（它是"腹部"的单字形式，图上不重复给）。
- **感觉词是前端自持的**（疼 / 胀 / 酸 / 麻 / 灼热 / 绞痛 / 刺痛 / 说不上来）：术语表里的症状词全是「部位 + 症状」的复合词（腹痛 / 胸痛 / 头痛 / 腰痛），**没有"绞痛 / 刺痛"这类纯形容词**，这一排无法与后端同源。不影响判定——句子里已经有部位词兜住命中。
- **方位不是新词**：术语表里没有左 / 右 / 侧，但"左腹部 / 左上肢"含部位词，照样命中白名单；且"上腹 + 左"在临床上本来就写成「左上腹」，组合结果比口语更规范。
- **常见主诉快捷词改为图的快捷入口**（只保留能明确对应区域的 5 个：肚子疼 → 腹部、头疼头晕 → 头、心慌胸闷 → 胸口、腰背酸痛 → 腰、皮肤起疹 → 皮肤）。**移除"发热咳嗽"**——它对应不了任何体表区域。目的是让必填变成省事，而不是拦路。
- **无库表变更、无中间件新增、无新依赖。** 术语表已经是既有事实源，本功能只是给它加一个读取角度。
- **管理端零改动。**

### 提交与状态

- 前端提交时：`content` = `sentence` + 患者补的字（患者可编辑），部位声明字段 = `locations`（**不随患者后续编辑变化**）。
- 空对话的初始态：输入框为等待态；覆盖层关闭后回到引导页（不是死路——大按钮就在原处）。
- 页面状态是一个三态机：`引导 → 选图 → 已锁定`。任何一个出口都通向"已锁定"，区别只在于声明字段是否为空。

## Testing Decisions

**好测试的判据**：只断言**外部可观察的行为**，不断言实现细节——不断言某个 CSS 类名、不断言某个私有方法被调用、不断言中间数据结构。断言"给定这个输入状态，拼出来的句子/声明是什么"，以及"给定这个请求，链路行为的差异是什么"。

### 缝一（新建）· 患者端位置声明纯函数

- **测什么**：区域→词映射、拼句、方位前缀、全身词不加前缀、"说不上来"不过滤进句子、清空与部分选择、以及**映射里的词都在一张显式词清单内**（越界即失败）。
- **先例**：`utils/evidenceReplay.js` —— 本仓库既有的零依赖纯函数模块，当年用**临时 node 脚本**跑了 17 组断言（覆盖正常 / 无档案 / 坏 JSON / 空串 / 数组 / 缺字段 / 边界），验完即删、不入库。前端没有测试框架，这是本项目确立的做法，照抄。
- **为什么这是最高缝**：它是唯一一个"能纯逻辑地表达这个功能全部规则"的地方——覆盖层的视觉、门禁的时机都无法自动化，但**规则的每一分支都能在这里被断言**。

### 缝二（复用）· chat 模块的服务测试

- **测什么**：带部位声明时，首轮不进模板追问、声明被注入模型上下文；**不带声明时链路行为与今天完全一致**（回归）；声明只在首轮携带，追问轮不重复注入。
- **先例**：`ChatServiceTest` —— 既有风格是**断言落库副作用**（SSE 事件与落库的 role 一一对应），因为流式方法内部建 emitter、没有注入点。新增断言沿用同一手法。

### 缝三（复用）· kb 模块的术语服务测试

- **测什么**：按类型取词只返回部位词；停用项不返回；**不把症状词混进来**；结果与种子词清单一致。同时断言"停用后立即不返回"（该服务有 60 秒缓存与显式失效两条路径）。
- **先例**：kb 模块既有的服务测试（`KbAdminServiceTest` 等）。

### 缝四（人工）· 视觉与门禁时机

- **测什么**：无法自动化，只能真机目视——人体图区域点选是否准确、正反面切换、覆盖层与既有浮层语言是否一致、等待态是否够清楚、触控目标 ≥44px、响应式在 375–430px 不破。
- **不做自动化测试的诚实理由**：本仓库没有前端测试框架，为一套静态视觉引入快照测试的收益远低于维护成本；而门禁时机依赖真实会话状态流转，只有端到端点一遍才可信。

### 不做的事

- 不新增跨语言校验缝（脚本读后端种子词源码与前端映射做交叉校验）：文档解析脆弱、收益低于维护成本。改为**两边各守一张显式词清单**——任一边改了词，那一边的测试就红。

## Out of Scope

- **患者端视觉重设计本身。** 皮肤按方向 04「导诊伙伴」（暖沙 + 青绿 + 杏色、大圆角、陪伴语气）重做，走 `.claude/rules/前端设计方案.md` 患者端部分的重写，**不进本 spec**——它没有自动化判据，混进来会让 agent 分不清哪些条目能自动化。本 spec 只要求覆盖层"复用既有浮层语言"，不规定配色。
- **管理端的任何改动。** 管理端保持冷靛控制台不动。
- **把"患者选了哪个部位"落库做统计。** 这是个分析需求（哪些部位最常被选、选完以后推荐准不准），不是本功能的需求；已被明确推迟。
- **方位与感觉进入结构化字段。** 它们只留在患者那句话的文本里。
- **心肺胃肠进图、图上区分左右。**
- **语音输入、图片输入、多模态。**
- **删除或改写历史导诊记录。** 本功能只影响新会话的首条输入。
- **回改已归档 / 已出结论的会话。**

## Further Notes

- **需要补进 `CONTEXT.md` 的词条**：部位声明（患者在新会话首条输入前于人体图上标明的部位）、人体图（前后两面的体表区位图）。术语表里现有"部位"只是术语白名单的一个类别，与"患者声明的部位"不是同一个东西——写代码前先把词条补上，避免两处混用。
- **前端图上词与后端术语表的关系**是这次唯一一处必须靠约定维持的不变式：图上只能出现术语表里已有的词。两边各自被测试守着（缝一守前端清单、缝三守后端清单），但**没有单点自动校验**——这是明知的取舍。
- **术语白名单现在承担着三类读者**：入口防误杀（精确匹配）、信息充足性判定（子串匹配）、以及本功能（患者端选项）。第三类的加入让"内容安全配置"顺手决定了"患者能点什么"——目前两边能对上，但严格说是同一个字段承担了两个领域的职责。若日后要解耦，方向是给术语表加一个"对患者可见"的标记，或另建一张部位词表；**本功能刻意不加这个字段**（在真的遇到冲突之前属于投机性设计）。
- 可交互草案（四个页面状态：引导 / 选图 / 已锁定 / 发出后的追问）在 `前端方案/重设计-四方向草案/06-导诊伙伴-人体图选部位.html`，含"29 个部位词的覆盖账"：图内可选 22 / 全身快捷 2 / 刻意不进图 5。**草案是点时间产物，落地后不需要维护它**。
- 患者端皮肤那一份工作（令牌、部件规范、页面清单、逐屏验收）建议按"每屏独立可回退"分批推进，与本 spec 的落地互不阻塞——先换皮再上功能，两批各自可验证。
