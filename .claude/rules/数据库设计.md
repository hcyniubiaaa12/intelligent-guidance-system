# 数据库设计 —— 智能导诊系统

> 版本：v0.4（可能随功能修改调整，改动需同步本文档）
> 依据：《总体架构与链路设计.md》v1.4。MySQL 管事实，pgvector 管语义，ES 管全文检索与术语聚合。
> 通用约定：全部业务表带以下公共字段（下表只列业务字段，公共字段不重复）：
>
> | 公共字段 | 类型 | 说明 |
> |---------|------|------|
> | id | varchar(32) | 主键，Java 侧雪花算法生成（String） |
> | deleted | tinyint | 逻辑删除，0 正常 / 1 删除 |
> | created_at | datetime | 创建时间 |
> | updated_at | datetime | 更新时间 |
>
> 可变配置类信息抽离为独立字段/字典表，不散落在文本里。

## 0. 枚举字段规范

多状态字段一律枚举化，禁止在代码里散落魔法值（字符串字面量）。

**存储与装载**

- 数据库存**英文小写编码值**（如 `ongoing`），不存数字、不存中文——直接查库/排查时可读，新增值不会错位
- 列类型统一 `varchar(32)`，默认值写小写编码值
- Java 侧每字段一个枚举，放各模块 `enums` 包；枚举的编码字段用 MyBatis-Plus `@EnumValue` 标注，实体属性类型即枚举本身，读写自动转换：
  ```java
  @Getter
  @RequiredArgsConstructor
  public enum SessionStatus {
      ONGOING("ongoing"),
      CLOSED("closed");

      @EnumValue
      private final String code;
  }
  ```
- 枚举值**只追加不插队**（尾部新增），避免历史数据语义漂移

**不枚举化的字段**

- 纯布尔语义字段保持 `tinyint` 0/1：`deleted`、`enabled`(dept/sensitive_word/medical_term)、`low_confidence`、`top1_hit`、`top3_hit`、`aggregated`
- JSON 快照内容（`rec_top3`、`evidence`）不枚举化，按写入时原样保存

**全字段枚举清单**

| 模块 | 表.字段 | DB 取值（英文小写） | Java 枚举类 |
|------|--------|------------------|-----------|
| auth | user.role | patient / admin | UserRole |
| auth | user.status | normal / banned | UserStatus |
| auth | sensitive_word.type | banned / watch | SensitiveWordType |
| chat | chat_session.status | ongoing / closed | SessionStatus |
| chat | chat_message.role | user / ai / question | MessageRole |
| kb | kb_doc.status | parsing / done / failed | DocStatus |
| kb | kb_doc.fail_type | retryable / fatal | DocFailType |
| kb | dept_mapping.source | init / manual / feedback | MappingSource |
| kb | medical_term.type | part / symptom | TermType |
| kb | medical_term.source | llm_extract / manual | TermSource |
| feedback | track_event.stage | result_view / sim_register / register_success | TrackStage |
| feedback | filter_log.action | blocked / watched | FilterAction |
| feedback | cluster_bucket.status | monitoring / pending / approved / rejected / dismissed | BucketStatus |
| feedback | review_task.status | pending / done | ReviewStatus |
| async | ingest_task.stage | parse / split / embed / done | IngestStage |
| async | ingest_task.status | running / success / failed | IngestStatus |

> 同名不同义：`kb_doc.status`(DocStatus) 与 `ingest_task.status`(IngestStatus) 是两套枚举，不合并。
>
> **例外**：`root_cause.causes` 的根因选项由**前端硬编码清单**定义（预定义 7 项），后端按 JSON 数组原样存取、不校验、不建后端枚举——选项清单变更只需改前端。
>
> ⚠️ **与实现的校正（2026-09-20）**：本节原写「选项存小写 key」，但实际前端硬编码的是**中文名本身**（`切分破碎` / `解析遗漏` / `检索失败` / `局部映射缺失` / `模型未依据检索` / `结构化失败` / `患者挂错`），看板与后续审核页都按这个存。已按实现校正，勿再按"小写 key"实现。
>
> - **`患者挂错` 有后端语义**：看板准确率口径要排除标了它的记录（`stats/service/DashboardService.CAUSE_PATIENT_WRONG`）。改这个文案必须同步后端常量，否则口径静默失效
> - **待决（建议在审核页动工时一并定）**：是否改为稳定小写 key + 前端 label 映射。好处是改文案不打破统计口径；代价是看板与审核页要同时改，且要看板侧多一份 key→中文名映射（或后端出枚举）

## 1. 用户与鉴权（auth，链路 D）

| 表 | 业务字段 | 说明 |
|----|---------|------|
| user | username, password(加密), role(patient/admin), nickname, status(normal/banned) | 登录注册；登录时校验状态（封禁即拒绝）；管理员由初始化脚本创建 |
| sensitive_word | word, type(banned/watch), hit_count, enabled | 敏感词库（链路 A 入口前置校验）；管理端可维护，支持批量导入 |
| sys_config | config_key, config_value, remark | 运行时可调配置字典表（管理端可调，进程内缓存 60s TTL，改后最长一分钟生效）。现有键：`cluster.bucket.threshold` 聚合归桶阈值(0.85)、`guide.upgrade.rounds` 升级阈值(3)、`guide.low.confidence` 低置信度阈值(0.5)、`term.manual.review` 术语人工审核开关、`retrieve.top.k`/`retrieve.top.n` 检索 Top-K/Top-N、`chat.ask.max.rounds` 追问轮数上限(3)。LLM API Key/模型名不走本表，坚持 application-local.yml（密钥不进库）。**管理端能改的只有这 7 个键**——后端白名单制（`auth/service/SysConfigAdminService` 的 ParamSpec 定键/类型/取值范围/默认值），不在白名单的键直接拒绝；值缺失时回落代码侧默认值（首次部署不灌本表也能开管理端页面）。详见《总体架构与链路设计.md》§7.1 |

## 2. 会话与导诊（chat，链路 A）

| 表 | 业务字段 | 说明 |
|----|---------|------|
| chat_session | user_id, status(ongoing/closed), ask_round(追问轮次 0–3), has_result(0/1，已出导诊结论) | 一条主诉一个会话；挂号成功（register_success）即置 closed；**新主诉判定 = 双信号：已出 result（has_result=1）或 closed 后，下一条输入开新会话**（未出 result 的 ongoing 会话内输入按追问处理；判定是状态机字段，非模型语义判断）；一个聊天页可先后承载多个会话 |
| chat_message | session_id, role(user/ai/question), content | question 即追问消息 |
| guide_record | session_id, rec_dept_id, confidence, rec_top3(JSON Top3 候选快照), low_confidence(0/1), actual_dept_id, top1_hit, top3_hit, aggregated(0/1 增量标记), evidence(JSON 证据快照) | 一条主诉一条导诊记录；rec_top3 与 evidence 同为只写快照，供看板"排序精度"聚合与审核回放；confidence = 模型自报的 top1 置信度（LLM 输出 JSON，后端校验 0–1 区间与单调递减，异常置 null 并按低置信度分流）；actual_dept_id 由挂号确认接口在 register_success 时与 top1_hit/top3_hit 同事务写入（非 feedback 回写）；**患者可不挂号（流失）——actual_dept_id 允许为空，为空则不参与准确率统计（口径 = 已确认记录）**；历史不回改 |

## 3. 知识库（kb，链路 B）

| 表 | 业务字段 | 说明 |
|----|---------|------|
| dept | name, enabled(0/1), location, intro | 科室蓝本，模拟挂号科室范围；**停用仅入口生效**：挂号页不显示 + 推荐校验拦截（见链路 A 对齐点），chunk 留库不删、历史记录引用不受影响 |
| kb_doc | dept_id, title, file_url(MinIO 链接), status(parsing/done/failed), fail_reason, fail_type(retryable/fatal), chunk_total, chunk_done | 文档状态机：解析中→完成/失败 |
| kb_chunk | doc_id, title, content, seq | 切片，MySQL 存事实；向量在 pgvector 同步；回流 approve 生成的**合成 chunk**（症状→正确科室鉴别语料，文本由 LLM 生成、管理员预览定稿）也写这里，doc_id 指向系统级「回流知识文档」容器，走链路 B 同一流水线——闭环生效唯一机制（RAG 检索到合成 chunk，同类主诉推荐变对） |
| dept_mapping | symptom, main_dept_id, cross_dept_ids(JSON), source(init/manual/feedback) | 症状交叉映射台账；运行时**不被 RAG 消费**（闭环生效靠合成 chunk，见 kb_chunk 说明），仅管理端维护与审核事实记录；回流 approve 写 source=feedback。台账键 = **(symptom 原文, main_dept_id)** 唯一：同键合并（cross_dept_ids 取并集）、异键新行——同症状可因不同方向的桶各审出一个主科室，各占一行 |

## 4. 检索存储（kb 唯一写入，双写）

### 4.1 pgvector（向量库，管语义）

| 表 | 业务字段 | 说明 |
|----|---------|------|
| kb_chunk_vec | chunk_id, dept_id, embedding vector(HNSW) | 向量召回；与 MySQL kb_chunk 以 chunk_id 对应 |
| cluster_bucket_vec | bucket_id, direction(rec_dept_id, actual_dept_id), embedding vector | 聚类锚点向量，语义归桶时按 direction 过滤 + 余弦检索；**归 feedback 模块直写（例外：kb 的"唯一写向量库入口"只管 RAG 语料）**；开新桶时写入 |

### 4.2 Elasticsearch（chunk 索引，管全文检索与术语聚合）

| 索引 | 业务字段 | 说明 |
|----|---------|------|
| chunk 索引 | chunk_id, dept_id, title, content, medical_terms(数组) | 关键词召回(BM25，title^2 加权) + terms 聚合得术语白名单；medical_terms 由 LLM 批量实体抽取产出；title 供推荐卡溯源引用。中文分词用 analysis-ik（索引 ik_max_word / 检索 ik_smart），建索引幂等，由应用启动时确保存在 |

### 4.3 MySQL（白名单副本）

| 表 | 业务字段 | 说明 |
|----|---------|------|
| medical_term | term, type(part/symptom), source(llm_extract/manual), enabled | 白名单**唯一生效源**，chat 入口加载内存 Set 一律取自此表；ES 聚合只是候选池；LLM 抽取新术语落库默认 enabled=0，受"人工审核"开关控制——开启时需管理端确认启用，关闭时直接 enabled=1；管理端增删/停用即时影响线上校验；知识库更新时刷新 |

## 5. 反馈闭环（feedback，链路 C）

| 表 | 业务字段 | 说明 |
|----|---------|------|
| track_event | record_id, user_id, stage(result_view/sim_register/register_success), dept_id, occurred_at | 埋点三触点，旁路落库；只作漏斗/耗时等过程信号，非准确率事实来源（事实在 guide_record.actual_dept_id） |
| filter_log | user_id, session_id, word_id, action(blocked/watched), matched_at | 敏感词过滤日志，旁路落库不阻塞主流程 |
| cluster_bucket | direction(rec_dept_id, actual_dept_id), anchor_text, exact_key, count, status(monitoring/pending/approved/rejected/dismissed) | 错误模式聚合桶（MySQL 存事实）；锚点固定不漂移；方向预筛；锚点向量不存本表，在 pgvector cluster_bucket_vec（见 4.1）。status 语义：rejected=审过否定（审核意见）、dismissed=未审清理（噪声）；终态桶可人工「修正重审」回 pending——幂等约束只针对自动升级 |
| review_task | bucket_id, status(pending/done), reviewed_by, reviewed_at, main_dept_id | 待审核队列；写知识库唯一路径是人工 approve；main_dept_id = 审核给出的主科室（修正目标），随确认写入映射台账 |
| root_cause | record_id, causes(JSON 多选), updated_by, updated_at | 根因归因：审核页**桶级一键套用**（写入桶内每条记录）、**可逐条覆盖**；与 approve/驳回互不代劳。可事后修改，看板按最新聚合；causes 存根因选项 key（选项清单前端硬编码，暂不建字典表） |
| root_cause_log | record_id, causes_before(JSON), causes_after(JSON), updated_by, updated_at | 归因修改历史，每次修改追加一条不覆盖；纯审计留痕，不参与看板聚合 |

## 6. 统计（stats）

- 不建新业务表：基于 guide_record（命中率）、cluster_bucket + root_cause（错误分布）实时/定时聚合；**看板 miss 口径 = actual_dept 非空 且 low_confidence=0 且 top3_hit=0 且未标"患者挂错"根因**（低置信度进盲区榜不算 miss；按 root_cause 最新归因排除患者挂错）；聚合中间结果可落 summary 缓存表（维度, 周期, 指标, 值）。

## 7. 离线任务（async，链路 B 流水线）

| 表 | 业务字段 | 说明 |
|----|---------|------|
| ingest_task | doc_id, stage(parse/split/embed/done), status(running/success/failed), total, done, error | 任务表是权威状态；幂等与重试以 taskId 为键 |
