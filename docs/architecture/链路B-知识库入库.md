# 链路 B：知识库入库链路

> 本文是《总体架构与链路设计.md》（仓库根，**总册**）的分册之一。全局约定——分层视图与设计原则、模块职责边界与依赖方向、部署形态、已定参数汇总——都在总册；动本册前先读总册 §1 / §3 / §5。

### 链路 B：知识库入库链路

```
管理端 DocManage 页        后端（异步线程池 + 任务表）          MinIO / pgvector
───────┬───────────────────┬─────────────────────────────┬──────────────────
  ① 上传文档                │                             │
  ② POST upload ─────────→ │ ③ 文件进 MinIO（存链接）       │→ MinIO
       │                   │    建任务表(taskId, 阶段=解析) │
       │                   │ ④ 提交线程池 → 解析→切分      │
       │                   │ ⑤ 切分 → embedding           │
       │                   │    → 批量写 chunk             │→ pgvector
       │                   │ ⑥ done/total 计数收敛 → 文档完成 │
  ⑦ 状态刷新(按 taskId) ◄─ │  （任务表是权威状态，幂等/重试    │
       │                   │   以 taskId 定位；线程池与 SSE   │
       │                   │   线程隔离，不拖慢在线导诊）       │
```

**组件作用**：
- **异步线程池 + 任务表**：入库流水线阶段编排（解析→切分→向量化→入库），阶段间异步衔接、**并发上传排队**；任务表记录进度（taskId 定位当前阶段），幂等与失败重试都以 taskId 为键；**只服务离线入库，不碰在线导诊链路（线程隔离）**。
  > 「排队」是有的（线程池队列 + 外部解析服务的并发限制），但**不存在"批量上传"这个接口形态**——一次请求只处理一个文件，多个文件由前端循环发起。这样每个文件有独立的事务边界、独立的 taskId、独立的失败，**部分成功不需要任何额外设计**：传 10 个挂 3 个，用户看到 3 条错误 + 7 条正常记录。把"批量"塞进一个请求，等于让后端承担"部分成功"这个新状态空间，再让管理端表达一遍。任务表还担着两件事：**失败留痕**（`status=failed` + `error` + 可重试/不可重试分类，决定「重新处理」按钮给不给）与**异步句柄**（上传接口不能等解析完才返回，把 taskId 交给前端轮询进度）
- **`kb_doc` 与 `ingest_task` 的分工**：两者都有状态字段（`status` / 失败原因 / `chunk_total`·`chunk_done` 对 `total`·`done`），但语义不同——**`kb_doc` 是文档的当前态**（管理端列表直接读它，一个文档一行），**`ingest_task` 是每一次运行的记录**（一个文档 N 次运行：首次 + 历次 reprocess，每次一行）。列表展示读前者，重试与排查读后者。**不要合并**：合并会让重试覆盖掉上一次的失败原因，"重试过几次、上次为什么失败"就再也答不上来
- **阶段状态只有任务表能表示**：向量行只在 `embed` 之后才存在，`parse`（正在解析）、`split`（切出 N 片但一条未入库）这两个阶段在向量表里是**零行**——所以进度、失败原因、阶段这类信息**必须**由任务表承载，不能让向量表兼职
- **MinIO**：对象存储，存文档原始文件；数据库只存链接/路径；解析重试可重复拉取原文。**没有「替换文件」这个操作**——重入库拿的就是 MinIO 里的原文件；要换内容就删掉这份文档、重新上传一份（不留旧对象、不留残余）

**对齐点**：
- 文档状态机：`解析中 → 完成 / 失败`，失败按原因分类（可重试/不可重试），可手动 reprocess
- **同一文档同一时刻最多一个 `running` 任务**：提交前检查该 `doc_id` 有无在跑的任务，有就拒绝（「该文档正在处理中，请等待完成」）。
  > 这条**比「以 taskId 为键的幂等」更强**，而后者管不到它：两条任务各自的 taskId 不同、各自都"幂等"，但合起来不幂等。放任两条并跑，按「先删旧再重建」的语义会交错删除与写入，最终库里是哪一套取决于谁最后写完，`chunk_total`/`chunk_done` 也会被交替更新成不确定值——而且**同一份文档付两次解析费**。同理不选"后到的取消先到的"：外部任务取消不掉，那份钱已经花了。
- **一份文档 = 一个科室**：`kb_doc.dept_id` 是**文档属性**，它的全部切片**继承**同一个科室（写进向量表的 `dept_id` 就是它；在线链路上它只服务**兜底选科**，不参与推荐校验——见 `docs/architecture/链路A-导诊对话.md`「科室校验」的注）。跨科室的内容**拆成多份文档上传**——上传界面要明确写这句话，别让这个约束留在默认里。
  > 说清这条约束的**性质**：它是**归口与可维护性**上的（一份文档归谁管、停用/统计/展示怎么算），**不是**"不拆就会推荐错"。文档的科室标签不约束模型能推荐谁——真要支持跨科室内容，靠的是**内容本身写清楚**，不是靠标签。
  > 为什么不让文档挂多科室、或把科室下移到切片级：那会把 `dept_id` 从**文档属性**降级成**切片属性**，一处改动牵动三处（向量表结构、召回过滤、chat 的推荐校验），换来的只是"跨科室文档不用拆"。而本项目的知识库本来就是按科室组织的（种子语料就是每个科室各一份，现 12 个科室），拆一份的成本远低于改这三处。
- 一致性（双库 + ES + 对象存储）四层防线：
  ① 入库校验：切分入库前查文档/任务表是否仍有效（处理中被删则不写向量与 ES）。**删除文档时同时终止它在飞的任务**——把该文档 `running` 的 `ingest_task` 置 `failed`（`error="文档已删除"`，不是 `success`：`success` 会让人以为处理完成了，而它并没有），定时任务扫到后自然跳过。
  > 为什么不能只靠这一层校验：**那次解析是按量计费的**。防线①能拦住"写脏数据"，拦不住"白跑一趟"——任务照常轮询、解析照常跑完，最后才发现文档没了。终止在飞任务不是额外机制，是**删除动作应有的一部分**。
  > 两道并存：终止任务覆盖"还在轮询中"的；防线① 覆盖"已经投回线程池队列、正要写库"的——后者赶不上了，但拦得住。
  ② 状态机收敛：全部 chunk 写入成功（pgvector + ES 双写完成）才置"完成"（done/total 计数），失败保持可重试
  ③ 写时补偿：**MySQL 在事务里，pgvector 与 ES 不在**——ES 或向量库写失败时 MySQL 会回滚，但**已写入的向量不会跟着消失**。故 `ChunkIndexService.indexChunks` 内 try/catch，失败时用本次内存里记下的 chunk_id 批量回删向量后再抛出。覆盖"依赖不可用"这类常见故障（进程仍存活）；JVM 崩溃等极端情况由下一层的读时兜底接住（脏命中不进 Prompt，只是白占空间）
  ④ 删除补偿：先删 ES → 再删向量 → 再删元数据 → 再删 MinIO 文件，顺序保证 + 失败标记待重试
- **chunk 双写**：切分后 chunk 同步写 pgvector（向量检索）与 ES（关键词检索 + 术语聚合），LLM 批量实体抽取结果随 chunk 入 ES（详见 `docs/architecture/链路A-导诊对话.md` §6.5）
- **审核回流 approve 走本流水线（闭环生效唯一机制）**：approve 时写映射台账（dept_mapping，source=feedback）+ 由审核结论**生成合成 chunk**（症状→正确科室的鉴别语料，如"颈肩僵硬伴手指放射性麻木建议首诊骨科，可与心源性胸痛鉴别"；文本由 LLM 生成、管理员预览定稿，见链路 C「审核产出规则」），挂**主科室**的那个「回流补充 · XX科」容器（见下），走本流水线完整入库（切分→向量化→pgvector+ES 双写→术语抽取→白名单刷新）。RAG 检索到合成 chunk 后，同类主诉推荐变对——准确率曲线抬升的全部来源。dept_mapping 运行时不被 RAG 消费，仅作管理端台账（可查"哪些症状补过映射、谁 approve 的"）

**解析与切分（实现定案）**

**格式白名单**：`pdf` / `docx` / `png` 走 DocumentMind；`txt` / `md` 原生读；`html` 走 Tika；**其余扩展名上传时直接拒绝**。
> 收窄白名单不是图省事——**支持但没验证过的格式，是静默的垃圾语料来源**：上传成功、进度条走完、状态"已完成"，然后切出一堆乱码进向量库，没有任何人会发现。而"不支持的格式"会当场报错。两种失败的可见度差着一个数量级。

**上传的校验边界**：**判定权在后端**，前端只做即时提示（没选文件时按钮禁用）；分流按**扩展名**做，名字改错就会走错解析器 → 解析失败 → 一条 `failed` 记录——这个代价可接受（留痕、可重试、白名单很窄），不需要再叠一层魔数判定。
> 为什么不做魔数校验：它防的是"恶意上传"，而这里的上传者是**管理员**（不会故意传 `.exe`，只会不小心选错文件）；而且 `docx`/`xlsx` 都是 zip、魔数一样，判不出细分。**校验的意义是让错误在最早的地方以最清楚的方式出现，不是把坏人挡住**——后者在这个场景买不到。
> **multipart 两条上限必须显式配**（建议 50MB）：Spring Boot 默认 `max-file-size=1MB` / `max-request-size=10MB`，一份带插图的科室文档（2–5MB 很常见）会被直接拒掉，而且这个拒绝发生在 controller **之前**。所以 `MaxUploadSizeExceededException` 必须接进全局异常处理器、回统一返回体（「文件过大，单个文件不超过 50MB」）——**不接的话用户看到一个跟本系统毫无关系的错误页**，排查成本全转嫁给他。

**DocumentMind 的定位**：外部云服务，**经 `llm` 适配层调用**（`llm` 是唯一外部出口），是 pdf/docx/png 的**唯一**解析路径——**不做降级**。
> 理由：降级路径（POI / PDFBox）产出质量不同，会让知识库里混进两种切分风格，而切分质量直接就是检索质量（`chunk_broken` 根因）；且降级路径**平时永远不跑**，只在故障时跑一次，产出的东西没人验证过就进了知识库。不可用即 `failed`（retryable），与 ES 挂掉的行为一致。
> 由此附一条硬规则：**Tika 只接 `html`，不得接 pdf/docx**——它本身就能解析这两种格式，躺在依赖里迟早有人把解析失败的 pdf 丢给它"试试"，那条刚被否掉的降级路径会顺着依赖慢慢爬回来。

**调用形态（实测）**：`submitDocParserJobAdvance` + `setFileUrlObject(InputStream)` **直接传文件流**——不需要 OSS，也不需要 MinIO 对公网可达 → 轮询 `queryDocParserStatus` → 取结果。
> - 状态值 `success`；`processing` 是 **0–100**（不是 0–1），可直接映射 `ingest_task` 的进度
> - 统计字段现成：`paragraphCount` / `tableCount` / `imageCount` / `tokens`
> - 取结果两条路：`getDocParserResult`（`layoutNum` / `layoutStepSize` **分页拉版面块**）与 `outputFormatResult[].outputFileUrl`（下载文件，OSS 签名**有效 12 小时**）。**两条都是读接口，反复拉不再计费**，所以任务号要留着
>   > 分页语义（实测）：`layoutNum` 是**块偏移**（在第几块起）、`layoutStepSize` 是取多少块；结果体**没有总数字段**，"取完了"只能靠"这一页不满 step"判（`queryDocParserStatus` 的段落数是解析计数，不等于版面块条数）
> - **提交必须设 `needHeaderFooter=false`**：实测页眉会被识别成 `type=title` 混在正文最前面，每页的页眉都会变成一个"标题块"，把文档切碎且 `title` 全是页眉文字

**解析产物**：`layouts[]` 版面块，每块带 `type`（`title` / `text` / `table`）、`fontSize`、`pageNum`、`index`、`markdownContent`、`text`。 类型最终随切片写入 `chunk_type`（`title` / `text` / `table` / `figure` / `image` / `formula` / `code` / `header` / `footer` / `unknown`）；历史、非外部识别来源和未映射类型统一为 `unknown`。
> - **类型判定是两步，且类型表按参考实现补全**（2026-09-30）：先按外部 `type` 映射（标题族 `title`/`heading`/`header1`/`header2`、`table`、`figure`/`chart`、`image`/`picture`、`formula`/`equation`、`code`、`footer`、`header`，**顺序即优先级**——`header1` 必须排在 `header` 之前；表外的值一律 `unknown`，不按"看着像"归类），`type` 给不出结论时再回到文字看章节编号（见下）
> - **只有 `TITLE` 与 `TABLE` 改变切分行为**：`figure`/`image`/`formula`/`code`/`header`/`footer` 在切分里都按正文处理。单独建类型是为了**可观测**（`chunk_type` 落三处，能查出"这份 pdf 的图注是不是混进正文了"）与**后续过滤的抓手**（页眉页脚要不要在检索前丢、图片块怎么处理，得先认得出）——**认得出与要不要动是两件事**
> - ⚠️ **为什么要第二步**：`type=title` 只看**视觉格式**（大字号/加粗/居中），而且服务端判定**有波动**。2026-09-30 拿真实解析结果数过：「多级标题测试文档」62 块里 28 个章节标题，服务端认 26 个、**漏 2 个**（`1.1.1.1术语约定`、`4.2.1.1四级`）——**字面样式与认出来了的同级标题一模一样**（14pt / bold / Verdana），调参数解决不了，只能靠本地兜底接住。漏判的后果是边界丢失、切分按长度切、跨小节拼成一片（每块文本都完整，单看一块看不出问题）
>   > 兜底判据（三条各挡一类误判）：**多级阿拉伯编号**（`1.1` 算、`1.` 不算，挡有序列表项）**且编号之后还有中文**（挡 `10.0.1.1`、`114.114.114.114`、`10.0.1.100/24`、`1.2 kg` 这种"整行是个值"）**且 ≤80 字**；`第X章`/`一、` 另外认。**不能用"编号后跟空白"**——DocumentMind 的 `text` 会吃掉编号与标题之间的空格（真实结果是 `1.1编写目的`），按空白判等于没写（2026-09-30 踩过）。**不收「以冒号结尾」**（中文文档里那种短行绝大多数是引导句，误提升会把真正的章节标题顶掉、溯源就丢了）
> - **`chunk_type` 记的是"这一片是什么"**（2026-09-30 起）：`title` = 这一片就是一个小节标题（每个标题块单独成片，content 等于标题本身）、`text` = 正文片、`table` = 表格片。**判"标题有没有被认出来"直接看有没有 `chunk_type=title` 的片**；要知道某片归属哪个小节看 `title` 列
> - ⚠️ **`index` 是页内序号**（实测：第 2 页从 0 重来），阅读顺序键是 **`(pageNum, index)`**。服务端返回的就是按它排好的平铺列表，**不要"防御性地"再按 `index` 单独排一次**——那会把多页文档逐条交错（A1、B1、A2、B2…），而每块文本都完整，单看一块看不出问题，症状只是"召回的内容牛头不对马嘴"
> - `fontSize` 能区分层级（实测 H1=15 / H2=14 / 正文=12），但**切分不需要层级树**（见下）
> - 普通文本块**没有 bbox 坐标**；坐标只出现在表格单元格上

**表格**：返回是**结构化的**——外层块带 `numCol` + `cells[]`，每个 cell 有 `xsc`/`xec`/`ysc`/`yec`（行列网格坐标）、`cellId` 与单元格文本；同时它的 markdown 形态是**完整的 markdown 表格**。**取 markdown 形态作为一整块入 chunk，不参与正文切分。**
> 一行的文本（`| 劳力性胸闷|心血管内科|需与呼吸系统疾病鉴别|`）本身就是完整自洽的语义单元，向量检索能精准命中，而它对应的患者主诉也高度相似。**表格是分诊知识里信息密度最高的部分**——丢掉它等于主动制造 `parse_missed`（解析遗漏）这个已定义的根因。

**切分三层**（每层的触发条件互不重叠：结构切管"有标题"、模型切管"无标题且够长"、递归切管"超长"）：

1. **结构切**：标题块 = 切分边界，`title` = 最近的标题块（标题块的来源是上一步的类型判定：版面类型 + 编号兜底）。**不建层级树**——**切分只需要边界，不需要层级**：`fontSize` 确实给得出层级，但那是"能不能"不是"要不要"，而猜层级猜错只会把内容切得更碎，分诊场景里患者也不会因为脚注少看到"第三章"而更不信这个推荐。`title` **永远来自原文**：它是推荐卡溯源引用要显示的东西（前端设计方案-患者端 §3.1），模型起的标题在原文里根本不存在，溯源就退化成"模型的转述"（即 `structure_fail` 幻觉）
   - **标题块的文字自己单独成一片**（`chunk_type=title`，2026-09-30 定案，**已真实环境验收**：多级标题测试文档 62 块 → 57 片，其中 28 条标题片）：外部组件既然认出这是标题，这份识别结果就该落进切片里——**可查**（不用再从 `title` 列反推识别情况）、**可检索**（"四、响应等级表"本身就是完整语义单元）、**不丢字**。标题片与表格片一样**整块入片、不过递归切**（标题是一个语义单元，切开就不再是标题片了）
     - 代价是**切片数明显变多**、标题片很短，检索时可能同时召回标题片与正文片。**已定案不降权、不过滤**：那是召回冗余不是召回错误，降权要先有真实误召回的案例
   - `title` 列负责**归属**：其后的正文片/表格片带着最近标题；**正文里不重复**这段文字（向量化文本本来就是「标题 + 正文」，见 `ChunkIndexService.embeddingText`，标题片也不再重复拼一遍）
   - 表格块**作为一整块入 chunk，不参与正文切分**：一行「症状｜科室｜鉴别方向」本身就是完整自洽的语义单元
   - 结构切给不出标题时（整段落在任何标题块之前，或全文没有标题块），`title` **回落文档标题**——它不是模型编的（上传时管理员填的、与原件同名），溯源指向仍然真实；留空则推荐卡的「判断依据」会是一条没有出处的引用
2. **模型切**：只在**没有标题块**的部分出场（结构切给不出边界时），**只给边界、不给 title**。触发条件是"**无标题但文本干净**"，不是"质量低"——质量低意味着解析出了问题，模型拿到的也是烂文本，**拿最贵的手段去处理最该被拒绝的输入**；触发长度由 `chunk.model.min.length` 定（低于它，递归切就够）
   - 结果必须过**产出校验**：拼接后是否覆盖原文（丢字检测）、块数与原文字数是否匹配、每块字数是否落在区间内
   - 校验不过 → `failed`，**不是** `done` + 0 片
   - 不能寄望"模型切不出来就返回空"：**模型不会说自己切不出来**，它会编一个看起来合理的切分——`structure_fail` 根因的修复动作原文写的就是「**输出校验**与重试机制」，不是"相信模型认输"
3. **递归切**：**无条件兜底**，任何超长块必走。它不是"超过配置字数才考虑"的可选策略，而是必执行的一层——否则会出现"三个策略条件都不满足"的**无策略状态**（纯 txt、无小标题的 pdf 都落在那里）。按分隔符优先级逐层降级（段落 → 行 → 句 → 分句 → 词 → 硬切），每层贪心合并到尽量靠近目标长度

> **实现顺序是「结构切 → （无标题部分）模型切 → 递归切兜底」，与上面"三层自上而下"的字面顺序不同**（2026-09-26 实现时定）：递归切若先无条件把长文本切碎，模型切面对的就已经是碎块，"给边界"这件事无从谈起——模型切正是用来**替代**结构切给不出边界的那个角色，必须在机械切分之前出场。三条硬约束（递归切无条件兜底、模型切只在无标题处、模型切只给边界）都仍然成立：模型切产出的块若仍超长，照样过递归切。

**切分参数**（目标长度 / 上限 / 各层触发条件）走 `sys_config`。这不是可选项：链路 C 根因表里 `chunk_broken` 的修复动作原文是「对该文档单独重新入库（**调整切分参数**）」——参数写死在代码里，这个修复动作就是**空的**：你能看出切得不好，但改不了、也重跑不了。

**失败分类**（`kb_doc.fail_type`）：判据压成一句「**再跑一次可能就好了**」。这个分类只有一个用途——决定管理端「重新处理」按钮给不给。
- 外部依赖故障（超时 / 限流 / 欠费 / 5xx）→ `retryable`
- 输入本身有问题（文件损坏 / 加密 pdf / 打不开 / 格式不在白名单）→ `fatal`
- **拿到了结果但不合格**（解析产出异常、切分校验不过）→ `retryable`：失败发生在**依赖的返回值**上，是依赖的问题不是输入的问题；且「重新处理」是**给人用的决策入口**，人看一眼日志就分得清是加密件还是服务端抖动——宁可多给按钮，也不要把文档卡死在不可重试的死路（那只能删了重传）

**`fail_reason` 写人话，原文只进日志**：解析失败时 DocumentMind 抛出的异常里有 OSS 路径、STS token 片段、请求 id、内部错误码，**不能直通管理员**——`fail_reason` 的读者是**要决定下一步做什么的人**，不是要读上游响应的人。做法沿用链路 A 修过的那个先例（异常原文白名单式映射）：每个已知失败类型对应一句**说清下一步**的话（「解析服务暂时不可用，请稍后重试」「文件无法打开，请确认不是加密件」「解析产出异常：3 页仅抽出 52 字，请检查原件」），带数字的判据要写进去——它们是可行动的。原文进 `logs/guide.log`，想排查的人去那儿。
> 三个字段、三种读者，别混：`fail_type` 给**程序**（决定「重新处理」按钮给不给）、`fail_reason` 给**要动手的人**（说清下一步）、日志原文给**要排查的人**。
> 这条是 2026-09-26 补的**教训**：三个 catch 当时都只留了人话、**谁也没打印 cause**，于是用户问「为啥不可用」时答不上来，只能从头复现一遍。笼统是给人看的**结果**，不是丢掉病因的**理由**——两者必须同时留下。

**失败的原因要分类，但只认能确定的那类**：连接层异常（`SocketTimeout` / `Connect` / `UnknownHost` / `NoRouteToHost`，沿 cause 链找）→ 「连接解析服务失败（网络中断或超时），请稍后重新处理」；其余保持笼统的「解析服务暂时不可用」。管理员由此分得清**"等一会再试"和"去查密钥"**。**只认连接层、不猜别的病因**——猜错比说得少更坏。

**提交失败不自动重试（2026-09-26 明确决定，别再"顺手"加上）**：轮询那条路是容错的（网络抖一下只记 WARN、下一轮再来），提交这条路一抖就判失败——**这个不对称是有理由的**：轮询是读接口、重试免费；提交会创建解析任务，**重试有概率重复计费**（第一次其实传完了、只是响应丢了）。判据同上：钱与体验的取舍交给**人**——管理端点一次「重新处理」即可，代价是明确且可见的。

**术语抽取是旁路**：LLM 批量实体抽取失败只记 WARN，chunk 照常入库（`medical_terms` 空数组）。判据同 `CLAUDE.md` §2「埋点旁路，不阻塞主流程」——白名单是**防误杀**的辅助，缺了它最坏是误杀**风险**上升（白名单由管理端维护，见 `docs/architecture/链路A-导诊对话.md` §6.5），而入库失败是**内容彻底进不来**。**因此这一块可以先不做**，流水线照样跑通。

**异步编排是两段式**（解析是外部服务、一份件可能几分钟，不能让线程池干等）：
1. 线程池只做「**提交**」——拿到外部任务号就结束，把它记进 `ingest_task.external_job_id`
2. `@Scheduled` 定时扫 `status=running 且 stage=parse` 的任务去**轮询**（`processing` 映射进度），完成后**投回线程池**做「读结果 → 切分 → 入库」

> 为什么不让线程池线程一路 sleep 轮询到底：① 一个文档占一个线程数分钟，批量上传时后面的干等；② **JVM 重启会丢掉正在轮询的任务**——线程死了，`ingest_task` 永远停在 `running`，变成没人管的僵尸任务。而"权威状态 + 可恢复"正是任务表存在的**全部理由**，选同步轮询就等于承认它只是个展示用的进度条。

**第二段可重入**：它只依赖 `docId` 与任务号，块不在手上时自己取（外部按任务号拉——**读接口不重复计费**；本地格式重新下载重解，不花钱）。所以 JVM 重启后任务能接着跑，而不是卡在半路。

**卡住的 split/embed 任务由轮询判中断**：进程在切分/入库中途退出，线程没了，任务永远停在 `running`——不处理的话这份文档**既跑不完、又因为「同一文档同时最多一个 running 任务」而重跑不了**（死胡同）。所以扫描时顺带把「仍在 running、阶段已是 split/embed、且超过总超时没动过」的任务标 `failed(retryable)`，原因写"入库中断（服务重启或超时），请重新处理"，让人能点重新处理。

**扫描节拍固定、轮询间隔可配**：`@Scheduled` 的固定间隔在启动时就定死、改不了，而**每个任务距上次轮询多久**是运行期可判的（靠任务的 `updated_at`）。于是节拍只当心跳（`guide.ingest.scan-interval-ms`，默认 5s），真正的轮询间隔（`ingest.poll.interval.seconds`）与总超时（`ingest.parse.timeout.minutes`）走 `sys_config`、改完立刻生效——**扫得勤只多几次数据库查询，不会多发一次计费的请求**。
> 单次轮询失败（网络抖动）不判死：只记一条 WARN，下一轮再来；真正的兜底是超时判定。**一次网络抖动就把文档判失败，会让管理员白重新处理一遍（还白付一次解析费）**。

**进度按阶段显示真实量，不拼成一根连续的条**：

| 阶段 | 屏幕上的字 | 数据来源 | 耗时量级 |
|---|---|---|---|
| `parse` | 解析中 37% | DocumentMind 的 `processing`（0–100） | **分钟** |
| `split` | 正在切分 | 无进度可显示（本地瞬时） | 毫秒 |
| `embed` | 写入 38 / 42 | `ingest_task.done / total` | 秒 |
| `done` | 已完成 | — | — |

> 为什么不做一根 0–100% 的条：那要把"解析的百分比"和"写入的计数"映射到同一根轴上，而两段耗时**差着数量级**——必须拍一个分段比例，那个比例在任何一份文档上都不会对。经典症状是"卡在 60% 不动"，人看到的是"卡死了"。
> **它直接影响行为**：进度条几分钟不动，管理员会以为没点上、再点一次——那正是「同一文档同时跑两次入库」的触发条件。显示真实量（「解析中 37%」）让人知道它活着且在动。
> 同理 `kb_doc.chunk_total` 在解析阶段是 **NULL**——**切出多少片是切分的结果，解析阶段不可能知道**。任何形如「15 / 38 · 解析中」的显示都是编出来的（管理端假数据里就有这么一条，做真页面时要改掉）。

**模块归属**：解析编排（格式 → 解析器）与切分策略放 **`kb`**（属"文档变切片"的领域逻辑，回流合成 chunk 可复用）；`async` 只管线程池与任务表编排；DocumentMind 客户端在 **`llm`**；Tika 依赖加在 **`kb`**。
