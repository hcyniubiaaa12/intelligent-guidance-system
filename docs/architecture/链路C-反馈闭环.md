# 链路 C：反馈闭环链路（差异化核心）

> 本文是《总体架构与链路设计.md》（仓库根，**总册**）的分册之一。全局约定——分层视图与设计原则、模块职责边界与依赖方向、部署形态、已定参数汇总——都在总册；动本册前先读总册 §1 / §3 / §5。

### 链路 C：反馈闭环链路（差异化核心）

```
患者端三阶段                         后端（比对+聚合+审核）         管理端
───────┬───────────────────────────┬───────────────────────────┬──────
  ① 推荐卡片渲染 ── result_view ──→ │ 埋点落库                    │
  ② 模拟挂号页选科室 ─ sim_register→│ 埋点落库                    │
  ③ 挂号成功确认 ── register_success│ 埋点落库                    │
       │            (deptId)      →│ ④ actual_dept 写入导诊记录  │
       │                            │   （挂号确认接口同事务写入   │
       │                            │    guide_record，非 feedback）│
       │                            │ ⑤ 比对 top1_hit/top3_hit   │
       │                            │ ⑥ 聚合归桶(整点/手动):      │
       │                            │    错误样本按方向聚类        │
       │                            │    分类型阈值升级待审核      │
       │                            │ ⑦ 看板实时反映准确率        │
       │                            │                          │ ◄── ⑧ 审核队列
       │                            │                          │ ⑨ approve(主科室+交叉科室)
       │                            │ ◄─────────────────────── │
       │                            │ ⑩ 写映射台账+合成chunk走链路B │
       │                            │ ⑪ 记录变更日志            │
       │                            │ ⑫ 看板准确率变化（闭环生效）│
```

**对齐点**：
- **模拟挂号 = 产品引导、非数据保证**：出结果后引导患者完成挂号确认，但患者可以不挂（流失）——会话保持 ongoing、actual_dept 为空；准确率口径 = **已确认记录**（actual_dept 非空）的命中率，不做 100% 完整性假设
- **新主诉判定（2026-10-14 改口径：由"双信号"收成"单信号"）**：**只有 `closed`（挂号成功）之后**，患者的下一条输入才 = 开新会话、新主诉；`has_result=1`（已出结论）**不再是**边界——出结论之后患者仍可在同一会话里补充症状、继续追问，判定信号仍是状态机字段，不做模型语义判断。配套三条：出卡后 `ask_round` 归零（语义改为"距最近一张卡已追问几轮"）、`forceConclusion` 加 `!hasResult`（结论后不再强制造卡，否则补充后兜底出的低置信度卡会挡住患者要挂的那张——前端只有最后一张卡能挂号）、一条会话可多张卡 ⇒ 回放改多卡、统计按**患者实际挂号的那张**。旧口径（已出 result 或已 closed 都算边界）已作废。
- 三个埋点阶段的页面归属：推荐卡片页 / 模拟挂号页 / 挂号成功页——缺一不可，前端流程必须串通
- `actual_dept` 只认 register_success 触点的 deptId，且由**挂号确认接口同步写入** guide_record（与 top1_hit/top3_hit 同事务）；未挂号记录 actual_dept 为空、不参与准确率计算；前面阶段（result_view / sim_register）与 track_event 全部触点只作时间过程信号（漏斗/耗时分析），非准确率事实来源
- track_event 埋点保留旁路落库，仅服务看板漏斗/耗时/交叉分析，不参与准确率计算
- **主从关系**：准确率唯一依据 = actual_dept（行为比意见可信）；**不做卡片 👍/👎 主观评价**（埋点三触点的漏斗/耗时分析已足够覆盖辅助分析，主观评价不参与任何统计）
- 聚合口径：仅统计"已反馈且未命中 top3"的记录（真正的系统错误）；**top-1 未命中但 top-3 命中视为"排序精度问题"，不进回流**（患者本来就在推荐列表里选的，不算系统错）
- 分类型升级阈值：top-3 未命中（错误样本信号）升级阈值低（默认 3 次）；已审核模式的新样本自动归类，不重复升级
- 闭环生效的可观测信号：**准确率趋势曲线在审核确认后出现抬升**（答辩/演示的关键证据）

#### 错误模式聚合算法（两级归桶，每小时整点 + 管理端可手动触发）

**设计哲学**：聚合是召回机制（宁可混、不能漏——漏了问题永远不升级，混了只是多审一条）；人工评审是质量闸门——聚合只负责把候选升级到管理员面前，**写回知识库的唯一路径是人工 approve**。

```
输入：已挂号反馈 且 top3_hit=0 的新记录（aggregated=0 增量标记，与聚合同事务置位防重复计数）

第一级 · 精确归桶（规则，零成本）：
  症状归一化（去口语词/标点/量词，固定词典）→ 与【同方向】桶的精确键比对 → 命中即归入
第二级 · 语义归桶（向量，处理同义不同形）：
  精确未命中 → 症状文本 embedding 向量化 → pgvector 中在【同方向】桶的锚点向量里
  找余弦相似度最高者（cluster_bucket_vec，direction 作为 SQL 过滤条件）
  → 相似度 ≥ 阈值（默认 0.85，可配）归入该桶；否则开新桶，本样本作锚点（锚点固定不漂移，
  开新桶时向 pgvector 写入锚点向量，归 feedback 模块直写）

升级：count ≥ 阈值（top3 未命中默认 3 次，键 `cluster.upgrade.count`）且 status=monitoring → pending 进待审队列
成员：归桶成功时把桶 id 写进 guide_record.bucket_id——同方向可有多个桶，审核按桶取记录，不按方向反推
```

**关键规则**：

- **方向预筛**：语义匹配只在（推荐科室, 实际科室）相同的候选桶内进行——方向是精确字段先锁死，歧义空间小
- **分类型口径**：top-3 未命中（错误样本信号）才进聚合；top-1 未命中但 top-3 命中 = 精度问题，不进回流
- **幂等**：已终态（approved/rejected/dismissed）桶的新样本只计数、绝不**自动**重新升级；管理员可对终态桶发起「修正重审」回 pending（人工纠错，不受幂等约束，见「审核产出规则」）
- **低置信度分流**：推荐 top1 置信度 < 0.5 → 不进聚合，进盲区榜
- **不调 LLM**：聚合是批量确定性活，规则 + 向量足够；语义歧义（同病不同表述、一词多义）交给人工审核兜底——审核看代表样本原文，不看归一化串
- **逐条独立事务**：扫描（`scanPending`）与逐条归桶（`clusterOne`）是两个方法，由 `AggregationScheduler` 串起来。归桶的「桶计数 +1」与「记录写上 `bucket_id`」必须同事务——单条失败整条回滚，记录留在 `aggregated=0` 等下次扫描。**循环不能放回 service 内部**：service 直调自己的方法走的是原始对象而非 Spring 代理，`@Transactional` 直接失效，失败那条会留下「桶计数加了、记录没标记」的半截状态，下次扫描再算一遍，桶计数就虚了
- **手动触发与定时共用一把锁**：整点任务没法用来演示与排查，管理端审核页有「立即聚合」（`POST /api/admin/review/aggregate`）；它与 `@Scheduled` 共用进程内 `AtomicBoolean`，正在跑时返回 6004，不并发跑两遍——并发会把同一条还没标记的记录算两遍，同样是计数虚增
- **「现在有没有活」是可观测的**：审核页顶部**常驻**一行提示，数字来自 `GET /api/admin/review/pending-records/count`（`ClusteringService.countPending()`）。它与聚合真正会扫到的集合**同源**——两条路共用同一份查询条件（`aggregated=0` 且 `actual_dept` 非空 且 `top3_hit=0` 且 `low_confidence=0`），不各自抄一份，避免改了一边忘了另一边。路径用 `records` 不用 `samples`：词表里「样本」是**桶内代表样本**，这里是还没归桶的导诊**记录**
- **提示行四态，压成两态会骗人**：`有 N 条`（左侧竖条转 coral）/ `当前没有待聚合的错误样本` / `正在读取…`（首次进页） / `暂时取不到`。「加载中」与「取不到」都不能折叠成「没有」——那样界面上三件事长得一模一样，人无从判断该不该点那个按钮
- **两个数字对不上是正常的（进度口径 ≠ 结果口径）**：提示行说的是**进度**（还有多少条没归桶），聚合后的提示说的是**结果**（本次真正归进桶的条数）。归桶时抽不出主诉的记录会被标记 `aggregated=1`、`bucket_id=null` 后跳过（主诉不会自己长出来，不标记就会每小时重扫一遍），所以「待归桶 N 条」≥「已归桶 M 条」；前端在 `M < N` 时把差额明说出来（「另有 X 条因无法提取主诉已跳过」），不让管理员以为系统漏算
- **前端超时单独放宽**：聚合是同步跑批（循环内每条记录还可能调一次 embedding），比普通 CRUD 慢得多；它和其他请求共用同一个 axios 实例，但单请求超时放宽到 120s。否则实例级的 15s 会先掐断请求——后端其实归桶成功了，用户却看到失败，再点一次正好撞上 6004，前后矛盾

#### 审核产出规则（approve 的完整机制）

**审核动作（管理员在审核页对 pending 桶操作）**：

- 给出**主科室**（必需）+ **交叉科室**（可增删）。交叉科室 = 该症状还需一并考虑、需鉴别的其他科室——回答"还可能是什么"，不是"系统当时误判成了什么"
- 交叉科室**预填 = 桶方向 {推荐科室, 实际科室} − {主科室}**（集合差一条规则，无特例）；预填只是建议值，管理员可增删
- 科室选择器**包含停用科室**（带"已停用"标记）——停用仅入口生效，审核是知识层动作、与运营启停解耦
- 合成 chunk 文本由 **LLM 生成**（经 llm 适配层，输入 = 症状原文 + 主科室 + 交叉科室）→ **管理员预览可编辑定稿** → 确认（LLM 失败用模板兜底）——守住"写知识库唯一路径是人工 approve"的完整闸门

**确认产出（一个动作，两样产物）**：

- 映射台账：键 = **(症状原文, 主科室)**——同键合并（交叉科室取并集）、异键开新行；source=feedback。同一症状可因不同方向的桶被审出多个主科室，各占一行
- 合成 chunk：挂**主科室**的「回流补充 · XX科」容器，走链路 B 流水线（见 `docs/architecture/链路B-知识库入库.md` 对齐点）

**合成 chunk 挂到哪个科室——按科室分容器**（2026-09-26 定）：
回流语料讲的是"症状 → 某个科室"的鉴别，而「一份文档 = 一个科室、切片继承文档的科室」是链路 B 的硬规则（`kb_doc.dept_id` 与 `kb_chunk_vec.dept_id` 都是 `NOT NULL`）。两者一撞就必须回答：**那个容器属于哪个科室**。
做法是**每个科室一个系统级容器**（如「回流补充 · 心血管内科」），approve 时合成 chunk 挂到 `review_task.main_dept_id` 对应的那个。
> 为什么不建一个全局容器：那样它必须凭空编一个**不是真科室的科室**挂在科室蓝本里，而科室表是**挂号范围与统计的口径**（科室名还全库唯一），凭空多出的一条会污染管理端与看板的科室口径；更要紧的是，全部回流语料都归口到同一个虚拟科室名下，**"哪个科室被回流补过、补了多少"就再也看不出来**——而按科室分容器恰好让这件事一眼可见，停用某科室也只影响它自己那一份。
> ⚠️ **纠正（2026-10-03）**：此处早先写的理由是"停用那个虚拟科室就会把全部回流知识一起拦掉"——**那个说法不成立**。停用科室的切片仍可被召回、也可被引用为判断依据，停用只是让**该科室不可被推荐**（见 `docs/architecture/链路A-导诊对话.md`「科室校验」的注）。按科室分容器的真正理由在**归口与可观测**，不在"防止被拦掉"。
> 按科室分之后整条链自洽，不需要任何例外分支，且管理端一眼能看出"哪个科室被回流补过、补了多少"——比一个混在一起、不知道是什么的容器信息量大得多。

**回流容器的三个字段约定**（`kb_doc` 对它有 `NOT NULL` 约束，但不适用普通文档的值）：
- `file_url` 填标记串 `feedback://synthetic`（种子语料已有 `seed://` 这个先例——**它不是文件，但也必须占住这个字段**）
- `title` = 「回流补充 · 心血管内科」（科室名）
- **懒创建**：某科室第一次 approve 时才建容器，不预先给每个科室建空壳——否则管理端列表里会挂着 7 条永远没内容的记录
- **操作列没有「重新处理」**（没有原文件可重跑），只有「查看切片」
- 落库边界：台账 + 桶状态**同事务**；chunk 入库**异步**，失败随合成文档在知识库页可见。**没有「重新处理」**——回流容器没有原文件可重跑（合成文本是 LLM 生成的），它的重试路径是**重新 approve**：终态桶走「修正重审」回 pending、再审一次，而"让人再看一遍生成的语料"对这种情况正是该做的事

**否决（不产出）**：

- **驳回（rejected）**：审过否定——人看过并判定"不是系统错"（如患者挂错、样本误聚合）。逻辑：回流只修错，没错可修就关桶
- **忽略（dismissed）**：没审就关——测试/演示数据、重复桶等噪声的清理动作

**纠错（人工闸门有权改自己）**：

- 终态桶（approved/rejected/dismissed）可发起**修正重审**：回 pending 重走审核——重新生成预览、按键规则处理台账旧行（旧行删除/新行写入）、替换合成 chunk
- **终态列表支持按状态多选筛选**（`GET /api/admin/review/terminal?statuses=approved,rejected`）：三种终态混在同一张表里，不筛就得靠肉眼翻。**空选 = 三种全看**（不传或传空都按不过滤处理）；状态编码走 URL，因此由 `BucketStatus.fromCode` 自己解析（Spring 默认枚举绑定只认常量名 `APPROVED`，认不出小写编码）。**认不出来的编码直接报 PARAM_INVALID，不静默忽略**——静默忽略会让一次打错的筛选悄悄退化成"不过滤"，人还以为筛过
- 边界：幂等规则只约束**自动**升级（防聚合反复翻烧饼）；人工重开是显式动作，不受限

#### 证据快照与根因归因（链路 C 的配套诊断能力）

**为什么需要**：全错（top-3 未命中）的根因不一定是"知识库缺内容"。知识库规模大时，主要矛盾在**离线入库/检索层**（切分破碎、解析遗漏、检索失败）和**回答层**（模型没用检索内容、结构化失败）。只靠"补知识"治标不治本，必须先归因、再对症修复。

**证据快照**：每条导诊记录留存 RAG 证据快照（JSON），让审核时能还原"系统当时看到了什么、怎么答的"：

```json
{
  "retrieved": [{"chunk_id": "12", "title": "骨科科室介绍", "score": 0.71, "rank": 1}],
  "retrieved_query": "（查询改写后的实际检索串；未改写时等于患者原话）",
  "model_cited": [1, 2],
  "profile": {
    "text": "（待注入模型的健康档案文本；为空 = 本轮无档案）",
    "query": "（档案检索用串，进检索扩容；为空 = 无）",
    "content": {"gender": "male", "ageRange": "45-59", "historyTags": ["2型糖尿病"],
                "historyOther": null, "medicationTags": [], "medicationOther": null,
                "allergyTags": ["青霉素类"], "allergyOther": null}
  },
  "prompt_snippet": "（实际送入模型的上下文摘要）",
  "model_output_raw": "（模型原始输出）"
}
```

> `profile` 是**健康档案快照**（2026-10-03 加）：档案参与召回与生成，就是"系统当时看到的输入"的一部分。三样都要——`text` 是模型看到的背景、`query` 是检索用到的串、`content` 是**患者当时填的结构化档案**（审核时能看清勾了什么、写了什么，而不只是加工后的文本）。**只写不读**：回放与审核读的就是这一份，**绝不**在读取时回查当前档案补全——档案可变而导诊记录不可改，实时回读等于把历史改掉（患者今天删掉"糖尿病"，旧记录的推荐理由就当场失真）。无档案 ⇒ 节点为 `null`（老记录无该节点），回放侧用 `path()` 取值、不炸。

> `score` 是精排（rerank）相关度；精排降级（退化为 RRF 顺序）时该值为 RRF 分（量级 ~0.01），日志有 WARN 可查。

**归因交互（管理员审核页）**：展示完整证据链后，管理员用**预定义选项多选**标注根因（不做自由文本填空，保证统计口径统一）。归因**逐条标注**：写在每条代表样本上，**不做桶级一键套用**——那会把桶内每条记录整份覆盖成同一组根因，包括管理员已逐条改过的；同方向一个桶里的样本未必是同一成因，一刀切等于用统计口径覆盖事实判断。归因与 approve/驳回是同一页上的**两个独立动作，互不代劳**（驳回桶不改归因，标归因不改桶状态）：

| 存 key | 显示名 | 含义 | 修复方向 |
|--------|--------|------|---------|
| `chunk_broken` | 切分破碎 | 语义被拦腰切断、标题与正文分离 | 对该文档单独重新入库（调整切分参数） |
| `parse_missed` | 解析遗漏 | docx 表格/格式内容被丢弃 | 修复解析器后重入库 |
| `retrieval_fail` | 检索失败 | 内容在库但未召回（表述不匹配/Top-K 不足） | 调检索参数（混合检索、扩大 Top-K） |
| `mapping_missing` | 局部映射缺失 | 交叉症状映射没有覆盖 | 补映射（回流） |
| `model_ignored_retrieval` | 模型未依据检索 | 检索到了但模型凭常识答 | Prompt 版本迭代 |
| `structure_fail` | 结构化失败 | JSON 解析异常、幻觉科室 | 输出校验与重试机制 |
| `patient_wrong` | 患者挂错 | 非系统责任 | 标根因（看板统计信号）+ 驳回桶（审过否定）——两个动作都要做；看板 miss 口径排除已标此项的记录 |

**归因可更新**：归因结果允许事后修改（单选变更多选、错误标注纠正），每次修改记录操作人与时间，并追加写入 `root_cause_log`（修改历史留痕，不覆盖，纯审计不参与聚合）；看板"**错误根因分布**"基于 `root_cause` 最新归因实时聚合——分布图直接指示下一步动作（检索层占比高 → 调参；回答层占比高 → 修 Prompt）。

**存 key、显示 label（实现定案）**：`causes` 存上表左列的小写 key，页面显示中列的中文名——文案可改、口径不动。字典唯一定义源是后端 `feedback/enums/RootCauseKey`（key 由常量名派生，防漂移）；后端不校验存量值，字典外的 key 原样显示并记 WARN（统计可以少一行解释，不能把数据藏起来）。`patient_wrong` 是唯一带后端语义的一项：看板准确率口径靠它排除记录。
