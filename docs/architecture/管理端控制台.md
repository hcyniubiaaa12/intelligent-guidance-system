## 7. 管理端控制台（运行时配置面）

管理端页面壳与视觉（冷靛控制台 方案 B）已定稿。本节记的是管理端的**设计口径与边界**：数据从哪来、哪些能改、改完何时生效、越不过哪条线——接口明细（路径/字段）按文档定位仍搁置，以各节「落点」里点到的 controller / service 为准。

### 7.1 LLM 配置页

**模型接入信息（只读）**：
- 模型名 / base-url / embedding 维度来自 `application.yml` 的 `llm.*`；**API Key 来自 `application-local.yml`，不进库、不出后端**——接口只回"是否已配置"的布尔位，**不回值也不回掩码串**
- 在线改模型或密钥这条路刻意不做：一旦允许写库，密钥就进了数据库备份与审计日志；改模型改配置重启

**运行时参数（可改，白名单制）**：
- 受管键、类型、取值范围、默认值、说明全部写在代码侧（`SysConfigAdminService` 的 `ParamSpec`），页面只能改这些键的**值**——不让前端决定能写哪些配置，否则字典表会被塞进任意键，或以"页面上有输入框但没有任何代码读它"的形式产生假配置
- 受管键就是管理端能改的**全部范围**，共 **17 项**（`ParamSpec` 白名单），按分组各归各的面板：**LLM 配置页 8 项**（`retrieve.top.k` / `retrieve.top.n` / `chat.ask.max.rounds` / `cluster.bucket.threshold` / `guide.low.confidence` / `profile.tag.max` / `profile.text.max` / `profile.text.total.max`）、**敏感词处置 5 项**（用户管理页「处置规则」）、**知识库页 4 项**（`ParamGroup.KB`：切分三档 `chunk.target.length` / `chunk.max.length` / `chunk.model.min.length` + 术语人工审核开关 `term.manual.review`——审核开关与"哪些词被抽出来"同页，见 §7.3）。**切分三档的页面现状如实标注**：后端 `GET/PUT /api/admin/kb/params` 端点已就绪（`ParamGroup.KB`），但前端知识库页目前只渲染并改写 `term.manual.review` 一项，**切分三档在页面上还没有输入框**（改库即生效：60s TTL / 保存即 refresh）；补输入框是增量，别把它读成"已支持"。**「追问升级阈值」一项已移除**——它从建表起就没有任何业务代码读，与 `chat.ask.max.rounds` 语义重叠而非互补，留着就是"页面上有输入框但没人读"的假配置。**库里那行数据也已清掉**（2026-10-17：代码零引用，留着只会让人误以为它还有作用；`sys_config` 现为 19 行，与初始化脚本的种子数量一致）
- 后端按类型二次校验（int 范围、小数 0–1、布尔只认 true/false），前端控件只是提示，**不信任前端**；不在白名单的键直接拒绝（错误码 2008）

**保存语义（实现定案）**：
- **先全量校验、再统一写入**——"有一项非法则一项都不落库"是校验阶段的自然结果，不依赖事务回滚
- 写完调 `SysConfigService.refresh()` 让进程内缓存**立即**失效，不等 60s TTL；清缓存必须发生在所有写操作**之后**，否则别的线程会在提交前的窗口期用旧值把缓存重新填上
- 值缺失时回落到代码侧默认值（首次部署无需先灌 sys_config 就能开页面）

**连通性探测（人工触发，同步返回）**：
- 三路各发一次最小请求：对话一句问候 / 一条文本向量化 / 一对候选精排；**探测不走 SSE 线程池**，避免占用在线导诊线程
- 每路独立兜异常，一路失败不影响其余两路结论；向量维度与配置不一致单独判失败（提示换模型需重建向量）
- 失败原因**先按配置里的密钥做替换再截断**：上游响应体可能回带 Authorization 头，直出等于把 Key 送到管理端页面上；截断防止一串上游响应体糊满页面

**落点**：`admin/controller/LlmConfigAdminController`（`/api/admin/llm/{models,params,probe}`，仅 ROLE_ADMIN）→ `auth/service/SysConfigAdminService`（参数读写）/ `llm/service/LlmDiagnosticService`（模型信息与探测）

### 7.2 数据看板页

**准确率口径（后端统一算完再下发，前端只负责显示）**：
- 分母 = 已确认挂号（`actual_dept_id` 非空）**且**非低置信度 **且**未被标注「患者挂错」的导诊记录
- 三条排除各有出处：未挂号没有事实可依（模拟挂号是产品引导、非数据保证，不做 100% 完整性假设）；低置信度进盲区榜、不参与准确率统计；「患者挂错」是归因表里明确的"非系统责任"（见 `docs/architecture/链路C-反馈闭环.md` 根因表）
- 分子 = `top1_hit = 1`（Top-1 命中率）/ `top3_hit = 1`（Top-3 命中率）
- **样本为 0 时显示「—」而不是 0%**：0% 会被读成"全错"，与"还没有数据"是完全不同的两件事
- 环比 = 近 N 天 vs 前 N 天，给的是**百分点差（pp）**；上期无样本时明说"不可比"，不伪造成一个数字

**每日趋势（命中构成）**：
- 与 KPI 同一口径（已反馈集合），按 `DATE(created_at)` 分组：命中 = `top3_hit=1`，未命中 = `top3_hit=0`——Top-1 与 Top-3 之间的差（排序精度）由 KPI 卡体现，两段堆叠图不表达第三态
- 没有数据的日期**补 0**，不能让图错位；柱高按窗口内最大值归一化并留 20% 余量（真实日量可能远超 100 条，直接当百分比会溢出容器）

**错误根因分布**：
- 数据源 = `root_cause` 的**最新归因**（可事后修改；`root_cause_log` 只做审计、不参与聚合）；一条记录可标多个根因 → 按**标注项**计数、降序，百分比 = 该项数 / 全部标注项数
- 库里存**小写 key**、下发**中文名**：字典唯一来源是 `feedback/enums/RootCauseKey`（见 `docs/architecture/链路C-反馈闭环.md` 的选项表）；后端不校验存量值，字典外的 key 原样显示并记 WARN
- `patient_wrong` 是唯一带后端语义的一项——它决定准确率口径排除哪些记录；判定用 LIKE 粗筛后**再按数组元素精确比对**（避免 `patient_wrong_pending` 这类新 key 被子串误伤）
- 表为空时页面显示空态并指向审核页（根因由审核页标注），不是显示 0 分布

**最近导诊记录**：
- 主诉摘要 = 该会话的**第一条患者消息**（按页批量查一次，不在循环里回表）；截断 40 字
- 科室名用 `dept` 表直查而不是 `DeptService.listEnabled()`：停用科室的历史记录也要显示得出科室名
- 结果列四态：未反馈（`actual_dept` 为空）/ top-1 命中 / top-3 命中 / **未命中**——top-1 未中但 top-3 中属于**排序精度问题、不是系统错**（与链路 C 的聚合口径一致），不显示成"未命中"
- 置信度为 null（模型未给合法值或兜底科室）显示「—」，不显示 0%

**落点**：`admin/controller/DashboardAdminController`（`/api/admin/dashboard/{overview,records}`，仅 ROLE_ADMIN）→ `stats/service/DashboardService`（纯读聚合，不写业务表）

### 7.3 知识库管理页

四个 tab，每个 tab 对应一类**可维护的领域数据**（页面不是只读报表：科室与术语都是能改就即时影响线上行为的）。

| tab | 数据 | 能改什么 | 改完何时生效 |
|---|---|---|---|
| 科室蓝本 | `dept`（含停用）+ 文档数/切片数 | **新增** / 改名 / 位置 / 简介 / 启停 | 立即（挂号的科室范围与推荐校验都直查此表） |
| 文档入库 | `kb_doc` + 最近一次 `ingest_task` | 上传 / 重新处理 / 删除 | 异步（看进度） |
| 映射台账 | `dept_mapping` | **只读** | — |
| 术语白名单 | `medical_term`（含停用 / 含模型抽取候选） | **新增** / 编辑（词面 + 类型） / 删除 / 启用 / 停用 / **按来源筛选（人工维护 / 模型抽取）** / **「待确认 N · 全部启用」** | 立即（`MedicalTermService.refresh()`，不等 60s TTL） |

**进度显示按阶段给真实量**（`kb_doc.status` + 最近一次任务的 `stage/total/done`）：「解析中 N%」（N 来自外部服务）→「正在切分与提取术语」（切分 + 一次旁路术语抽取，两段都没有数字——切出多少片是切分的结果，抽取也不是可线性推进的量）→「写入 x / y」（自己的计数）→「已完成 · N 片」。**不给前端任何推算出来的总进度**，理由与写法见前端设计方案-管理端 §3.8「进度条不许撒谎」。
> 文档行的进度与状态**取自两份数据**：`kb_doc` 给当前态、`ingest_task` 给这次运行的阶段与计数。页面不自己拼接推断——它没有推得出来的东西。

**术语白名单 tab 的三件事（2026-10-17 入库即抽取接通后）**：
- **来源筛选**：`source=manual / llm_extract`，与关键词、启用状态组合下到同一个分页查询里。**「待确认」的严格口径是 `source=llm_extract && enabled=0`**——只用 `enabled=0` 会把管理员**故意停用**的词也算进去，那个数字会骗人，一次「全部启用」还会推翻人的决定。
- **「待确认 N · 全部启用」**：N 固定按上述严格口径另查一次（与当前筛选无关——它答的是"这个库积压了多少待确认"），点击先 confirm 写明条数与后果；批量接口只对 `source=llm_extract && enabled=0` 生效、**上限 500 条**（防一次误点全库），返回**实际**启用条数。启用成功后清空筛选、回第 1 页，否则启用后的词可能落在筛选外、管理员以为没生效。
- **审核开关 `term.manual.review` 与词表同页**（`ParamGroup.KB`，与敏感词页「处置规则与词库同页」同一判据）：它决定"抽出的词要不要我确认"。关掉只影响**之后**抽取的词，已待确认的词仍需「全部启用」；**人工新增/编辑/删除/启停不受它约束**。
- **来源文档列**（`medical_term.doc_id`）：模型抽取的词显示「首次抽到它的文档」标题（列表页一次批量取标题，不逐行查），人工维护显示「—」；文档删除后术语不回删，该列显示「文档已删除」——它回答的是"这个词从哪来"，够管理员判断可信度。

**科室名全库唯一**（写库前拦，不是靠数据库唯一键兜底）：模型输出的是**科室名字符串**，写库与推荐校验都靠"按名字精确匹配"（`DeptService.findByName`）把它换回科室实体。重名会让这一步变成"取第一条"——同一条主诉今天落到 A 科室、明天落到 B 科室，而**页面与看板都看不出异常**。
> 停用科室**不做连带清理**：切片留库、历史记录引用不受影响，停用只作用在导诊入口（挂号页不列 + 推荐校验过滤）。

**映射台账只读**：它的键是 `(症状原文, 主科室)`——同一症状可因不同方向的桶各审出一个主科室、各占一行，每一行都是一次真实审核结论的留痕（谁 approve 的、补过哪些症状）。这里没有"合并/去重"的余地，所以不提供增删改；写入唯一路径是链路 C 的 approve。

**「重新处理」只在 `failed` 且可重试时出现**：判据是 `kb_doc.fail_type`（外部依赖故障=retryable / 输入本身有问题=fatal）与 `reprocessable`（有原文件的才能重跑）。**不问"能不能重跑"这个技术问题，只问"重跑一次可能就好了吗"**——fatal 的件重跑一百遍也是同样的结果。

**落点**：`admin/controller/KbAdminController`（`/api/admin/kb/**`，仅 ROLE_ADMIN）→ `admin/service/KbAdminService`（编排：实体 → 页面形状）→ `kb`（科室/文档/切片/台账/术语的领域规则）与 `async`（任务表与流水线）。

### 7.4 管理端边界与约束

- **管理端是运行时配置与审阅面，不参与在线导诊主流程**：不占 SSE 线程池（连通性探测这类同步外呼同理）、不写 `chat_message` / `guide_record`。导诊记录只由链路 A 写，`actual_dept` 只由挂号确认接口写
- **分层**：页面 → `/api/admin/**` controller（admin 是启动器，只做编排）→ 业务模块 service。参数归 auth（`sys_config` 的属主）、模型信息与探测归 llm（适配层自己的知识）、聚合归 stats（纯读侧）、审核与回流归 feedback
- **口径与参数一律后端定，前端只显示**：能改哪些键（白名单）、取值范围、准确率分母、环比是否可比，全部在服务端判定；前端控件只是提示，不构成约束
- **approve 的落库边界（链路 C）**：映射台账与桶状态**同事务**；合成 chunk **必须走链路 B 流水线**入库——`kb` 是唯一写向量库与 ES 的入口，**不得为审核回流另开直写通道**
- **只读观测类面板归属管理端职责**：`filter_log`（敏感词命中留痕）与 `track_event`（三触点埋点）是管理端应当能查的过程信号；它们只作漏斗/耗时参考，不参与准确率统计（准确率事实仍只有 `actual_dept`）
