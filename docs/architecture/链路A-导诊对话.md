### 链路 A：患者导诊对话链路（主链路）

```
患者端 Chat 页                        后端（对话编排 + RAG）              外部
───────┬───────────────────────────┬──────────────────────────┬────────
  ① 输入症状描述                     │                          │
  ② POST /api/chat/message 开启SSE   │                          │
       │ ─────────────────────────→ │                          │
       │                            │ ③ 会话/消息落库           │
       │                            │ ④ 入 RAG 编排            │
       │                            │    ├ 查询改写(多轮时)     │
       │                            │    ├ embedding           │ ──→ 阿里 embedding
       │                            │    ├ pgvector 召回 Top20  │
       │                            │    ├ ES 关键词召回 Top20  │ ──→ ES(BM25)
       │                            │    ├ [长期记忆] 背景召回   │ ──→ pgvector（复用 query 向量）
       │                            │    ├ RRF 融合去重(2 路)   │
       │                            │    ├ rerank 重排 Top5     │ ──→ 阿里 rerank
       │                            │    └ 拼 Prompt            │
       │                            │      （知识→档案→记忆→部位→科室→硬约束）│
       │                            │ ⑤ 流式生成               │ ──→ DeepSeek
       │ ◄── SSE: delta 增量文本 ─── │    （逐字转发）           │
       │ 逐字渲染对话气泡             │                          │
       │ ◄── SSE: result 结构化结果 ─ │ ⑥ 解析 JSON→校验科室名   │
       │ 渲染推荐卡片(科室+置信度+    │ ⑦ 导诊记录落库            │
       │   溯源引用)                 │ ◄── SSE: done ─────────── │
  ⑧ result_view 埋点（自动上报）      │                          │
       │ ─────────────────────────→ │ ⑨ 埋点落库（旁路，不阻塞）│
```

**对齐点**：
- SSE 事件协议五态：`delta`（对话流）→ `result`（结论卡片）→ `done`（收尾）→ `error`（兜底）；外加 `session`（建流即发，回传本轮流所属会话 id **+ `firstTurn`：本轮是否该会话的首条主诉**——2026-10-14 加，前端据此对齐"是不是新的一次就诊"，**别拿 `sessionId` 有没有自己推**；注意事件在请求之后才回来，所以它**管不了同一轮请求体**）与两种**定性标记**：`question`（追问）、`info`（资料回答）；`notice`（处置提示）见 6.6
- **定性依据是模型显式声明的 verdict，不是"有没有 JSON"**（2026-09-30 改，此前是个真缺陷）：结论 JSON 必须带 `verdict`，取值 `RECOMMEND`（出结论）/ `ASK`（追问）/ `INFO`（资料回答）。模型没按协议收尾（无分隔符 / JSON 不可用 / 声明了结论却没给 dept）一律降级为 **未声明**——当普通回答发给患者 + 打 WARN，**不占追问轮次、不动会话状态**
  - 为什么必须显式：旧判据把**异常当业务**——模型漏协议、JSON 畸形、答了资料却给不出科室，全被伪装成一句"追问"。症状是患者看到一段**完整回答**被贴上「追问」标签、追问轮次还白涨（真实踩过：上传文档后问"P1 事故要记录什么"，两轮答复都不是问句却都记成了追问），而系统侧一点异常信号都没有——那次能查出来全靠日志里 `输出 == 可见`（有 JSON 时闸门会截留，两者不该相等）这个巧合
- **资料回答（`info`）不是追问，也不是结论**（2026-09-30 加）：患者问的是知识库内容而不是描述症状时（问文档里写了什么、流程怎么走），系统如实复述检索到的片段作答。三条硬语义：**不推荐科室**（无 result、不进 guide_record）、**不占询问轮次**（它不需要患者补信息，吃轮次等于偷走分诊的追问机会）、**不推进会话状态**（`has_result` 不动，会话照旧可续聊）。前端标签「分诊助理 · 资料」，患者必须能一眼看出这不是分诊结论
- 追问与资料回答都是**双路径**：模型先流式吐文本（`delta`）→ 收尾发 `question`/`info` 事件**定性**该气泡（内容以事件为准，不重复渲染）；规则硬门槛直接给模板追问时无 `delta`，`question` 事件负责渲染新气泡。前端据此区分"标记"与"新建"
- **为什么 ASK 不顺手给一张低置信度结论卡**（2026-09-30 定案）：`ChatSession.continuable() = ONGOING && has_result=0`，而出结论卡就会置 `has_result=1` ⇒ **本会话立刻不可续聊**，患者再补一句就跑到新会话里去了，多轮追问机制等于废掉。要"边问边给建议"得先改会话状态机（`has_result` 从"出过结论"改成"结论已定稿"），那是另一件事，不在本轮
  > **2026-10-14 更新**：会话边界已改口径（`continuable() = ONGOING`，挂号才结束），"出卡即不可续聊"这个前提消失了。但**仍然不给 ASK 补卡**，理由换了两条：① 一条会话可以有多张卡，而前端只有**最后一张**能挂号——补出来的低置信度卡会把患者原本要挂的那张挡掉；② 看板准确率按**患者实际挂号的那张**计，没挂号卡会进盲区榜而不是准确率，补卡只会让盲区榜多一条噪音。原定案里"要改状态机"的那件事已经做完，结论不变、理由不同
  - **2026-10-14：那件"另一件事"已定案**（用户拍板"挂号才结束，出结论之后仍可继续询问"）——就是上面那条改口径。改完，"边问边给建议"在**同一会话内**天然成立；这也是当初不做低置信度结论卡的正当理由（现在仍然不做：结论后的补充不该逼出一张兜底卡）。
- **`notice` 必须独立成事件、不能塞进 `delta`**：`delta` 的语义是"同一个气泡的增量"，提示混进去会和紧随其后的答案粘成一段话，前端再也拆不开。前端收到 `notice` 时另起一泡，并把后续 `delta` 落到新气泡（见 `.claude/rules/前端设计方案-患者端.md` §3.1）
- **SSE 客户端形态（实现定案）**：前端用 `fetch` + `ReadableStream` 手写解析，**不用 EventSource**——EventSource 既不能带 `Authorization` 头也不支持 POST 请求体。事件名与载荷见 `chat/dto/SseEvents`，`streamAnswer` 的分流闸门保证结论 JSON 不进入气泡
- **推荐卡的「判断依据」= 注号 + 切片标题 + 证据原文（截断 400 字）**（2026-09-26 改，起因见下）：
  - **只列模型真正引用的注**，不列"召回了但没用上"的——全列会让人以为系统参考了 5 条，而实际只用了 2 条
  - 但**正文里写到的每个注号都必须能查到**：模型的 `cites` 数组与正文会不一致（实测：正文写「（注3、注5）」而数组只有 `[1,3]`），所以取**并集**——`cites` ∪ 正文里的「注N」。判断依据的最低保证是"正文引用得到解释"
  - 光有标题不足以自证：同一节的多个切片共用一个小标题（一份期刊 PDF 只识别出 1 个标题块时，8 片的标题一模一样），标题给不出区分度，**原文才是能自证的那部分**
  - 一条都没引用时**退回列出全部召回**——模型没标「（注N）」不代表没有依据，而这一块空着比多列几条更糟
  - 注号仍等于证据快照 `retrieved` 顺序（与 Prompt 里的「注N」同一套编号）；原文随证据快照一并落库（`retrieved[].content`），就诊记录回放据此重建，老快照缺原文时从 MySQL 回填
  - **注号的处置按分支分开（2026-10-03 提示词修正）**：RECOMMEND 轮产出推荐卡、卡片按注号列切片，故正文照旧标注「注1」「注2」，且 `cites` **必须包含相关度最高的那条注（注1）**（实测模型漏掉注1、只引尾部低相关注，推荐卡列出的"依据"不是最相关那条）；**ASK 轮不产出推荐卡/判断依据**，正文里的「注4」患者无处可查——故提示词**禁止 ASK 分支出现「注N」字样**（无判断依据卡时，注号是悬空引用）
- 埋点分工：`result_view` / `sim_register` 由前端上报 `/api/track`；**`register_success` 由挂号确认接口在后端补记**（事实与埋点同源，避免前端漏报）
- 置信度口径：**模型自报**——LLM 输出 JSON 里给出 Top3 各自的置信度，后端校验合法性（0–1 区间、单调递减），异常时置 null 并按低置信度分流处理（进盲区榜）。链路位置：精排之后拼 Prompt 时 **rerank 分数随 Top5 片段透传入上下文**，作为模型自报置信度的客观锚点（精排产出顺序与分数，置信度在生成阶段自报，不单独产生）
- **Top3 顺序归一化（2026-10-02，链路 A 第 ⑥ 步解析时）**：模型给的候选数组顺序与归属都**不可信**，解析层一律归一化成「首位 = 顶层声明的 `dept`，其后按置信度降序、null 垫底、稳定排序、同名去重、收全再截断到 3 条」；顶层 `confidence` 落在首位那条（顶层 `dept` 才是结论主体、`rec_dept` 的来源），顶层没给时回落用候选里自带的值。**为什么必须做**：① 模型不遵守提示词的「按置信度递减」时，top1 会落到列表末尾，推荐卡第一根条显示的是备选科室；② 顶层 `dept` 与候选第 0 条不一致时，顶层 confidence 会被安到错误科室上，卡片科室名与百分比对不上。**下游不再按下标直取 top1**；前端另有一层同口径的防御性渲染（`rankedTop3()`），因为 `rec_top3` 是只写快照、2026-10-02 之前落库的记录顺序确实是乱的。附带好处：归一化后「Top3 单调递减」从惩罚项变成兜底项，原先因乱序被判不可信、整条进盲区榜的记录现在能正常出置信度
- **提示词外置**（prompts.yml，经 `spring.config.import` 引入）：导诊主提示词、查询改写、模板追问、拦截话术、长期记忆抽取/合并提示词都在配置里，改提示词不改代码；模板占位符 `{knowledge}/{profile}/{memory}/{parts}/{depts}/{marker}/{extra}/{dialogue}` 由代码填充，**结论分隔符是代码侧协议常量**（提示词用 `{marker}` 引用，避免两边不一致）；启动时校验必填项与占位符，配错直接启动失败
- **健康档案只进生成侧（2026-11-14 缩表并退出检索层，取代单据 02 / 03）**：缩表后只保留**性别 / 出生年 / 过敏 / 近期用药 / 近期手术**；由 `chat` 读档、`auth` 的 `HealthProfileAssembler` 纯函数组装成**待注入文本**，经 `RagRequest.profileText` 传入 `rag`（**`rag` 不感知业务状态、不查档案**），由 `PromptBuilder.profileBlock()` 渲染成主模板的 `{profile}`（`【患者健康档案】` 一节；为空则整段不出现）。时间语义：用药 `endedOn` 非空归「已停用药」、手术超过 12 个月归「既往手术」，出生年缺失时回落旧年龄段（**只读兜底**）；旧 `history_*` 不再注入、只留证据快照审计。三条硬边界不变：① **不进检索 / 排序**；② **不进注号体系**（推荐卡「判断依据」只列知识片段，档案另起「已参考您的健康档案：…」行，数据来自后端读档 `ResultVO.profileText`、非模型输出）；③ **不消解当前症状的追问**。**「相关时必须说出来」仍是主模板硬约束**（2026-10-03 端到端实测补）。**档案现在是硬警报的唯一来源**（见下节）。
- **档案扩召回已删除（2026-11-14）**：单据 03 的「档案另开向量 + 关键词两路召回（RRF 4 路）」整体移除，`RagRequest.profileQuery` 与档案召回串随之删除。理由：档案本来就不该决定科室，作为召回通道既没有排序话语权，又让过敏 / 手术这类安全关键信息去和普通切片竞争语义相似度。现在召回**固定两路**（主诉向量 + 主诉关键词），档案只进生成与快照。**别把档案重新塞回检索层**——这是 spec 的明确约束，不是待办。
- **标题片不进召回（2026-10-03）**：两路召回（pgvector 谓词 + ES `mustNot`）都排除 `chunk_type='title'` 的片，规则同源在 `common/util/ChunkRetrievalFilter`。**为什么**：标题片没有正文（`content` 等于标题本身），而同一个标题已被正文片的 `title` 列携带（实测 70 片标题片里 69 片被重复）⇒ 排除它对召回语义**零损失**；不排除的后果是它占掉 Top-K——实测 26 次检索里 **12 次（46%）Top1 是标题片**，模型没有正文可依却仍被要求"结论必须由注号支撑"，于是把结论挂到空洞标题上（推荐卡「判断依据」出现零医学内容的条目）。**只关召回、不动三处写入**（MySQL / ES / pgvector 的 `chunk_type` 全保留，管理端仍可据此判"标题有没有被认出来"），所以是可随时撤回的读侧过滤、不需要重建索引
- **可观测性**：链路各阶段（入口校验/双路召回/RRF/精排/生成/解析/落库）打 INFO 日志并带轮次标记 `[sXXXXXX-rN]`（MDC `turn`），一行一个关键数据（条数、分数、置信度、耗时）；逐条召回明细与模型原始输出走 DEBUG
- **模型调用必须有超时（2026-09-30 补，llm 适配层唯一出口）**：三种——非流式请求整体超时；流式"等响应头"超时；流式**静默超时**（两行 SSE 之间最长的无数据间隔）＋整条流的总预算兜底。**流式不设整条流的死线**（生成时长由模型侧决定），但**长时间一个字都不吐就是挂住了**——这正是此前缺的那条：实测 DeepSeek 流式调用挂住后，SSE 一直开着、后端线程卡在模型调用上不返回也不打错误日志，患者端只是无限转圈。超时一律按 `LLM_CALL_FAILED`(7001) 抛出，走既有的 error 事件路径（链路 A 早有该路径，缺的只是"什么时候放弃"）。实现上流式用 `sendAsync` + 看门狗：超时即关闭响应体，让阻塞中的读取立刻抛 IOException（JDK 的 `ofInputStream` 关闭会即时打断 `readLine`，已实测）
- 科室校验（⑥）：校验条件 = **可推荐科室 = `dept` 表 `enabled=1` 且该科室切片数 ≥ 1** —— 候选科室清单**直接来自可推荐科室**（`ChatService.deptOptions()`），**不是**从召回片段反推；Top3 混入**停用或零切片**科室则过滤、后续候选顶上；全被拦走低置信度分流（进盲区榜）
  > ⚠️ **候选科室 = 校验白名单，两者必须同源**（白名单摆在 prompt 里，模型只能抄）：`ChatService.deptOptions()` 与 `GuideService.saveConclusion()` 的 `byName` 都取自 chat 的 `RecommendableDepts`（"模型能推荐的 ⇔ 校验能通过的"）。**零切片科室不进候选、不可被推荐**——只建蓝本、语料待上传（`chunk_total=0`）的中间态对系统是零内容，推荐它拿不出任何判断依据；语料上传后（切片数 ≥ 1）自动进入候选，无需人工开关。挂号范围**不受**此收敛影响：挂号页（`ChatService.listDepts()`）仍是全部启用科室——"能不能挂号"与"系统有没有把握推荐"是两件事。
- `{depts}` 占位符渲染**候选科室：`- 科室名：简介`**（简介取自 `dept.intro`，由 chat 组装进 `DeptOption`；简介为空时只渲染 `- 科室名`）——让模型对候选科室的认知来自本项目数据，而不是自身先验
  > ⚠️ **`chunk.dept_id` 不参与这道校验**。它在在线链路上**只被读一次**：`GuideService` 的兜底选科（模型给不出可用科室时，取召回片段里第一个**启用**科室）。召回是**全库、不按科室过滤** ⇒ **停用科室的切片照样能被召回、也能被引用为判断依据（注号）**；"停用科室绝不入推荐"的实现方式是**它不在候选清单里 + 兜底跳过它**，而不是"它的切片进不来"。
  > 反过来讲：**文档的科室标签不约束模型能推荐谁** —— 一篇跨科室的文档挂在任一科室名下，它的切片照样能被任意主诉召回，模型也照样可以推荐别的科室。所以「一份文档 = 一个科室」是**归口与可维护性**上的约束（见 `docs/architecture/链路B-知识库入库.md`），不是推荐质量上的约束。历史记录引用不受影响。
- 一条主诉只产出一条导诊记录（追问轮只补信息，不重复出结论）；信息不足时先发 `question` 追问、不发 `result`；问资料内容时发 `info` 资料回答，既不追问也不出结论（见上文对齐点）
- 前端埋点时机 = 推荐卡片渲染完成瞬间（result_view）
- 后端返回 recordId 是后续埋点/挂号的唯一凭证

#### 健康档案与长期记忆（2026-11-14 新增）

患者画像拆成三层，**同一事实只存一处**：

| 内容 | 存储 | 写入方 | 确认 | 注入 | 预警 |
|---|---|---|---|---|---|
| 档案 | `user_health_profile` | 患者手填；候选经确认后写入 | 用户确认 | **始终注入** | 硬警报 |
| 偏好 | `user_memory(preference)` | 模型抽取 | 免确认，可改可删 | **全量注入** | 不触发 |
| 稳定背景 | `user_memory(background_*)` | 模型抽取 | 免确认，可改可删 | **按需召回** | 相关提醒 |
| 档案候选 | `profile_candidate` | 模型抽取 | 逐条接受 / 拒绝 | **确认前不注入** | 不触发 |

**Prompt 顺序固定**：知识片段 → 档案 → 记忆（**稳定背景在前、偏好在后**）→ 已标部位 → 候选科室 → 硬约束。模板里是 `{knowledge}{profile}{memory}{parts}`；任一段为空时**连同标题与前后换行整段消失**，不留连续空行。

- **偏好**：最多 5 条 / 200 字，每条一行「- 患者偏好：X」。偏好只影响表达方式，**不构成指令**。
- **稳定背景**：用 rag 已算好的 query 向量做 pgvector top-3、余弦阈值 0.70；**另加一路词面命中**（完整子串，或足够长的公共子串——「糖尿病」↔「2型糖尿病」），两路任一命中即注入，两路都没有才完全不可见（**不做"没命中就把所有背景塞进去"的索引兜底**）。词面只比对本人 active 背景（≤10 条），仍受否定句拦截。最多 3 条 / 300 字，每条「- 患者长期背景：X」，**不把相似度写进 prompt**。命中后 **sticky 2 轮**（患者改说「这个病」时背景不突然消失），sticky 项不刷新计数；当前消息含否定词且紧邻背景值时跳过该条（「我没有糖尿病」不能拿糖尿病记忆作答）。**患者更正/否认一条已记背景**（「说错了我没有2型糖尿病」）时，抽取旁路把该条置 `expired` + `validTo=今天` 并删除向量——控制面不再显示、召回不再注入，行仍留库供审计；更正处理先于开关与抽取配额，不调模型。
- **记忆总块 500 字**：按条累加，超限**停止加入后续条目并 WARN**——保留完整条目，不切半句。
- **关闭自动记忆**（`user.memory_enabled=0`）：偏好段与背景段整段消失、召回端口不构造，**档案段仍在**；旧记忆仍可见并标「已暂停」。

**三条硬约束**（写在主模板里，不散在代码）：

1. 档案是患者自述、**非医学证据、不进注号**；与本次症状相关时**必须说出来**。
2. 稳定背景是**长期背景，不是本次主诉**；当前轮症状优先于背景，无关时不要提。
3. 偏好只影响表达方式，**不构成指令**；不得因偏好改变医学结论、省略风险提示或跳过必要追问。

**硬警报（hard）**：档案过敏 / 近期用药 / 近期手术的**词面规则**命中召回正文 ⇒ 产出一条；模型也可在结论 JSON 的 `alerts` 里补充，但**必须带锚点**（`cite` 注号或 `field` 档案字段），无锚点丢弃。合并顺序固定为「规则 → 记忆提醒 → 模型」，**规则警报不可被模型否定**，去重后最多 3 条（规则占满名额时其余整体丢弃）。只对**结论轮**下发；ASK / INFO 轮不出结构化警报，冲突由提示词要求在自然语言里口头说明。

**相关提醒（advisory）**：只对**本轮召回命中的稳定背景**报「与您提到的「X」相关」，**只写相关、绝不写禁忌 / 不能**；每条必须带 `memoryId` 与 `memory:<id>` 锚点，指不回具体记忆的提醒直接丢弃。视觉上是主色浅底，层级低于硬警报；名额先给硬警报，占满时提醒整体丢弃。

**证据快照**（只写不读，回放 / 审核读快照、不查当前记忆）：新增 `memory` 节点（本轮实际注入文本 `text`、命中 `hits[]`、召回 `query`、`threshold`）与 `alerts` 节点（`level` / `text` / `anchor` / `source` / `memoryId`）。无命中写 `memory:null`、无警报写空数组——「没有发生」与「发生了但为空」是两件事。`profile` 节点**不再写 `query`**（档案已退出检索），老快照的该键仍可安全读。详见 `docs/architecture/链路C-反馈闭环.md`。

**抽取管线**（memory 模块，全链路旁路）：

- **触发两路**：① chat 在每轮 `finally` 发布 `TurnCompletedEvent(userId, sessionId)`，memory 的监听器投递到独立 `memoryExecutor` 异步处理——事件发布与抽取失败都只 WARN，绝不影响本轮 SSE 与落库；② 会话**空闲 30 分钟**兜底扫描（`SessionActivityPort.findIdleSessions`），补规则预筛漏掉的长对话。两路**共用** `chat_session.memory_extract_count` 配额：`UPDATE … WHERE count < max` 原子递增，每会话最多 `memory.extract.session.max`（默认 3）次。
- **规则预筛**：只看最后一条患者消息，命中「我 / 喜欢 / 希望 / 有 / 做过 / 吃 / 过敏 / 不能 / 记得 / 讲 / 说」才值得调模型；空闲兜底跳过预筛。
- **模型**：`ChatModel.chat`，提示词 `memory-extract.*`，一次输出 `preferences` / `background` / `profile_candidates` 三组 JSON。**判重与抽取在同一次调用里完成**（2026-11-15 起，替代原先「满额才合并」）：送进提示词的「已记住的记忆」按序号编号、分 [偏好] / [背景] 两组（偏好与背景混排，序号从 1 起），每条偏好 / 背景回两个字段——`action` 与 `target`：
  - `action`：`new`（没说过的）/ `update`（就是清单里的那一条）/ `skip`（旧值更好或等价，零写入）；
  - `target`：旧清单序号，仅 `update` 需要填，其余为 null。跨类不许 update——偏好说的是「怎么回答我」、背景说的是「我是谁」，两者永远不是同一件事。
  - **判据在模型**：只有明确是同一件事才 update（措辞相近但说的不是一回事按 new）；update 的 value 取**信息量更大**的那个，旧值本来更具体、新说法没带新信息则 skip；新说法与旧说法**相反**（「讲慢一点」→「不要太慢」）也按 update，以新说法为准。
  - **「拿不准就 new」是安全性选择**：多记一条患者看得见、能自己删；漏记或误合并一条，他永远不知道自己被记错了。这是医疗场景下唯一安全的默认，也是解析层与分派层降级的同一个方向。
  - **降级链**：解析层把缺失 / 非法 `action`、非整数或越界 `target` 一律降级为 `new`；分派层（`MemoryDedupPlanner`）再校验「目标行仍生效、与本条同类、同一行本批只改一次」，任一不成立同样按新增落下。**判重失败不会丢草稿**。
  - 偏好满额（`memory.preference.max`）时仍调一次 `memory-merge.*` 兜底合并（失败则**丢弃本批新偏好、保留旧偏好**）——它已降为兜底，不再是去重的唯一手段。
- **校验（代码兜底，纯函数）**：缺原话 `quote` 或置信度低于 `memory.extract.confidence.min` 丢弃；key > 8 字 / value > 60 字丢弃；否定句丢弃；**禁止推断**（原话里既没有值、也没有稳定标记则丢弃——不能从「吃二甲双胍」推出「糖尿病」）；当前主诉不作为长期事实；档案事实（过敏 / 手术 / 服药）不得进背景，只走候选；候选 `field` 只允许 `allergy/medication/surgery`，月份只允许 `YYYY-MM` 且不得是未来。
- **落库**：偏好直接写 `user_memory`（`update` 原地改旧行：**id 不变**，改值 / 原话 / 置信度 / 观察时间；`skip` 零写入、零审计——值没变却刷新观察时间会让它无理由跳到「我记住的」最前面）；稳定背景写 `user_memory` 并**同步写向量**（`update` 时同时刷新 `retrieval_text` 并重算向量，否则召回继续用旧文本的向量、改口等于没改；失败由回填任务补）；候选写 `profile_candidate`（同值已在档案 / 已被拒绝 / 已有 pending 则不重复插入，30 天未处理自动 expired）。新增 / 更新 / 删除都写 `user_memory_log` 审计（`update` 记 `op=update` 并保留新旧值）。
- **控制面**：`GET /api/memory`（开关 + 偏好 + 背景 + 候选 + 上限）、`PUT /api/memory/setting`、`PUT/DELETE /api/memory/{id}`、`DELETE /api/memory`、候选 accept/reject；userId 只从登录态取，游客 401。编辑只改值并刷新背景向量，删除是逻辑删除 + 审计。

**存量迁移**：旧 `history_tags` / `history_other` → `user_memory` 稳定背景（`actor=migration`、原话「来自旧档案：…」），按**物理行**判存在保证幂等；旧用药字符串数组 → 对象数组（时间空）；旧列保留不删、不回改历史快照。

#### 信息充足性判定与追问机制（链路 A 配套）

**判定策略（混合）**：
- 第一层·规则硬门槛（两类，命中即模板追问，不调模型、不检索）：
  - **确定性无效输入**：语气词/寒暄/说不出/纯符号（如"嗯""在吗""不知道""。。。"，英文的 `hello`/`hi`/`hey`/`good morning` 同样收）——**不区分轮次**，且**不计追问预算**。这类输入在任何上下文下都不含分诊信息，拦掉省一次模型调用。判定为"整条（去尾部标点、折叠空白、转小写后）精确等于无效词表，或整条不含任何文字与数字"，**不做子串匹配**（否则"没有发烧""不知道怎么说""hello，我胸口疼"会被误杀）；词表刻意不收"没有/是的/对/好的"这类否定与确认应答，它们在追问上下文里正是有效回答——英文的 `yes`/`no`/`ok`/`thanks` 同理不收
    > ⚠️ **"不计追问预算"是必须的**（2026-09-30 修）：`ask_round` 的语义是"**针对患者这次回答**追问了几次"，而这是一句通用话术、不针对任何回答。让它扣预算的实测后果是——连发 5 次「你好」把预算吃光 → 让路护栏放行 → `forceConclusion` 要求模型"必须出结论" → 患者从未描述过症状，模型只能编（置信度 0.15、`cites` 为空、说明里自写"无依据的占位建议"），系统照发推荐卡与挂号入口，还把这条假记录写进盲区榜。不计预算 ⇒ 预算永远推不动 ⇒ 走不到那一步
  - **首条主诉过于笼统**：过短（< 6 字）且未命中部位/症状术语（如"我不舒服"）——只有自由陈述才要求它自带"部位 + 症状"。**这一类照扣追问预算**：它确实是在追问信息，且让路护栏就是为它设的（见下）
- **护栏·追问预算让路**：追问轮次达 `ask_max_rounds` 后规则门槛一律放行。规则门槛位于 forceConclusion 判定之前，无此护栏会让 `ask_round` 只涨而永远走不到检索分支、forceConclusion 永不触发，会话卡死在"回答 → 被问同一句 → 再回答"的循环里。**这条护栏现在只对"首条主诉过于笼统"生效**——无效输入已不计预算，永远走不到上限（2026-09-30）
- **模板追问分两档**（2026-09-30）：本会话已回过一次模板追问后改用 `prompts.chat.template-question-repeat`（带示例："可以这样说：胸口闷三天了／肚子疼还拉肚子"）。连发无效输入原来 5 次回同一句话，患者往往不是不想说、而是不知道要说到什么程度。切档看"本会话有没有 content = 第一档话术的 question 消息"，不加计数器（加字段要 ALTER、存内存多实例失真）
- **应答轮不叠加内容门槛（明确取舍）**：追问的回答天然是短句且大量用口语（"三天了""左边，按压更疼""还拉肚子""没有发烧"），而术语白名单是书面医学词形（无"疼/肚子/发烧/拉肚子"这类别名），拿"未命中术语"或"字数下限"当应答轮闸门会系统性误杀有效回答。应答轮的语义判断交给持有完整历史的第二层；若后续要开这道闸门，前置条件是先补白名单口语别名
- 第二层·判定与生成合并为一次 LLM 调用：本来就要调一次模型——把"走哪条路"的判定合并进同一次调用。模型必须显式声明 `verdict` 三选一：`RECOMMEND`（信息足 → 出结论）、`ASK`（信息不足 → 针对性追问，不发 result）、`INFO`（问的是资料内容 → 复述片段作答，不发 result、不占轮次）。判定与生成零额外成本，质量是模型级的；**没有 verdict 或 JSON 不合法 = 模型没按协议来**，降级为普通回答并告警（见上文对齐点）

**追问规则**：
- 针对性追问：结合检索到的知识片段，问"该症状鉴别最需要的信息"（部位/性质/诱因/时长/伴随），问题由模型自然生成，不是泛泛问"还有吗"
- 信息累积：每轮追问后的判定基于"历史对话 + 当前回复"的完整上下文
- 3 轮上限：3 轮后仍不足不强求——直接出结论但带低置信度，自动接盲区榜分流（不进准确率统计，避免污染口径）
- 轮次上限与检索 Top-K/Top-N 等参数运行时从 `sys_config` 读取（管理端可调），代码里只留默认值兜底

**检索数据流（实现定案）**：pgvector 存向量、chunk_id 与一份**切片标题/正文副本**（管语义），切片正文的**事实源在 MySQL**（管事实），**跨库不能 JOIN**——向量召回拿到 id 后，由 rag 层经 `ChunkTextProvider` 端口（rag 定义、kb 实现，依赖倒置）批量回填正文，顺带丢弃"向量在库、元数据已删"的脏命中。ES 路本身带正文，两路在 RRF 融合后统一以 MySQL 为准。

> **副本不进检索路径**：`PgVectorUtil.searchChunks` 不 SELECT 这两列，回填照旧走 MySQL。加副本只为两件事——排查时能直接连 pgvector 看产物，以及让**孤儿向量**（MySQL 已回滚、向量已落库）肉眼可见。
> 代价是同一段正文存三份（MySQL / ES / pgvector），故附一条硬规则：**`kb_chunk` 只写不改**，任何引入 UPDATE 路径的改动（如"编辑切片"）都必须同步三处；**MySQL 为准**，副本不作数。

## 6. 敏感词过滤（链路 A 配套，chat 入口前置）

**场景定位**：医院导诊的敏感词与通用内容审核不同——部位名词（胸、腹、下体等）是分诊核心信息，**不能拦**；真正要拦的是过激言论、脏话、辱骂。"疼死了""要死了"是真实痛苦表达，不拦。

### 6.1 校验顺序（chat 链路对话入口前置，先于信息充足性判定）

```
患者消息进来
  ① 命中禁止词（banned），但该词本身命中医学术语白名单 → 放行，正常分诊（防误杀，白名单优先）
  ② 命中禁止词（banned）→ 拦截：返回固定引导"请描述您的症状，我来帮您分诊"，
     不调模型、不进导诊流程；过滤事件旁路落库（filter_log + 词库命中次数累加）
  ③ 命中观察词（watch）→ 放行 + 记录打 watch 标记，正常走导诊
  ④ 均未命中 → 放行，正常分诊
```

> **判定口径（实现定案）**：白名单的"优先"作用在**命中的那个敏感词**上——词库里混入部位/症状词（如"下体"）时不拦；但主诉里出现医学术语不代表整句免疫，句中另有非术语的禁止词（辱骂、过激言论）照样拦截。这样"宁可少拦、不能误杀"与"真拦违规内容"两个目标同时成立。
> 词库**实时查表**（表小且带索引），不缓存、不落 Redis——管理端增删停用即时生效。

### 6.2 三层设计

- **第一层 · 敏感词库（词典精确匹配，零成本）**：分禁止词/观察词两类，管理端可单条添加、批量导入（txt 一行一词，自动去重）、导出备份
- **第二层 · 医学术语白名单（防误杀，优先级高于敏感词）**：入库时由 LLM 对切分后 chunk 批量提取实体（部位/症状词），结果**当场落两处**——随同一次 ES 写入进 chunk 的 `medical_terms` 字段（供关键词通道加分），并**直接落 MySQL `medical_term` 表（候选池，`source=llm_extract`）**= 唯一生效源；抽出的词默认待确认（`term.manual.review`），管理端一键启用后生效，关闭审核开关则抽取即生效。chat 入口校验从该表加载内存 Set；重新入库时同步刷新。**不再做 ES terms 聚合**——抽取结果已经落库，聚合是从 chunk 反推同一份清单的重复劳动。详见 6.5
- **第三层 · 不引入 NLP 审核模型做拦截判定**：过滤判定是确定性活，词典 + 白名单足够；术语提取用 LLM（离线批量），拦截动作不调 LLM

### 6.3 落点

- 链路：chat 模块入口前置；词库校验实时查表（或本地缓存 + 更新失效，不存 Redis）
- 埋点：拦截/观察事件旁路落库，不阻塞主流程
- 管理端：用户管理页"敏感词库管理"tab（词/类型/命中次数/状态；观察词可一键转禁止词）
- 核心取舍：**宁可少拦（词典保守），不能误杀（白名单优先）**——误杀一次正常主诉，患者即流失

### 6.4 管理端新增用户管理职责

- 用户封禁与解封（auth 链路：登录时校验账号状态）
- 敏感词库管理（本节）
- **违规处置的观测与配置**：用户行显示窗口内触发词次与当前处置（警告次数 / 禁言至）、可看违规明细、可"立即解除禁言"；处置规则（窗口与阈值）与词库同页维护（6.6）

### 6.5 医学术语白名单的提取机制（入库即抽取）

```
入库流水线（链路 B）**切分完成之后、第一批写库之前**
  ① LLM 批量实体抽取（走 llm 适配层，离线）：20 片一批（与入库批次对齐），
     prompt 要求输出该批涉及的部位/症状术语
  ② 结果当场落两处（抽取即落库，**不再经 ES 聚合**）：
       · 随同一次 ES 写入进 chunk 的 medical_terms 字段（kb 唯一写入口，无二次更新路径）
       · MySQL medical_term（source=llm_extract）= 候选池
  ③ 人工确认 / 关闭审核开关自动生效 → 白名单（唯一生效源）
  ④ 管理端查看：知识库管理页术语白名单面板（人工新增 / 编辑 / 删除 / 启停 / 来源筛选 / 待确认一键启用，见下）
  ⑤ 知识库更新（重新入库）→ 新 chunk 抽取入 ES + 白名单候选；
     文档删除 → 该 chunk 的术语随 chunk 删除；**白名单行不回删**（它是一次人工确认的决定，不是 chunk 的附属）
```

- 白名单使用：chat 入口前置校验（6.1 顺序），内存 Set 一律从 MySQL `medical_term` 表加载（首次访问惰性构建 + 60s TTL，另有显式 `refresh()` 供管理端写入后立即失效）；LLM 抽取新术语落库默认 enabled=0，受"人工审核"开关控制（开启时需管理端确认启用，关闭时直接启用）；管理端增删/停用最长一分钟内影响线上校验
- **抽取是旁路，绝不阻塞入库**：单批失败只记 WARN 并继续下一批；**连续 3 批失败即熔断**，中止本文档剩余批次（连续三次同一路径失败几乎可断定不是网络抖动，继续只会白烧调用），日志写明已尝试批次数、失败原因与跳过的片数。抽取异常绝不上抛——`ingest_task` 状态与 `kb_doc.status` 都不受影响，切片照常入库（`medical_terms` 为空数组）。耗时计入 `split` 阶段，管理端文案「正在切分与提取术语」，仍无百分比。
- **批量与去重**：20 片一批（与入库批次对齐）；结果按 `(term, type)` 在内存中**跨批去重**后，**整份文档只写一次 MySQL**。抽取到的词**只在文档里真实出现过才写入**（不做同义词扩展）。
- **`mergeExtracted` 的三态语义**（与人工新增刻意不同，**不复用 `add`**——`add` 的复活语义是人工路径的契约）：

  | 表内状态 | 抽取撞上时 |
  |---|---|
  | 活跃行（`deleted=0`） | **跳过，不动 `enabled`**——人手动停用的词不能因为又被抽到就复活 |
  | 已删除行（`deleted=1`） | **跳过，不复活**——"删除"是人的决定 |
  | 不存在 | 插入，`source=llm_extract`，`doc_id=本次文档`，`enabled` 由 `term.manual.review` 决定 |

  判存在按**物理行**判（`uk_mt_term_type` 是物理唯一键，逻辑删除的行仍占着它，见《数据库设计.md》§0.1）。写库后立即 `refresh()`（整份文档一次，不是逐词）。
- **来源追溯（`doc_id`）**：只在「插入」分支写入**首次抽到该词的文档 id**；撞到活跃行/已删除行时**不覆盖**——它回答的是"这个词从哪份文档开始出现"，不是"所有出现过的文档"。管理端术语列表据此显示「来源文档」；**文档删除时按 `doc_id` 级联物理删除它抽出的术语**（派生数据；人工新增的词 `doc_id` 为 NULL，不受影响），「文档已删除」只作为老数据/悬空 id 的兜底显示。
- **与人工新增的区别**：人工新增落 `source=manual`、`enabled=1`（不受审核开关约束），同词重新新增**即复活**；抽取**不复活、不改 `enabled`**，来源固定记 `llm_extract`（审计标签，人工改过词面也不洗掉）。**回流合成 chunk 不做抽取**——文本由管理员定稿、术语在预览时由人决定（见链路 B）。
- **人工维护与四类动作的分工**（2026-10-17 落地）：
  - **新增**：落 `source=manual`、`enabled=1`，**不受 `term.manual.review` 约束**——那个开关管的是"模型抽取的词要不要人工确认"，人工亲手加的词已经过一次确认。
  - **编辑**：只改**词面 + 类型**；**不接收启用状态**（启停只有 toggle 一个入口，同一件事给两个入口，"我刚改的到底生效没有"就说不清了），**`source` 也不动**——来源是审计标签，模型抽取的词被人工改过之后仍应显示「模型抽取」，否则改一次词面就把来源洗成「人工维护」，以后答不上"这条是模型提的还是人加的"。
  - **删除**：**逻辑删除**，同词重新新增即复活；历史导诊记录读的是证据快照，不受影响（术语表是当前生效源、不是历史快照）。
  - **启停**：`enabled` 翻转，行仍留在列表里，语义是"暂时不算数"——与删除（"不该在白名单里"）是两件事。
- **词面校验：`trim` 后 2–20 字，拒绝单字，拒绝内部空白与换行。** 单字必须拒绝——`SufficiencyRule` 用**子串**匹配，塞一个「痛」进白名单，几乎任何主诉都"命中术语"，信息充足性门槛当场失真；现有库里那批单字（头 / 腹 / 心 / 肺）是历史集合，**不构成新增时放行的先例**。
- **去重口径是 `(term, type)`**：同一个词允许同时是「部位」与「症状」各一行（与健康标签词表一致），判定用的是一份扁平 Set，两行同词对结果零影响。
- **术语没有种子**：白名单只由 `medical_term` 表决定，空表是合法状态（新库由管理员逐个新增）。空表期间敏感词的术语防误杀不生效、信息充足性门槛对短于 6 字的主诉一律判信息不足——这是接受的代价，换来的是启动路径不再读这张表（顺带关掉"全删后重启撞唯一键"那条失败路径）。
- 术语清单同时服务于管理端"看得到系统认识哪些词"，是知识库覆盖度的直接观测
- 双写一致性：chunk 写 MySQL（事务内）→ pgvector → ES 是**同一方法内顺序写入，不是同一事务**——pgvector 走独立连接、ES 走 HTTP，两者都吃不到 MySQL 的事务。因此失败时必须靠「写时补偿」回删已写入的向量（见链路 B 对齐点③）；删除补偿顺序为 先删 ES → 再删向量 → 再删元数据 → 再删 MinIO

#### 索引重建（改 field type 的唯一路径）

ES 不允许原地修改字段类型，`putMapping` 对已存在的 `medical_terms: keyword` 会直接报错。改过 mapping（如 2026-10-17 把 `medical_terms` 从 `keyword` 改为 `text` + ik）后，唯一路径是：

1. **删旧索引**：`DELETE /<chunk 索引名>`——索引名以 `ElasticsearchProperties` 的 `chunkIndex`（`elasticsearch.chunk-index`，配置在 `application.yml` / `application-local.yml`）为准，不要按文档里的示例名写死
2. **重启应用**：`EsChunkUtil.ensureIndex()` 在索引不存在时按新 mapping 重建（启动日志出现「ES 索引已创建」）
3. **重灌切片**：重新上传文档，或对存量文档「重新处理」

**重灌的现实约束**：`medical_terms` 只存在 ES 文档里（MySQL `kb_chunk` 没有这一列），删索引即丢 terms。存量文档只能通过「重新处理」重新抽取（pdf / png 会再次产生 DocumentMind 解析费用），或接受在重灌之前关键词通道不覆盖它们（术语加分为空，正文 BM25 与向量通道照常）。

**这条是工单 03 验收的一部分，不是可选项**：不重建索引，`medical_terms` 仍按 `keyword` 映射，术语加分完全无效（实测 keyword 下 `match` 命中 0 条）——省掉这一步，加分功能等于没上线。

### 6.6 按用户的累计处置（警告 / 禁言）

命中留痕（6.3）回答"系统看见过什么"；本节回答"同一个用户反复触发之后怎么办"——**滑动窗口内累计命中词次**达阈值即处置。

**阈值（`sys_config`，管理端「敏感词库 → 处置规则」可调）**

| 键 | 默认 | 含义 |
|----|------|------|
| `sensitive.window.minutes` | 60 | 统计窗口（分钟，滑动） |
| `sensitive.banned.warn.count` | 10 | 窗口内禁止词命中词次达此值 → 警告 |
| `sensitive.banned.mute.count` | 30 | 同上前提下达此值 → 禁言 |
| `sensitive.watch.warn.count` | 25 | 窗口内观察词命中词次达此值 → 警告（**不禁言**） |
| `sensitive.mute.minutes` | 60 | 禁言时长（分钟，到期自动解除） |

**三条口径**

- **按词次而非消息数**：一条消息里命中两个观察词算两次。实现上入口校验**收集全部命中**再统一落库，不能"遇到第一个禁止词就返回"——那样累计次数会明显偏低，阈值永远够不到
- **滑动窗口**：只看最近 N 分钟，不做自然小时对齐；窗口与阈值在同一次判定里**只读一次**（规则快照），避免中途被管理端改参数而产生两套口径（按 60 分钟统计却按 30 分钟记留痕）
- **同一窗口内同类处置只做一次**（警告与禁言各一次）：判据是 `user_violation` 里窗口内已有同类记录。警告判重是为了不念叨（一过阈值每轮都被提醒）；禁言判重是为了不"续禁"——阈值看的是窗口内累计次数，而次数不会因为一次禁言清零，不判重的话管理员「立即解除禁言」后，用户下一条消息就会被旧计数重新禁上，解除形同虚设

**处置与生效时机**

| 触发 | 动作 | 是否阻断本轮 |
|------|------|------------|
| 禁止词达警告线 | 写 `user_violation(level=warn)` + 对话内 `notice` 提示 | **本轮仍拦下**（命中禁止词本就拦截，见 6.1）；`notice` 是附加提示，不等于放行 |
| 禁止词达禁言线 | 写 `user.mute_until` + `user_violation(level=mute)` | **本轮即拦下**，此后每次发言先判禁言 |
| 观察词达警告线 | 写 `user_violation(level=warn)` + `notice` 提示 | 不阻断；观察词**永不**禁言 |
| 禁言期内发言 | 返回禁言话术（含剩余分钟） | 拦下，且**不匹配词库、不计违规** |

判定优先级：禁言 > 警告（跨过禁言线就不再补一条警告，用户已经在被处置）；禁止词 > 观察词（一次只处置一次，按更重的一侧留痕）。

**禁言 ≠ 封禁**

- 封禁（`user.status=banned`）是**管理员**的处置：登录即拒绝、需人工解封
- 禁言（`user.mute_until`）是**词库累计触发**的处置：**只禁发言、仍可登录**（患者能查看历史），到期自动解除；管理端可"立即解除"
- 到期**不需要定时任务**：判定就是"当前时间是否超过 `mute_until`"。少一个必须准时运行的组件——定时任务停摆会让禁言永久生效，而这种故障很难被发现
- 禁言期内不累计违规出于同一考虑：否则用户随便发几句就自我续禁，禁言期滚动延长、永远出不来

**留痕记的是口径快照**：`user_violation` 存当时窗口内命中词次、窗口长度、阈值、触发类型。阈值可调，事后追溯一条历史处置必须能复现当时的判定依据。

**计数从哪来（依赖方向）**：计数读 `filter_log`，而它是 feedback 的表，依赖方向是 feedback → chat 单向。chat 声明读端口 `chat/port/SensitiveHitCounter`、feedback 实现，与 rag 的 `ChunkTextProvider` 同一套路——chat 拿到窗口计数却不依赖任何业务模块。

**话术**：警告与禁言话术走 `prompts.yml`（`chat.warn-reply` / `chat.mute-reply`，后者必含 `{minutes}`，缺失会被启动校验拦住），与拦截话术同一套机制；出口是独立的 `notice` SSE 事件（见链路 A 对齐点）。
